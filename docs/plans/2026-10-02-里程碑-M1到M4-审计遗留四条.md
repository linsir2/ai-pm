## 2. M1 · 确认写入的重复 `remove`（F28）

**一句话**：同一批确认里对同一个 `entry_id` 的多条 `remove`，是**同一条指令**——只该算一条。

**现场（P30 实测，可指到字段）**：L4 第 3 轮 `POST /confirm` → 422
`shape_error: 找不到条目 r-a80daa26#open23`，接受的 45 条**一条都没写**。
草案里 `p14`–`p21`（整合者那条路，text 是被撤下条目的正文）与 `p34`–`p39`（`use_cases.py`
的 carried 清理那条路，text 是"本轮已回答，撤下这条未决项"）指向**同一批 entry id**。

**退出条件（可测）**：

1. 新造的草案里，同一条目**只会有一条** `remove`；
2. **老草案**（修好之前存下来的、带两条重复 remove 的）走 `POST /confirm` 也能 200、版本 +1；
3. `ProposalCommitter` 把"合并掉了哪几条"报得出来（domain 层可断言）；
4. 真跑复验：同形态输入那一轮不再 422。

**明确不做**：不动 `document._apply_remove` 的报错语义（手改路径依赖它）；
不动 `replace` 的顺序语义；不加端点、不改 schema、不动前端。

**tasks 级计划**：`docs/plans/2026-10-02-P32-M1-确认写入的重复remove.md`（本次一并给出）。

## 3. M2 · `integration` 的 180 秒墙（F30）

**一句话**：现在这个模型下，整合调用**平均 1.5–2.5 分钟、最长 5.8 分钟**，已经两次撞上 180 秒的墙。

**现场（P30 实测）**：

| 车道 | integration 次数 | 平均 | 最慢 | 说明 |
|---|---|---|---|---|
| L2 | 9 | 149.7s | **346.7s** | 1 次 177.52s 撞 180s 超时 → 重试成功 |
| L3 | 13 | 111.6s | 333.4s | 同上 |
| 其余 | 8–11 | 73–123s | 98–174s | 没撞墙但已经很近 |

对照 P20（旧模型 `deepseek-v4-flash-0731`）：平均 ~103s、最慢 103.5s。

**要做成什么样**（三条路，等拍板，见 §6）：

1. **抬超时**（`.env` 一行的代价）：`PMSTUDIO_MODEL_TIMEOUT` 180 → 300。好处是改动最小；
   代价是"卡住的时候一次要等 5 分钟"，且一轮最坏 3 次尝试 → 15 分钟。
2. **换更快的模型**（或给整合单开一个模型）：口径要写进 `04-未决.md`，
   而且**全批结论必须重跑**（P30 的 189 次调用都是在当前模型上量的）。
3. **给整合瘦身**：整合提示词最大（一万多字符）——但这是提示词工程，
   要真跑对照，成本比前两条高。

**退出条件（可测）**：选定一条路之后，**同车道两轮**真跑里
`integration` 的 `max_secs` 落在墙内、且 `errors_sample` 里没有 timeout。

**明确不做**：不改 `num_retries=0`（那是 P5c 特意关掉 SDK 内部重试换来的墙钟准确性）。

### 3.1 M2b · 供应商能力差异：`json_schema` 不可用时怎么办（**2026-10-03 新增**）

**怎么冒出来的**：P33 做 M0（"供应商抖动"）时，作者在 08:05 把 `.env` 换成了
`openai/deepseek-v4.1-flash`，随后**主闭环一次调用都发不出去**。实测能力矩阵：

| 模型 | `response_format: json_schema` | `json_object` | 不带 `response_format` |
|---|---|---|---|
| `deepseek-v4.1-flash` | **400 ×2（稳定拒）** `This response_format type is unavailable now` | OK | OK |
| `qwen3.8-27b` | OK | OK | OK |

**两条要分清**（我一开始把它们混成一条，已经在 P33 里纠正）：

1. **真抖动**（已修，M0）：`qwen3.8-27b` 在 08:15 短暂拒收、08:17 起 8/8 通过。
   网关原来把 `invalid_parameter` 一律当不可重试 → 一次抖动 = 一次调用判死。
   处置：`TRANSIENT_HINTS` 加**那条很窄的** `"response_format type is unavailable"`（已交付）。
2. **能力差异**（**未做**，就是 M2b）：`deepseek-v4.1-flash` **永远**不支持 `json_schema`。
   网关每次都带 `json_schema` → 这个模型上**产品不可用**（3 次尝试全 400 → 502）。

**要做成什么样（推荐）**：**回落，而不是放弃**。网关捕获那条明确的 400 之后，把这一次请求
改成 `response_format: {"type": "json_object"}` 再试一次。

- **契约不变**：`LLM 契约`要的是"输出必须过 schema"，那**由我们自己的 packet 校验强制**
  （`_is_json` + 各 agent 的 pydantic 解析 + 失败重试都在）；`json_schema` 只是帮模型守规的助攻。
- **只在那一条 400 上回落**：别的 `invalid_parameter`（如 glm 的 `enable_thinking` 互斥）照样立刻失败。
- **留痕**：回落发生的次数要能从 `model_calls` 看出来（留样本来就有 `ok`/`error`），
  报告里要写"这个模型是靠回落跑通的"。

**退出条件（可测）**：`PMSTUDIO_MODEL=openai/deepseek-v4.1-flash` 时，真跑一轮能走到草案卡；
单测钉两头（那条 400 → 回落成功；别的 400 → 不回落、立刻失败）。

**备选（不推荐但要拍板）**：什么都不改，改成"只支持 json_schema 的模型才能用"——
写进 `04`，换模型时靠 `gate.py` 拦（现在的闸门就能拦：它判红）。

### 4.1 M3b · 联网提名太保守（**2026-10-03 新增**）

1. 文档/材料里已有的 → 别提；
2. 用户能回答的（业务口径、取舍、偏好）→ 那是**问他**；

P30 **0 条**。所以不是功能坏了，是**分析者在这份输入上变保守了**（中间换过模型）。

**为什么归到 M3 而不是另开一个**：它和"矛盾判据退化"是**同一个通道、同一个文件**
（`infrastructure/llm/prompts/analyzer.md`）、同一种病（"该说的没说"）、同一种验法
（只能靠 eval/真跑，没有便宜的单测），而且两处一改就要一起真跑一轮。

**要做成什么样**：先在 M3 里**量一次**（拿一份明确依赖外部事实的输入问分析者，看提不提名）：

- 提了 → 说明只是那份输入偏"问用户"，M3 只做矛盾判据；
- 没提 → 把第 3 层的判据写得更可判（例如"输入里出现法规名、标准名、第三方系统名时，先找有没有
  对应条款要查"），并补一条 eval 用例钉住。

**退出条件（可测）**：`scripts/eval.py` 新增/改的那条用例在真模型下 PASS，
且**不牺牲** M3 原有的 8 条；再补一次 live 一轮（见 P33 ②）。

## 7. 断点续跑：**产品支持，缺的是驱动**（2026-10-03 核查结论）

作者问："这个断点续跑，我们本身项目支持吗，还是你自己写了个脚本续跑？"

**答：产品本身支持，而且写在设计里。** 证据四处：

| 证据 | 内容 |
|---|---|
| `domain/round/round.py::Round.resume()` | 按 `failure.at_step` 把轮次恢复到失败前那一步 |
| `application/use_cases.py::RetryRound` | 注释原文："**继续这一轮**：失败就先 `resume`；**没失败就直接接着跑**。为什么允许对'没失败'的轮调用：关页面 / 进程崩了以后，轮停在 `seats_running`，它不是 failed 状态，但同样需要接着跑" |
| `tests/e2e/test_resume.py` | 两条 e2e，标题就是"**换一个进程**（同一个 db 重建容器）接着跑"：一条"A 交回、B 崩 → 只补 B"，一条"席位全交回但整合挂了 → 重启复用编号" |
| `infrastructure/graph/graph.py::RESUME_ROUTES` | `seats_running → seat_round`、`started → analyze`——`POST /retry` 就是那个"继续"按钮 |

`04-未决.md` E3 也早写过：**席位轮是调用级续跑**（只补 `pending_seats`，已交回的不重跑）。

**缺的是审计驱动那一环**：`drive.py` 原来**只在 `step == failed` 时**才点 `/retry`，
于是 `seats_running` 这种"不是失败、也没有等待卡片"的半途状态会被 park 成**未知等待态**、退出码 10
——P33 ① 真踩到了。**处置**：给驱动加一段"半途状态 → 点一次继续（409 就等 20 秒再点）"。
**不新建里程碑**（产品侧不用动）；已在 P33 交付，并从 live 里验过（驱动打印"轮停在
seats_running（不是失败，也没有等待卡片）→ 点一次「继续」"）。

**真正"还没做"的那一条**（`04` E3 里明确写着**不做**，这里只记账、不进里程碑）：
**进程崩在单次模型调用内部**的续跑——那要 provider 侧支持，最小续跑单位是"一个动作 = 一次 `ainvoke`"。
