## 1. 现状核对（对着代码，不对着印象）

| 设计里写的 | 代码里的事实 | 差在哪 |

| `01` F6/F9/F10/E4 记忆层、工具层、讨论区、索引层 | 都没有 | 设计里明确"以后"，本文不动它们 |

一句话：**主闭环（输入→问→答→写→版本）是通的；"闭环之外还差什么"缺三样——能不能交付、
凭什么信它、卡住了怎么办。**

## 2. 三个根因（"不扎实"到底指什么）

1. **完成度有三套语言，没有一套是判据。**
   `01` §4 是形容词；`Document.gaps()` 只管功能字段；`status.ts` 只管本轮。
   三者互不相同，而且都不回答"能不能交付"。→ 需要 **就绪度（readiness）**：把形容词改写成
   可执行的判据，输出一份"差 N 项"的清单，同时喂给 AI 与界面。
2. **交付物不存在，所以"可靠"无从检验。**
   文档只活在库里和界面上；没有导出、没有版本对比、没有"这版比上版改了什么"。
   → 需要 **导出** + **版本 diff**：把文档变成可以递出去、可以对比的东西。
   （这也是 `01` 里本来就写了 v1、但一直没做的 F3/F19。）
3. **信任靠留痕堆，现在缺三块。**
   出处链 ✓、草案三组 ✓、失败原因 ✓；缺"这条意见为什么没被采用"（C5 后半）、
   "上一版到这版改了什么"（F1）、"这条内容现在还作不作数"（F5 跨轮编号）。
   → 需要 **信任三件套**。

三条线依次是本文的 A / B / C。

## 3. 设计 A · 交付闭环（就绪度 + 导出）

### 3.1 就绪度：把"合格标准"变成可执行的判据

**判据只有六种**（少而清晰，全部纯代码、无模型）：

| code | 判据 | 例子 |
|---|---|---|
| `section_empty` | 某章没有任何非空条目 | s1 一条都没有 → blocker |
| `section_min_entries` | 某章至少 N 条非空条目 | s2 至少 2 条（目标 + 非目标）→ blocker |
| `section_kind_present` | 某章至少要有一条某种 `BlockKind` 的条目 | s9 至少一条 `decision`；s12 至少一条 `acceptance` |
| `feature_field_empty` | 功能必填字段为空（**已有**，就是 `gaps()`） | login-wechat 缺 `acceptance` → blocker |
| `open_blocking_question` | s11 里有**阻塞型**未决条目 | "登录页上线时间未定"→ blocker |
| `cross_section_link` | 结构性关联 | 某功能的 `dependencies` 非空，但 s7 没有任何 `interface` 条目 → warn |

输出统一形状：

```python
Severity = "blocker" | "warn"
@dataclass(frozen=True)
class ReadinessItem:
    section_id: str        # s1..s13
    code: str              # 上表那六种之一
    title: str             # 人话："背景与问题还没有内容"
    detail: str            # "至少要有 1 条：现状/问题/不做的代价"
    severity: Severity
```

**哪些条款判不了、就明说判不了**（这是"扎实"的关键）。`01` §4 里"事实与推测分开"
"验收清单每条能独立判定真假""关键决策有理由"这类**语义**条款，纯代码判不了。
处理方式：降级成 `warn`（结构存在性检查 + 标题提醒人去读），并在文档里列一张
**"只能人看"清单**——不假装判了。

**判据表（初稿，逐章）**

| 章 | 判据 | 级别 |
|---|---|---|
| s1 | ≥1 条非空 | blocker |
| s2 | ≥2 条非空（目标 + 非目标） | blocker |
| s3 | ≥1 条非空 | blocker |
| s4 | ≥2 条非空（本期范围 + 本期不做） | blocker |
| s5 | **有至少一个功能子树**；每个功能的必填字段非空（复用 `gaps()`） | blocker |
| s6 | 有功能却没有任何 `steps` 条目 | warn |
| s7 | 有功能 `dependencies` 却无 `interface`/`entity` 条目 | warn |
| s8 | ≥1 条非空 | blocker；"六项表态"降为 warn（判不了具体项） |
| s9 | 有技术约束却无 `decision` 条目 | warn |
| s10 | ≥1 条非空 | blocker |
| s11 | 无阻塞型未决条目 | blocker（有非阻塞未决 → warn） |
| s12 | ≥1 条 `acceptance` | blocker |
| s13 | **永不判**（系统按版本生成，见 3.3） | — |

**为什么不用 TOML 数据驱动？** 判据要能执行、要有测试、要能一眼看懂"为什么报这条"。
表驱动省下的那点改动，换来一套解析器和更差的报错。等出现"用户自定义判据"再说（不在 v1）。

**契约变化**

- 新文件 `domain/authoring/readiness.py`：`Severity` / `ReadinessItem` /
  `ReadinessChecker.check(view: DocumentView) -> tuple[ReadinessItem, ...]`。
  **纯函数、只读 `DocumentView`**，不碰别的上下文（守住 05 §1 的分层）。
- `Question.blocking: bool = False`（补 `02` §⑤ 已定但没实现的那条）。判定规则写死：
  `target.field ∈ REQUIRED_FEATURE_FIELDS`（acceptance / exceptions / goal / audience / name /
  one_liner）→ blocking；`target` 是章节级且 `section_id ∈ {s1,s2,s3,s4,s5,s8,s10,s12}`
  （那几章的合格标准是 blocker 级）→ blocking；其余（含 `zone=preference`）→ 非阻塞。
  **规则算，不问模型**；`open_question_proposal()` 把标记写进 s11 的文本前缀
  `〔未决·阻塞〕`。
  - 为什么用文本前缀而不是给 `Entry` 加字段：`Entry` 是核心值对象，序列化/手改/导出全要跟着动；
    现在只有一种标记需求，不值得动契约。**升级触发条件**：出现第二种标记（如"待补""假设待验"）时，
    把它升级成 `Entry.flags`，判据改成读结构化字段。

**数据流（就绪度）**

```
Document（聚合）
  └→ view(): DocumentView（现有投影，够用：sections→blocks→entries/field/feature_slug）
       └→ ReadinessChecker.check(view)  ← 纯代码，无 IO，无模型
      └→ tuple[ReadinessItem]
                 ├→ context.render_readiness() → 追加到三个提示词的 $document_state
                 │    （Analyzer / 席位 / 整合者：让 AI 被"本章还缺什么"驱动）
                 ├→ dto.ReadinessItemView → WorkspaceView.readiness（界面）
                 └→ deliverable.render_markdown()（导出头部与缺章标记）
```

`render_readiness()` 的输出长这样（追加在文档正文之后，**只讲缺口，不复述内容**）：

```
## 本章还差什么（系统按 01-规格 §4 的合格标准算的）
- s1 背景与问题：还没有任何内容（至少 1 条：现状 / 问题 / 不做的代价）〔阻塞〕
- s5 功能需求：login-wechat 缺 5 项必填字段：名称、服务的目标、面向角色、异常与边界、验收标准〔阻塞〕
- s6 业务流程与交互：已有功能但没有一条主流程〔提示〕
```

**让 AI 被缺口驱动**——这条比界面上的红点重要得多：现在席位只知道"文档是空的"，
不知道"哪一章按标准还没达标"。把就绪度清单塞进上下文后，席位的问题会自然指向
`acceptance` 这种必填字段，而不是泛泛地问"要不要考虑性能"。
但要同时加一句硬规矩，否则会变成"为凑判据写废话"：**补缺口不等于填满；拿不准就出题**
（`tests/application/test_context.py` 里钉住这句在提示词里）。

### 3.2 门禁：提示，不挡

- **写入**：不受就绪度影响（现在也不挡，别改）。
- **导出**：允许"未就绪也能导"，但文件头部盖章：`就绪度：未通过（阻塞 9 项 / 提示 7 项）`。
- 理由：门禁挡写入会让用户被自己没答的问题卡死（与 C6/C7"用户永远能走到草案卡"同一条原则）；
  而"能不能交出去"本来就该由人拍板——系统只负责把缺的东西摆到台面上。
- 这条是**拍板点 1**。

### 3.3 导出：一份可以递出去的 Markdown

**形态**：`GET /projects/{id}/export/markdown` → `text/markdown; charset=utf-8` +
`Content-Disposition: attachment; filename="<项目名>-v7.md"`。
界面：顶栏一个「导出」按钮，直接下载（不做预览页——省一处会腐坏的第二渲染）。

**长什么样（骨架）**

```markdown
# 产品文档 · 订单中台（v7）
> 导出时间 2026-09-24 12:40 · 文档版本 v7
> 就绪度：未通过（阻塞 9 项 / 提示 5 项）——见文末《未完成项》

## 1. 背景与问题
（本章为空：至少需要 1 条）        ← 空章显式写出，不许静默省略

## 5. 功能需求
### 5.1 order-export · 订单批量导出
- 一句话描述：把订单按筛选条件导出成表格〔E1〕
- 验收标准：
  - AC-1 5 万条内 60 秒可下载〔E4 E9〕
- （非必填空缺：优先级 / 用户故事 / 主流程 / 输入与输出 / 状态与规则 / 依赖）

## 12. 验收与迭代
## 13. 版本历史        ← 由 versions 生成，不读 block 树
| 版本 | 时间 | 触发 | 摘要 |
| v7 | … | manual | 手工改一条：…… |

---
## 附录 A · 出处（只给编号与一句话摘要）
E1 · 用户输入（第 1 轮）· 想做个订单导出的功能
```

**四条硬规矩**

1. **纯函数**：`application/deliverable.py::render_markdown(view, *, refs, readiness, versions)`，
   无 IO、无模型。同一份输入永远导出同一份字节——"权威"的前提是确定性。
2. **遵守 `04` D5**：附录只给 `编号 + kind + 一句话摘要`，**不带 `raw_span`**（原话留在系统内）。
3. **偏好区不进正文**：按 `01` §5 的约定，偏好区不进交付；如要保留，作为附录 B
   并明确标"不进交付物"（**拍板点 2**）。
4. **s13 由版本生成**：文档 block 树里的 s13 保持空、永不参与判据；导出时用 `Version[]` 渲染。
   好处：版本历史这份"系统事实"不需要 AI 或用户维护，也不会和 `document_versions` 打架。

### 3.4 界面上放哪

- **底栏 `VersionBar`**（已存在）：`v7 · 6 / 13 章有内容` → 追加就绪度：
  `v7 · 6 / 13 章有内容 · 就差 9 项 ⚠`（点开列出 blocker/warn）。
- **章节头**：`sectionStatus()` 增加一种来源——readiness 的 blocker/warn
  （优先级：`conflict > open > gap > warn > filled > empty`）。
- **顶栏**：「导出」按钮。
- ⚠️ 顺带修一个现在就有隐患的地方：`status.ts` 判"有内容"用的是 `blocks.length > 0`，
  而 `filledSectionCount` 也走它。将来若给 s8 加固定子块（见拍板点 3），空块会被算成"有内容"。
  统一改成**按非空 entry 判定**。

## 4. 设计 B · 信任三件套

### 4.1 C5 后半：意见为什么没进卡片

现状：`Questionnaire.dropped` 只装"归因对不上"。整合者把一条意见**默默丢掉**时没有留痕。

设计：

- 报文加 `dropped_opinions: [{handle, reason}]`（模型自己写理由；`handle` 形状 `seat.x:O1`）。
- 装配层把它与已有的 `dropped_attributions` **合并成一条通道**：
  `Round.dropped: tuple[DroppedItem, ...]`，`DroppedItem{handle, reason, source: "integrator"|"assembly"}`。
  对不上号的 handle 仍然不判死整轮，只是 `source=assembly`、理由写"没找到这条席位条目"。
- 双向可查：闭环区每个席位包下面一行"它说的 4 条里，2 条没进卡片（原因：…）"；
  点进去能跳到那条意见。

### 4.2 F1：版本历史 + diff + 回退

已有基础：`document_versions` 表在存整棵树快照；`Document.rollback_to()` 已实现且有测试。

设计：

| 动作 | 端点 | 实现位置 |
|---|---|---|
| 列版本 | `GET /projects/{id}/versions` | `GetVersions` 用例 → `VersionSummaryView[]` |
| 看差异 | `GET /projects/{id}/versions/{a}/diff?to={b}` | **纯函数** `domain/authoring/diff.py::diff_snapshots(a, b)` |
| 回退 | `POST /projects/{id}/versions/{n}/rollback` | 新增 `RollbackVersion` 用例，**写入仍走 `ProposalCommitter`**（守卫白名单里只有它持有 `DocumentWriter`） |

diff 的形状（按 entry 比对，因为 `entry_id` 稳定——原地替换 + 快照留旧值）：

```python
DiffGroup(target_label, added=(entry…), removed=(entry…), changed=((before, after), …))
```

前端：底栏 `VersionBar` 点开抽屉（`01` §5 草图里本来就画了"版本历史 ▸ v0.4 … 查看差异"）：
版本列表 + 选两个版本看差异 + 「回到这一版」（确认后产生一个新版本，`trigger=rollback`）。

### 4.3 F5：跨轮编号跳转

现状：`api/evidence.ts` 只建"本轮"索引，跨轮的编号查不到（界面上写的是"不在这一轮里"）。

设计：`GET /projects/{id}/evidence/{eid}` →
`{eid, kind, text, summary, round_id, seat_id, question_id, chain: [eid…], used_by: [entry_id…]}`。

- 按编号查是 O(n) 扫描账本（单项目几千条以内没问题）；真要快，等索引层一起加。
- 前端：本轮回退到端点查询 → 得到 `round_id` 就切到那一轮（`GET /rounds/{id}`）+ 高亮；
  得到 `used_by` 就滚到那条内容（`#entry-<id>`）。**这就是"点编号跳回原文"的完整实现**。
- `raw_span` 只在**界面上**给（点开看原话），**不进导出**（D5）。

## 5. 设计 C · 韧性 + 缩编

### 5.1 网关超时（今天实测到的洞）

`LiteLLMGateway.complete()` 现在不传 timeout。设计：

- `Settings` 加 `PMSTUDIO_MODEL_TIMEOUT`（默认 120 秒）+ `PMSTUDIO_ROUND_BUDGET_CALLS`（默认 40 次）。
- 调用传 timeout；超时按现有 `TRANSIENT_HINTS` 走重试（最多 3 次），仍失败 → `ModelCallFailed`
  → 整轮失败（现在会走整合降级出口，见 P4）。
- 顺带收紧参数名：以 litellm 实测为准（`timeout` / `request_timeout`），先写一条真调用测试钉住。

### 5.2 放弃这一轮（卡住时的出口）

- 领域：`Step.ABANDONED`（新步骤）+ `Round.abandon(reason)`；`LEGAL_ADVANCES` /
  `RESUME_ROUTES` 各加一行（`abandoned → END`）。
- 编排：`RoundRunner` 记当前任务的 `asyncio.Task`；`POST /rounds/{id}/abandon` →
  `task.cancel()` → 节点抛 `CancelledError` → `run()` 里 `except asyncio.CancelledError`：
  **先写"已放弃"状态、再 re-raise**（别吞掉取消，这是这里最容易写错的地方）。
- 界面：正在跑时进度条旁边出现「放弃这一轮」；放弃后这一轮置灰，可以重新输入（新轮）。
- 为什么用新 Step 而不是复用 `failed`：失败是"系统出问题、可重试"，放弃是"人不想要了、别再跑"；
  两者在界面与重试语义上完全不同。
- **取消为什么是安全的**：模型调用一律在事务外（`tests/architecture/test_no_await_in_uow.py`
  守的那条），所以 `CancelledError` 只可能落在 `await` 点（正在等模型），
  **不会落在 `with uow:` 中间**——不会出现"写了一半"的文档或账本。这是那条守卫的第二个红利。
- `abandon` 不走 `RoundRunner.run()`，所以不受 `RoundBusy` 影响（被拦的正是"重试"，
  而放弃恰恰是重试之外的另一个出口）。

### 5.3 模型留样（可开关）

- 新表 `model_calls(id, round_id, purpose, seq, model, prompt_sha, reply_text, usage_json,
  duration_ms, created_at)`；`PMSTUDIO_TRACE_MODEL=1` 时才写（默认关：隐私 + 库膨胀）。
- 只有 infrastructure 知道这张表；`LiteLLMGateway(recorder=…)`，application 完全 unaware。
- 用途：出问题复现（P4 的 `O1` 就是靠重放才定性）、提示词回归对比。

### 5.4 最小 eval（免费拿到"提示词没退化"的证据）

- `backend/evals/cases/*.json`：`{name, user_input, document_fixture, assertions}`；
  断言是**结构性的**，不是文案比对，例如：
  `题目 evidence_refs 只含 E 编号`、`疑问不超过 5 道/批`、`同一字段不重复问`、
  `不新建未授权功能子树`、`席位不超过 7 个`。
- `uv run python scripts/eval.py` → 逐条结果 + 通过率（真模型，不进 CI）。
- 首批 8 条：直接复用 `03-案例与验收.md` 的案例 A/B + P4 那一轮真实输入 + 6 条边界输入。

### 5.5 C8 答案轮缩编（要先把 F16 补齐）

现在答完一批就把整批席位全量重跑。缩编需要"谁管这个面"的映射——正好是 `01` F16 里
写着的"负责章节 / 能读什么 / 能产出什么"，补进 TOML：

```toml
seat_id = "seat.data_scale"
title   = "数据规模与性能"
sections = ["s5", "s8", "s10"]      # 新增
fields   = ["acceptance", "rules"]  # 新增（功能字段）
```

**缩编规则（保守版）**：下一轮席位 = ① 上一轮对该 target 出过意见的席位
∪ ② 映射命中该 target 的席位。常驻席位**不再**强制入选（否则缩不掉）。
`round_.seats` 不变（只决定跑谁，不改编制），所以 R7 不变量不受影响。

**风险**：漏掉一个本该被问到的专业面。兜底：缩编后若整合者认为"信息不够"，
它可以出题（`from_opinions` 空、依据为空都是合法的），不会有静默缺口；
界面上把 `asked_by` 为空的题标成"整合者提的"（前端补一行，P5b 一起做）。

**契约**：现在 `pending_seats` 是从 `round_.seats` 减掉本轮已交回来算的，
缩编要新增 `Round.active_seats`（这一 pass 实际要跑的名单：开场卡确认时 = 用户编制，
答案轮 = 缩编结果），`pending_seats` 改成基于它算；`round_.seats`（用户编制）不变，
所以 R7 与复述卡都不受影响。

## 11. 失败模式（提前想好会怎么错）

| 风险 | 表现 | 兜底 |
|---|---|---|
| 判据太严 | 满屏 blocker，用户干脆不看 | 只有"结构缺失"是 blocker；语义条款一律 warn；每章最多报 2 条 |
| 判据太松 | 导出盖章"已就绪"但其实不能开发 | 导出附录保留"只能人看"清单；门禁不挡写入但盖章显眼 |
| 缺口进上下文后，席位开始"为了凑判据写废话" | 内容变长、质量下降 | 提示词明说"补缺口不等于填满，拿不准就出题"；eval 里加一条"不得为必填字段编内容" |
| 缩编漏掉专业面 | 某轮之后文档缺一个视角 | 整合者仍可出题；闭环区显示"这一轮只请了谁、为什么" |
| 放弃这一轮留下半截状态 | 已交回的席位意见留在 round 上 | 与失败同语义：文档零写入，round 置灰可查 |
