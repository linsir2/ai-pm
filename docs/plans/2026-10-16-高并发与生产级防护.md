# 高并发与生产级防护 · 实施计划

> 2026-10-16。目标：**200+ 并发**，分阶段做，每阶段都有可量的验收。
> 决策（作者拍板）：① 三个维度都要（读/SSE、登录、模型轮次）② 上多 worker ③
> 熔断用 **pybreaker**、隔离舱手写（`asyncio.Semaphore`）④ 多 worker 的 SSE 跨进程
> 扇出与共享限流走 **Redis**。

## 0. 基线（实测，不是估算）

压测工具 `backend/scripts/load_probe.py`（零依赖）与 `/tmp` 的 SSE 探针，同机发压：

| 路径 | 并发 | 吞吐 | p50 | 判断 |
|---|---|---|---|---|
| `GET /api/health` | 50 | 1070 req/s | 43ms | 健康 |
| `GET /api/projects`（SQLite 读） | 100 | 902 req/s | 102ms | 健康 |
| `GET /api/events`（SSE 建连） | 200 | 200 条 / 0.2s | — | 健康 |
| **`POST /api/auth/login`** | 50 | **13 req/s 恒定** | **2354ms** | **队头阻塞** |

**硬伤**：argon2 同步跑在事件循环里。并发 1→50，吞吐一点没涨（12→13 req/s），
延迟从 81ms 涨到 2354ms。并发不换吞吐只换延迟；登录风暴期间**整个事件循环被占住**，
SSE 推送与其他所有请求一起停摆。按该斜率，200 并发登录 p50 ≈ 16s。

**另一个被忽略的事实**：`PMSTUDIO_MODEL_TIMEOUT=300`（单次模型调用 **5 分钟**），
而实测平均 66.7s、失败 8.7% 全是 `APITimeoutError`。一个挂死的调用占住槽位 5 分钟。

**当前为零的东西**：熔断、限流（除登录节流）、缓存、隔离舱、并发上限。
全仓 `Semaphore` 零命中。

## 1. 必须先说清的硬约束：SQLite 写天花板

WAL 解决的是"读不阻塞写"，**不是多写者并发**——不论几个 worker，SQLite 同时只允许
**一个写事务**。我们每轮要写 ~19 条模型调用 + 轮次 + 草案 + 文档版本。

所以本计划**不承诺高并发写入**。多 worker 的真实收益是：读吞吐、SSE 分发、
argon2 这类 CPU 密集的并行（每进程一个事件循环）。写仍然串行。
对外表述一律照实说，不把"读与 CPU 并行"包装成"高并发写"。

## 2. 阶段

### P1 · 登录不再阻塞事件循环（无前置，最高优先）
- argon2 的 `hash_password` / `verify_password` 改 `asyncio.to_thread` 离开事件循环。
- **登录隔离舱**：`asyncio.Semaphore` 限制同时进行的哈希数（默认 `min(4, cpu)`）。
  登录风暴排队而不是把循环压死。密码哈希吃内存（argon2 LOW_MEMORY ≈ 64MB/次），
  并发上限同时是内存上限。
- **验收（已跑）**：判据不是"登录自己变快"，而是**登录期间别的请求还动不动**。
  30 线程登录风暴期间打 `/api/health`：

  | | 改前 | 改后 |
  |---|---|---|
  | p50 | 2182ms | **2ms** |
  | p99 | 2752ms | **16ms** |
  | 吞吐 | 0.46 req/s | 319 req/s |

  登录自身：并发 50 时吞吐 13 → 23 req/s，p50 2354 → 2109ms（argon2 本身就是故意慢的，
  队列深度决定尾延迟，这部分是**设计使然**不是缺陷；闸门的作用是让它排队而不是把机器打死）。
  `PMSTUDIO_LOGIN_HASH_CONCURRENCY` 可拧（默认 `min(4, CPU)`，8 核机器上是 4）。

### P2 · 模型侧防护（熔断 / 隔离舱 / 分层超时 / 重试预算）
- **熔断**：`pybreaker`，**累计依赖失败计数、成功即清零**，到 `fail_max` 开闸
  （低流量时单次失败不许开闸，否则启动第一秒就会误开），只计"依赖不健康"的失败
  （timeout / 5xx / 限流），用户输入错误、schema 不合**不计**——用库的 `exclude` 表达。
  **口径更正（2026-10-16，真库实测）**：原文写的是"滑动窗口**失败率**"，
  但 pybreaker 1.4.1 **没有**这个语义——`CircuitClosedState.on_failure` 判据是
  `counter >= fail_max`，而 `_handle_success` 会 `reset_counter()`。实测 50% 失败率
  交替调用 40 次**永不开闸**。已按你的决定采纳原生语义，计划原文相应更正。
- **熔断的半开探针必须是那次真实调用**：库的 `CircuitOpenState.before_call` 会调
  **同步** `call()` 去跑探针，而我们要保护的是协程——同步路径只会拿到一个从未被
  await 的协程对象，并把它当成"探针成功"当场闭合。实测会漏 `RuntimeWarning`。
  所以我们自己用公开的 `half_open()` 先切半开，再让库用 `call_async` 跑真调用。
- **隔离舱**：在飞模型调用数上限 + 超出排队 + 排队超预算即**快速失败**（返回明确的中文
  错误与 `Retry-After` 语义），不让请求无限堆积。
- **分层超时**：单次模型调用（从 300s 收到有意义的值）/ 轮次总预算 / 外部检索单独一份。
  "25 秒才响应的服务等于已经挂了"。
- **重试**：只重试瞬时失败（timeout、429、5xx），**必须带抖动**（无抖动＝重试风暴），
  且受**重试预算**约束（重试量占原始量的比例有上限）。
- 验收：注入"模型持续超时"时，熔断在窗口内打开、后续请求毫秒级失败；隔离舱满时
  返回 503 而不是排队到超时。
- **默认超时按真跑数据定**：167 次成功调用 p99 131.3s / **最大 143.0s**，故
  `DEFAULT_TIMEOUT` 90 → **150**；`.env` 的 300 同样收到 150——失败调用耗时中位
  恰好 300.2s、最大 900.5s（= 300 × 3 次尝试），300 只是在多占 150 秒去看一个
  必然超时的结果，并且占住隔离舱槽位。病态挂起由熔断兜底，不靠拉长单次超时。

### P3 · 限流（Redis 共享计数）—— 已交付
- **形状更正**：登录节流**早就存在**（`use_cases.LoginThrottle`，`ip|用户名` 失败锁，
  内存滑动窗口）。P3 不是新建限流，是**把已有计数搬到 Redis + 补"尝试维度"**。
- **三维**（三种不同形状的攻击，各挡一种）：
  | 攻击 | 失败锁 `(ip,user)` | per-IP 尝试 | per-username 尝试 |
  |---|---|---|---|
  | 单 IP 撞单账号 | 挡 | — | — |
  | 单 IP 喷很多账号 | **不挡** | 挡（20/分） | — |
  | 很多 IP 撞单账号 | **不挡** | — | 挡（10/分） |
- **状态码分两路**：失败锁仍回 **401**（与密码错逐字节相同——加了限流也不能改掉
  不可枚举性）；尝试超限回 **429 + `Retry-After`**。判定顺序是**先失败锁后速率闸**：
  顺序反了会让失败锁永远轮不到，撞库者拿到 429 就等于把"我被限了"说出去。
- **加 per-username 闸为什么没引入用户名枚举**：计数打在**调用方给的那个字符串**上，
  查都不查库就知道该不该记，`ghost` 与 `alice` 被同样对待，429 逐字节一致。
- **库选型**：`limits`（Flask-Limiter 同源）。不自己写 Lua——原子性、NOSCRIPT 回退、
  集群 hash tag 都已经写好并测过。砍掉 slowapi / fastapi-limiter（middleware 会把
  限流判据塞进 api 层）、redis-ratekit / redis-limiters / self-limiters（v0.1.0 /
  小众 / 作者已声明停止维护）。
- **两个不设就一定咬人的地方**（都是实测值，不是推断）：
  - `max_connections`：redis-py 的 asyncio 池**默认 100**，200 并发直接
    `MaxConnectionsError`。实测配 256 后 200 并发恰好放行 20，无超发。
  - `socket_timeout`：不设的话 Redis"连上但不回包"让登录**卡 5 秒**，
    降级分支根本走不到。设 0.3s 后实测 71-85ms。
- **降级：既不 fail-open 也不 fail-closed**。"完全 open 的限流器不叫控制，
  完全 closed 的是故障制造机"——降级目标是**已经存在的内存闸**：
  Redis 正常→共享计数（精确、跨 worker）；Redis 挂了→进程内计数（不精确但仍挡撞库）。
  降级状态对外可见（`degraded`）+ `dev.py` 告警。连接类异常才降级，
  其它异常照抛（吞掉就等于藏 bug）。
- **全局 API 限流：不做，交给 Caddy**。200+ 并发下 per-IP 全局限流有**自伤风险**
  （同出口 IP 的多人互相限死），而反代在应用之前拦、绕不过。
- **`--proxy-headers` 已补**（否则 Caddy 后面所有请求源 IP 都是 Caddy 的，
  "每 IP 限流"退化成"全站限流"，正常用户互相锁死）。
- 已知边界：`limits` 用**客户端时钟**（不是 Redis 服务端时钟）。多机部署会有漂移；
  **本项目不受影响**——P4 是单机多 worker。

### P4 · 多 worker + Redis 跨进程扇出 —— 已交付

- **`Event.seq` 已删除（2026-10-17）**。它由总线**逐进程**自增（`bus.py` 的 `_seq`），
  而前端 `workspace.ts` 拿它当**全局水位**——4 worker 下 worker B 的 `seq=3` 会被当成
  worker A 的 `seq=9` 的重复而丢掉，**大约 3/4 的事件静默消失**。
  删它的依据不是"修好了"而是**它防的东西不存在**：进程内队列与 Redis pub/sub 都是
  at-most-once。留着它的两条路各自引入更严重的新失效——Redis `INCR` 计数器遇 Redis
  重启归零会把客户端的 `lastSeq` 饿死；服务端时钟派生 seq 则同微秒碰撞会丢一条。
- **扇出拓扑**：每 worker **一条**共享订阅连接 → 进程内扇出到各 SSE 连接。
  不按连接订阅（会打爆 `maxclients` 默认 10000）。实测 `PUBLISH` **0.30ms/次**，
  1000 次 publish / 298ms，两个订阅者各收全 1001 条。
- **靠 Redis 回声而非本地直投**：Redis 会把消息回送给所有订阅者（含发布者自己），
  本地再直投 = 每事件两次。单一投递路径顺带保证**每个连接看到同一条有序流**。
- **`publish()` 保持同步**：改异步要 `await` 37 个业务调用点；`create_task` 会造出
  无人 await 的生命周期风险。做法是入队 + 后台 drainer 任务排空——发布方永远不 await。
- **owner 在总线盖章**：37 个调用点没有一个签名带 owner，而 `ALLOWED_LAYER_IMPORTS`
  规定 application 根本 import 不到 `owner_scope`。`Event.owner_id` 加**带默认值的
  字段**，8 个构造点一行不用改；`owner_visible` 拿到 owner_id 走字符串比较（不查库），
  **缺失时回落查库**（留空 ≠ 谁都能看）。隔离判据的**收口位置不变**，只是快路变快了。
- **降级**：Redis 挂了落回**进程内总线**，与 P3 登录限流同一条规矩。代价是跨 worker
  的事件会漏——事件只是"去重读"的信号，下一次重读会补上。
  **实测坑**：`ps.listen()` 异步迭代器在连接断开时**静默结束、不抛异常**，
  不主动判就会"Redis 死了但没人知道、界面静默不更新"。
- **真多进程冒烟**（`scripts/multiworker_smoke.py`）：2 个真 uvicorn 进程，
  各自开 SSE 连接，随机挑 worker 触发 → **两个 worker 各收 24 条**。
- **顺手修的现存 bug**：`event_stream` 断开时**没有 finally**，内层订阅的清理要等异步
  生成器被 GC——摘除是非确定性的，4 worker 下泄漏速率 ×4。
- **真跑抓出的两个多进程启动竞态**（单 worker 永远看不到）：
  - `PRAGMA journal_mode=WAL` 要短暂持排他锁且**不吃 `timeout=10` 的 busy 等待**
    → 两个 worker 同时启动、都在新库上执行，直接 `database is locked`，
    **两个都起不来**。改为"切完再读一次，是 `wal` 就没事"。
  - 首管理员种子的"users 表为空"检查在 N worker 下不够：都看到空表然后都 insert，
    第二个撞 `UNIQUE(username)` 起不来。改为把"别人已种好"当成功。
- **SQLite 写**：实测 4/8 进程 × 150 INSERT **零争用**（WAL + timeout=10），
  且只串行化**写**，读与 SSE 不受影响。`model_calls` 静默吞 `database is locked`
  仍是**理论风险**，记在 P5。
- **部署约束**：`PMSTUDIO_WORKERS` 与热重载**互斥**（uvicorn 的 `--workers` 不能与
  `--reload` 同用），冲突时 dev.py 退出码 2。`timeout_graceful_shutdown` **必须给**
  ——SSE 是长期未完成的响应，不设超时则关停永久挂住（uvicorn #2635）。
  每条 SSE 连接占 1 个 fd：200 连接 × 4 worker = 800，Linux `ulimit -n` 默认 1024
  就贴着上限，dev.py 会把当前值打出来。
- **实测的真实天花板**：`InProcessEventBus` 的 `DEFAULT_QUEUE_SIZE=256` 才是 SSE 扇出
  的天花板，不是 Redis。1 个事件扇到 200 个订阅者耗时 5008ms（首次含建 200 个
  生成器），200 条事件 → 20 个订阅者各收 200 条且流完全一致。

### P5 · 混沌与常驻护栏
- 故障注入：模型超时 / 5xx / 慢响应、Redis 断开、SQLite 写锁、磁盘满。
- 每种故障下**断言行为**（不是"没崩"，而是"按设计降级"）。
- 压测变成常驻回归：`load_probe.py` 的基线数字进 CI 阈值（如登录 50 并发 p50 < 300ms）。

## 3. 明确不做（以及为什么）

- **不承诺高并发写入**（见 §1，SQLite 的硬约束）。
- **不引入任务队列**（Celery/RQ）：现在的工作流是"一轮跑完再下一步"，异步队列会
  改掉产品语义（`02` 的编排契约），那是另一个决定。
- **不做多区域/多活**：单机部署形态。
- **缓存只加在明确幂等且有 TTL 的读上**（`/schema` 这类每次不变的）。
  文档/轮次是用户自己的可变状态，缓存错了就是"看到别人的旧版本"这类事故。
