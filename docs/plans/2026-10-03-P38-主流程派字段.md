# P38 方案 + 执行结果 · 主流程：把"要写"这件事送到模型眼前（不升必填）

> 这是 **P37 ①（主流程覆盖率）的续篇**。P37 量出覆盖率 48%（历史）/62%（当前配置），
> 加了整合者那句"每个功能要有一条 `main_flow`"却**零效果**；P37 的诊断是"缺口在上游"。
> 作者拍板：按推荐做——**只做 `main_flow`**（不顺手加 `priority/user_story/io`）、
> **继续不升必填**、真跑**同时跑 L2**（多一个证伪点）。
> 状态：已交付。
> 口径来源：`产品设计说明书` §2.6 · `01` §4 · `02` §11.0.43 · `04` G10 · `docs/plans/2026-10-03-P37-*.md`。
> 给执行的 agent：先写红 → 跑到红 → 再实现 → 再跑绿；除非测试本身写错（要说明错在哪），
> 不许改测试迁就实现；`src/` 里不许有假实现。

## 0. 根因（三张只读取证表）

### 0.1 分析者切出来的字段，正好是代码里那 6 个"必填"

两轮真跑 / 29 个功能，各字段的提案条数：

| 字段 | 代码标必填 | 设计说明书 §2.6 | 条数 |
|---|---|---|---|
| name / acceptance | ✔ | 必填 | 37 / 67 |
| one_liner / goal / audience / exceptions | ✔ | 必填 | 37 / 34 / 39 / 46 |
| **main_flow** | ✘ | **必填** | **18** |
| priority / user_story / io | ✘ | **必填** | **4 / 3 / 3** |
| rules / dependencies | ✘ | — | 74 / 6 |

`rules` 高是模型自己爱写；**"设计说必填、代码没标必填"的那 4 个全被饿死**。
机制：字段表（`context.FEATURE_FIELDS_TEXT`）只标"必填"，而那是**就绪度**的标记，
不是"这一轮该写什么"的标记。

### 0.2 分析者标没标 `field: main_flow`，直接决定整合者写不写

跨全部真跑库、按轮统计（只统计有草案的轮）：

| 情形 | 轮数 | 换算 |
|---|---|---|
| 主张标了 → 提案里也有 | **16** | 标了之后 **16/18 = 89%** |
| 主张标了 → 提案里没有 | 2 | |
| 主张没标 → 提案里却有 | 16 | 没标的只有 **16/71 = 23%** |
| 都没 | 55 | |

### 0.3 L5（社区食堂，最差样本）的现场

两轮 20+20 条主张，`field` 分布 = **{name, one_liner, goal, audience, exceptions, acceptance}**
（正好那 6 个必填），`main_flow` 一次都没有 → 62 条提案里 **0 条主流程、0 条 s6**。
P37 加给整合者的那句话在这条输入上没起作用——因为它的输入里**没有这个去处**。

## 1. 决定与改动

| 项 | 决定 |
|---|---|
| `main_flow` 升必填？ | **不升**（升上去 = 每个缺主流程的功能加一条**阻塞**；P30 的 0 阻塞车道会破） |
| 怎么让模型写？ | 在它**每一轮都会读到的两处**加压力：① 字段表那一行写"每个功能都要写：这个功能怎么走一遍（1. …；2. …）"；② 归位表加一行把"怎么走一遍"指到 `s5 + feature_slug + field: main_flow` |
| `priority / user_story / io`？ | **本批不做**（一次只动一个变量好归因；而且一次加 4 类会让每轮提案数明显涨，直接撞 P37 刚量过的 60 条上限与输出体量） |

### 逐文件

| # | 文件 | 改动 |
|---|---|---|
| 1 | `application/context.py` | 新增 `FIELD_PRESSING = {"main_flow": "每个功能都要写：这个功能怎么走一遍（1. …；2. …；3. …）"}`，`FEATURE_FIELDS_TEXT` 拼上它（**只改提示词文本**；`/schema`、前端、落库都不动） |
| 2 | `infrastructure/llm/prompts/analyzer.md` | 归位表加一行：**功能怎么走一遍（正常路径、先后步骤）→ s5 + feature_slug + `field: main_flow`** |
| 3 | `tests/application/test_context.py` | 钉住字段表那行（先红） |
| 4 | `tests/infrastructure/test_llm.py` | 钉住 `analyzer.md` 的归位行（先红） |
| 5 | `tests/domain/authoring/test_readiness.py` | **护栏**：缺 `main_flow` 仍**不产生阻塞** |

**不动**：`schema.py`（不加 `FieldSpec.expected`——那会连带 `/schema` → API → 前端三层）、
`readiness`、整合者 `LIMITS_TEXT`（P37 那句已经在）、端点、落库结构。

```
   ▼
[readiness] 零新阻塞 · 导出第 5 章的功能段里出现"主流程：1. …；2. …"
```

## 4. 真跑验证

三条线一起跑：**L5 两轮 + 导出**（P37 时 0%）、**L2 两轮 + 导出**（P37 时 50%）、**整轮 eval 10 条**。

### 4.1 功能级 `main_flow` 覆盖率（导出层）

| 车道 | P37（改前） | **P38（改后）** |
|---|---|---|
| L1 设备点检 | 4/4 = 100% | 4/4 = 100%（沿用 P36 那轮） |
| L2 连锁健身房 | 4/8 = 50% | **2/5 = 40%** |
| **L5 社区食堂** | **0/1 = 0%** | **2/3 = 67%** |
| 当前配置合计 | 8/13 = 62% | **8/12 = 67%** |

**三条车道的第 6 章全部非空**：L5 的 s6 收了 **3 条**流程（7 步 / 3 步 / 6 步，都带出处编号），
L2 收了 2 条，L1 早就有了。就绪度里 s6 的 warn 在 L5/L2 都消失。

### 4.2 这次到底是谁写出来的（诊断）

L5 第 1 轮的主张里**仍然一条 `main_flow` 都没有**（只标了 name / one_liner / goal / audience），
但两轮后的草案里有 **2 条 `main_flow` 提案**（`pickup-verify`、`menu-admin`）——
**是整合者写的**。原因也说得通：`FEATURE_FIELDS_TEXT` 是**两个智能体共用**的，
那句"main_flow——每个功能都要写：这个功能怎么走一遍"整合者也看得见；
而分析者那一侧，L5 这种"一串目标/角色句"的输入，它仍然照旧切成 s2/s3。

→ **这条改动的有效面主要在整合者**；分析者的归位仍然没被撼动（见 §6 遗留）。
