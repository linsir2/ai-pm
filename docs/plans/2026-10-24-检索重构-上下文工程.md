# 检索重构 · 上下文工程版（最终方案）

> 2026-10-24 · 作者已接受三层重构。本文是**方案的唯一入口**：现状 → 目标 → 删除/搬迁/新增 → 数据流 → 影响面 → 量化验收。
> 实现细节的 TDD 计划在本文 §9 的 P1/P2 立项后另出，不在这份里重复。

---

## 0. 一句话目标

**把"检索"从"UI 搜索 + 开轮时一次性焊死"改成"轮内按步骤取证据、每步按任务投影上下文"；联网从"开轮前勾一次"改成"模型申请、人授权、随时研究"。**

三条硬边界不变：

1. AI 不写文档，写入只走确认端点；
2. 进上下文的每块材料必须有 E 编号，编号只由账本发；
3. 模型调用在事务外，Round 聚合是唯一真相源。

## 1. 现状（代码事实，带行号）

### 1.1 检索器被用在哪

全仓生产代码只有 **两个** `MaterialRetriever.search` 调用点：

| 调用点 | 用途 | 行号 |
|---|---|---|
| `StartRound._pick_materials` | 建轮时库级宽召回 + 收敛 | `use_cases.py:601-604` |
| `SearchProject` | 顶栏搜索框的"材料"那一类结果 | `use_cases.py:4081-4086` |

**席位轮、整合、答题回灌、继续深挖：零检索调用**（`use_cases.py:1289-1360`、`2546-2635`）；它们只反复渲染 `Round.materials` 里已经冻结的块（`use_cases.py:1307`、`2623`、`4538`）。

### 1.2 一次性的代价（实测）

用生产 `select_chunks` 对本地 40 篇语料逐篇模拟"手勾一份材料"：

| 语料 | 篇数 | 文档字符中位 | 手勾用掉预算中位 | `remaining = 4000−used−96` | 结果 |
|---|---|---|---|---|---|
| RAG 长文 | 15 | 7,202 | **3,988** | **−84** | 13/15 篇 **自动段永不触发**（`use_cases.py:599-600` 早返回） |
| 日志短文 | 25 | 1,338 | 1,588 | +2,316 | 整篇进预算 → 手勾臂=oracle（天花板） |

结论：**"手勾 + 自动"在长文场景根本不存在**；而 slots 实验只作用于自动段，因此 v6 原方案在 13/15 篇上会测到逐字节相同的两组。这不是参数问题，是**上下文预算被单一来源吃光**的结构问题。

### 1.3 联网的三条"以为有"

| 入口 | 真实情况 |
|---|---|
| 复述卡勾选 | **唯一真通**。Analyzer 提名（`analyzer.md:66-88`）→ 用户勾（`OpeningCard.tsx:199-241`，默认不勾）→ `SubmitOpening` 执行（`use_cases.py:1027-1123`） |
| 席位/整合中途联网 | **不存在**。两者走 `call_structured`，不带 tools；`run_tool_loop` 只有 `scripts/mcp_probe.py:167` 在调 |
| M8 调研 | **不联网**。`RunInquiry` 只读文档+记忆（`use_cases.py:4743-4895`），产物要用户收下才变材料 |

### 1.4 全局搜索在搜什么

`search_hits`（`dto.py:749-864`）五类结果：

| 类型 | 实现 | 走检索器 |
|---|---|---|
| 条目 / 功能 / 出处 / 席位发言 | `casefold` 子串 | ❌ |
| 材料块 | `SqliteHybridRetriever(limit=50)` | ✅ |

材料结果**只到前端导航**：`SearchProject` 没有 `round_id`，不写 ledger、不写 Round、不进提示词（`use_cases.py:4057-4098`）。材料命中只有"该块已在当前显示的那一轮"才跳得动（`App.tsx:280-289`）。

**因此：用 bench 的 recall@5/MRR 给"检索质量"背书，测的是这个 UI 分支，而不是上下文效果。**

### 1.5 指标错位

| 指标 | 真实回答 | 缺什么 |
|---|---|---|
| bench r5/MRR/假阳性（`retrieval_bench.py:297-400`） | 合成查询能不能搜到 | 默认 `limit=5`，生产 50；不答答案对不对 |
| v4/v5 答案覆盖率 | 给定材料，单轮答案覆盖要点 | 臂与生产语义不一致；单轮答题不是真实轮次 |
| 生产日志（`materials.py:655-664`） | 两路返回多少候选 | 无 caller/round_id/limit/结果 id/是否被引用；建轮检索混入后样本已被污染 |

## 2. 目标形态

### 2.1 三个概念分开

| 概念 | 是什么 | 谁写 | 谁读 |
|---|---|---|---|
| **证据池**（Pool） | 本轮所有"候选过"的块：手勾 + 各步检索命中 + 手动带料 | 建轮/各步检索/手动带料 | 每步投影 |
| **每步投影**（Projection） | 从池里按"本步任务"选出 ≤4000 字、带 E 号的上下文 | 纯函数 + 一个事务 | 当前 agent 的提示词 |
| **证据账本**（Ledger） | 全局只增的 E 号 | 投影时/入池时 | 追溯、导出、界面 |

**关键改动：池可以长，提示词不跟着长。** 每步重新投影，而不是把历史材料一路追加进提示词。

### 2.2 每步投影的选块顺序（确定性）

```
budget = MATERIAL_BUDGET (4000) - SECTION_OVERHEAD (204)
① 手勾材料（pinned）：按本步 query 的相关度取，**有可行自动候选时最多用掉可用预算的 60%**（PINNED_BUDGET_SHARE）；无候选/不可行时可用满
② 本步检索命中的块：按检索分数降序
③ 池里其余块：按本步 query 的 2-gram 相关度
   每份材料最多 _MATERIAL_SLOTS 个槽；同 chunk_id 去重；装不下就跳过（不 break）
```

- **60% 上限（有可行自动候选时）**是这次重构的核心参数：它保证"手勾"仍是骨架，但**不再能把自动检索饿死**。无候选/全部不可行时手勾可用满，不人为留空预算。这是对 §1.2 那个实测缺陷的直接修复。
- 手勾材料的"保证"从"尽量全带"变成"每步有优先份额"——**这是行为变更，需要作者确认**（§8 D1）。
- 没有 query 的步骤（手动带料后的第一次渲染）退回"手勾优先 + 文档序"。

### 2.3 触发点与 query 构造

| stage | 触发位置 | query 从哪来 | 上限 |
|---|---|---|---|
| `SEED` | `StartRound.create`（保留） | 用户原始输入 | 1 次 |
| `SEAT` | `RunSeatRound.__call__`，`pending` 算完之后、组装上下文之前 | 待跑席位的 `sections/fields/focus` + 未答阻塞题 + readiness gaps | 每趟 1 次，≤2 趟 |
| `INTEGRATE` | `IntegrateRound._integrate_with_repair`，`while` 之前 | readiness gaps + `deferred` + 互斥对子 + 未被引用的主张 | 1 次 |
| `MANUAL` | 新端点（搜索框"带进本轮"） | 无 query，直接 pin 指定 chunk | 不限次，按需 |
| `WEB` | 新服务（联网申请/研究） | 模型申请的 query（结构化） | ≤3 条/轮 |

幂等键：`(stage, pass_index)`。`SEED` 用 `0`，`SEAT` 用 `seat_round_count`，`INTEGRATE` 用 `integration_seq`。零命中也要写 trace，否则恢复会反复重查。

> **2026-10-24 修订（实施计划 v2）**：**删除 `OPENING` 阶段**。`opening → seat_round` 之间没有任何模型调用；claims 落库后紧接着就是首趟席位轮，首趟 `SEAT` 的 query 已经用 claims + 席位职责构造。保留 OPENING 只会连着查两次。详见 `docs/plans/2026-10-24-检索重构-实施计划.md` §11-C10。

### 2.4 联网：申请 → 授权 → 执行（**不新增中断**）

- **申请**：Analyzer 的 `web_queries` 保留；`SeatPacket` / `IntegrationPacket` 新增 `web_requests: [{query, why}]`。模型只提名，不执行。
- **授权**：复述卡加一个"本轮允许联网"开关（默认关）。开了 → 申请在下一模型步之前自动执行；没开 → 闭环区出现一张**非阻塞**的「它想查这些」卡，用户点"查"才执行。
- **不新增 `waiting_on`**：它不是第 4 次人机中断，也不改图与恢复路由。这样避免"点接着跑绕过授权"的坑（`RoundStatus.canResume` 包含 `seats_running`）。
- **执行**：抽成 `application/web_research.py`；结果仍按"一条结果一个 E 号"入库，`origin=web_search`，走 `render_web_results` + `WEB_BUDGET`，**不进材料池的投影**（否则会破坏编号粒度）。
- **随时研究**：闭环区"研究这个"→ 有界 research 子流程（search → fetch top N → 收为材料），复用探索生命周期但新增 `kind=web_research`，**不复用模拟调研的 prompt**。

为什么不用 `run_tool_loop` 接主链路：`tools` 与 `response_format` 互斥（`litellm.py:208-214`、`tests/harness/test_gateway_resilience.py:276-310`），一开工具就丢结构化输出；且自由工具取回的内容没有 E 号，破坏不变量。**agentic 只用于研究子流程。**

### 2.5 全局搜索：人找东西，不用 RAG

- 材料那一路从 `SqliteHybridRetriever` 换到 **`SqliteKeywordRetriever`（FTS5 only，无 embedding、无融合、无 slots）**。只改 `container.py:739-741` 一处接线。
- 材料命中新增 `material_id` / `chunk_id` 字段；行结构从"整行一个 button"改成"主按钮（跳转）+ 次按钮（**带进本轮**）"（`SearchBox.tsx:85-101`）。
- "带进本轮"→ `POST /rounds/{id}/materials`：pin + 入池 + 发 E 号，返回 `RoundView`。
  - 只允许 `STARTED / CLAIMS_READY / SEATS_RUNNING / AWAITING_ANSWERS`；`AWAITING_CONFIRM / DONE` 返回 409，文案说清"这一轮已出草案，下一轮再带"。
  - `origin=web_search` 的材料不允许走这条端点（它有自己的预算与编号粒度）；前端置灰并说明。
- **不删 `SqliteHybridRetriever`**：它是轮内池与研究的唯一检索实现，只是不再服务搜索框。

**回答"一堆检索都设计到哪去了"**：

| 组件 | 新归属 |
|---|---|
| FTS5 + jieba | 轮内检索（主）+ 搜索框关键词（唯一复用） |
| sqlite-vec + bge | 轮内检索（独占） |
| 凸组合融合 | 轮内检索（独占） |
| stage 2 收敛 | 轮内检索（独占） |
| `_MATERIAL_SLOTS` | 轮内投影（不再影响搜索框） |
| 子串兜底 | 轮内检索（独占） |
| bench / 指标 | 只服务轮内上下文与投影，不再给搜索框背书 |

## 3. 新数据流（端到端）

```
POST /rounds
  └─ SEED 检索（user_input）→ 入池 → 投影(SEED) → Analyzer
      → claims + web_queries(申请) + 席位提名
  ← 复述卡（中断 1）：改 claim / 席位 / 勾联网 / [本轮允许联网]
POST /opening
  ├─ 应用 claim_edits
  ├─ 已授权的 analyzer 联网申请 → WebResearch（事务外）→ 入池（web 段）
  └─ 投影(SEAT 首趟) → 席位轮
RunSeatRound（每趟）
  ├─ SEAT 检索（pending seats + 阻塞题 + gaps）→ 入池（trace 幂等）
  ├─ 投影(SEAT) → 所有席位共用同一份（并行只读）
  ├─ 席位并行交回 → 各自事务写 opinions
  └─ 收集 web_requests → 自动执行（已授权）或挂出提案卡
IntegrateRound
  ├─ INTEGRATE 检索（gaps + deferred + 矛盾）→ 入池（trace 幂等）
  ├─ 投影(INTEGRATE) → Integrator
  └─ 问卷（中断 2）/ 草案卡（中断 3）
POST /answers → 回到 RunSeatRound（新 SEAT trace，pass_index+1）
POST /confirm → 唯一写路径 → 版本 +1

旁路：
顶栏搜索 → 关键词检索（FTS only）→ 点击跳转 或 [带进本轮] → MANUAL 入池
闭环区 [研究这个] → WebResearch（有界）→ 入池 + 可收为材料
```

## 5. 影响面（会发生什么）

### 5.1 行为变化（需要作者知情）

1. **手勾不再无条件吃满预算**：**有可行自动候选时**每步最多 60%，自动段才有位置；无候选/不可行时手勾可满。长文场景从"自动段 0 次"变成"每步都有机会"。
2. **同一块材料可能在某步进提示词、另一步不进**：池是轮级，投影是步级。`known_eids` 仍只算本步可见，模型不会引用看不见的编号。
3. **联网不再只在开轮时发生**：席位/整合可以申请；授权后可中途追加。
4. **搜索框材料结果变弱**：只有关键词（FTS），没有语义；换来的是"带进本轮"这个真动作。
5. **多 2–3 次本地检索**（无 LLM 调用）：每轮最多 SEED + 2×SEAT + INTEGRATE = 4 次，其中新增 ≤3 次；ONNX ~20ms/块。

## 7. 量化验证（重做）

### 7.1 四层指标

| 层 | 指标 | 怎么算 | 用途 |
|---|---|---|---|
| L0 检索 | 材料/块 r@k、MRR、context precision | 冻结金标集，**生产 limit=50** | 防检索器回归 |
| **L1 上下文（核心）** | **Context Precision**（相关块/注入块）· **Context Utilization**（被引用 E/注入 E）· **预算效率**（有效字/注入字）· **充分率**（gold 块在池/投影里的题占比） | 从 `Round.materials` + `Round.retrievals` + 席位 `evidence_refs` + 草案 `refs` 直接算，**零模型调用** | 回答"检索有没有被用上" |
| L2 产出 | 草案条目**用户采纳率**（confirm 勾选）、引用支撑率（裁判）、未支撑主张率、未决减少 | 真跑 + 预注册 | 回答"有没有让产出变好" |
| L3 产品 | 到草案步数、返工次数、每采纳条目 token 成本 | 生产遥测 | 长期 |

### 7.2 分阶段

| 阶段 | 做什么 | 代价 | 判据 |
|---|---|---|---|
| Q0 | 只读脚本扫真库：注入 vs 引用（按 origin/stage） | 0 次模型 | 先拿到基线，不设阈值 |
| Q1 | 搜索框摘掉 RAG 后：关键词命中率 vs 原混合（同一批查询） | 0 次模型 | 零倒退（词面类） |
| Q2 | SEAT/INTEGRATE 两处检索的**上下文层**对照：一次性 vs 分步 | 0 次模型（用既有真轮 + 重放） | Context Utilization↑、预算效率↑、充分率↑ |
| Q3 | 答案层 A/B：一次性 vs 分步投影 | ~1,600 次调用 | 非劣（下界 ≥−5 点）+ 跨块子集优效（≥+5 点）；按文档聚类 |
| Q4 | 联网漏斗：申请→授权→执行→引用→采纳 | 按需 | 如实记，不设门槛 |

**v6 的 slots 问题**：降级为 Q2 的组件实验（池+投影后用 2/3/4 槽扫 L0/L1）。现有数据：300 宽下跨块完整率 0.20→0.60→0.73，MRR 只掉 0.007/0.003，配对零倒退——先作为投影参数，不进答案层主实验。

## 10. 风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| 投影让用户"勾的材料没全读" | 有可行自动候选时 pinned ≤60% + 材料卡显示"本步带了哪几块" | 把 `PINNED_BUDGET_SHARE` 调 1.0（自动段保底消失；不承诺逐字回退） |
| 多步检索让提示词变长 | 每步固定 4000；池不直接进提示词 | `preparer=None` 只关每步插入点；`PINNED_BUDGET_SHARE=1.0` 只关自动保底；**不承诺逐字回退** |
| 检索恢复不一致 | trace 与材料同事务；零命中也写 | 已有 trace 跳过重查 |
| 联网卡被误当"接着跑" | 非阻塞设计，不动 `waiting_on` | 前端去掉卡即可 |
| 新文件破坏目录守卫 | P0 同步 `05` 目录图 | — |
| 搜索变弱 | 关键词仍覆盖标题/章节链（FTS `index_source`） | 保留 hybrid 实例，改回一行接线 |
