## 三、B2：progress.ts 席位进度判断修复

**文件**：`frontend/src/state/progress.ts`

**现状（bug）**：
```typescript
const integrated = round.questions.length > 0 || round.draft !== null;
// ...
state: seatsDone && integrated ? "done" : openingDone ? "active" : "todo",
```

当整合出了问卷（`questions.length > 0`）但还没提交时，`integrated = true`，席位轮显示 "done"。但问卷提交后可能触发第二轮席位——席位轮其实没完成。

**改后**：
```typescript
const seatsFullyDone = seatsDone && (round.draft !== null || done);
state: seatsFullyDone ? "done" : openingDone ? "active" : "todo",
```

席位轮只有出了草案（或整轮结束）才算 done。出了问卷但没提交 = 还要跑席位 = active。

**影响范围**：仅 `progress.ts` 一个文件，一个判断式。

**测试**：`progress.test.ts` 里加一个 case：`questions.length > 0 && draft === null` → 席位轮状态为 "active"。

## 四、B3：观察去重（槽位替换视图 — 最小可用版）

### 问题

L2 观察注入给席位/整合者时，用 `repo.recent(project, limit=5)` 取最新 5 条。但如果同一个席位（如 `seat.data_scale`）在多轮里对同一主题发了多条观察，席位会看到：

```
seat.data_scale R1: "导出应在 60 秒内"
seat.data_scale R3: "导出应在 30 秒内"  ← 新决策
seat.data_scale R5: "导出应在 60 秒内"  ← 又改回来了
```

三条都注入，席位不知道该信哪个。

### 方案：按 source_ref 去重，同 source_ref 只保留最新

**核心概念**：`source_ref`（如 `seat.data_scale:O1`）是观察的"槽位身份"。同 source_ref 的多条观察 → 只保留 `created_at` 最新的一条。

**为什么用 source_ref 而不是 content hash**：
- source_ref 是结构化身份（席位 + 局部编号），不需要文本相似度
- 同一席位对同一主题的反复观察，source_ref 相同（或可通过 `related_sections + related_features` 聚类）
- 零额外依赖（不需要 embedding / tokenizer）

### 实现位置

**文件**：`backend/src/pmstudio/infrastructure/sqlite/observations_repo.py`

**现状**：
```python
def recent(self, project_id: str, limit: int = 5) -> tuple[RoundObservation, ...]:
    rows = self._connection.execute(
        "SELECT * FROM observations WHERE project_id = ? ORDER BY id DESC",
        (project_id,),
    )
    return self._rehydrate(rows[:limit])
```

**改后**：
```python
def recent(self, project_id: str, limit: int = 5) -> tuple[RoundObservation, ...]:
    rows = self._connection.execute(
        "SELECT * FROM observations WHERE project_id = ? ORDER BY id DESC",
        (project_id,),
    )
    # 同 source_ref 只保留最新（id 最大）的一条
    seen: dict[str, sqlite3.Row] = {}
    for row in rows:
        ref = row["source_ref"]
        if ref not in seen:
            seen[ref] = row
    # 按 id 倒序取前 limit 条
    deduped = sorted(seen.values(), key=lambda r: r["id"], reverse=True)[:limit]
    return self._rehydrate(deduped)
```

**影响范围**：
- `observations_repo.py`：`recent()` 方法加去重逻辑
- `tests/infrastructure/test_sqlite_observations.py`：加测试——同一 source_ref 多条观察，recent 只返回最新

**为什么不改 domain 层**：去重是存储/检索层的关注点（不同存储策略可能有不同去重方式），domain 层保持纯数据。

**不改 L1/L3/L4 的原因**：
- L1 决策：来自文档正文（已确认内容），不存在"同槽位多值"问题——决策是用户确认的，不是席位观察
- L3 灵感：每条都是独立发现，不存在"同一发现反复出现"
- L4 摘要：每轮一条，天然唯一

## 五、B4：冲突感知整合

### 现有机制（不重复造轮子）

当前矛盾管道：
1. Analyzer 检测本轮主张互斥 → `Round.contradictions`
2. 整合者提示词注入 `$contradictions`
3. 装配层盖章：证据覆盖两侧 → `kind=conflict`

### 扩展：整合者检测席位间命题级冲突

**新增**：整合者在组装提案时，对比所有席位的意见，检测**跨席位冲突**——不同席位对同一内容持不同立场。

**冲突定义**：
- 两条意见的 `about`（针对的目标）相同或高度重叠
- 一条是 `judgment`（判断），另一条也是 `judgment`
- 两条判断的方向相反（一个支持、一个反对）

**实现位置**：`backend/src/pmstudio/application/assembly.py`

**新增函数**：
```python
def seat_opinion_conflicts(reviews: tuple[SeatReview, ...]) -> tuple[SeatConflict, ...]:
    """检测席位间的命题级冲突。
    
    冲突定义：两个席位对同一 about 持相反 judgment。
    返回：冲突对列表（含双方依据）。
    """
```

**新增数据类**（`domain/round/` 下或 `assembly.py` 内）：
```python
@dataclass(frozen=True, slots=True)
class SeatConflict:
    about: str                          # 冲突针对的目标
    opinion_a: OpinionView              # 席位 A 的意见
    seat_a: str                         # 席位 A 的 id
    opinion_b: OpinionView              # 席位 B 的意见
    seat_b: str                         # 席位 B 的 id
```

**整合者输出扩展**：
- `IntegrationPacket` 增加可选字段 `seat_conflicts: list[SeatConflict] = []`
- 整合者提示词增加一段："如果检测到席位间冲突，在 seat_conflicts 里列出"
- 或者：**不修改 IntegrationPacket**，而是在 `assembly.py` 的 `assemble()` 里做机械检测（和 `contradiction_pairs` 同理）

**推荐方案：机械检测（不依赖模型自觉）**

和现有 `contradiction_pairs` + `_covers_a_contradiction` 同模式：
1. `assembly.py` 里新增 `seat_conflict_pairs(reviews)` → 纯函数，对比所有 opinion 的 `about` + `claim` 方向
2. 检测到冲突 → 在整合者提示词里注入 `$seat_conflicts` 槽位（和 `$contradictions` 并列）
3. 整合者看到冲突 → 出一道 `kind=conflict` 的题让用户裁决

**前端可见性**：
- 草案卡片上标记"此处 N 个席位有分歧"
- 点击展开冲突详情（哪两个席位、各自依据）

### 冲突检测算法（最小可用版）

```python
def seat_conflict_pairs(reviews: tuple[SeatReview, ...]) -> tuple[SeatConflict, ...]:
    """机械检测：同 about + 相反 judgment 方向。
    
    简化判断：两条 opinion 的 about 相同（字符串匹配），
    且 claim 文本包含相反的关键词（"应/必须/需要" vs "不应/不能/不应"）。
    这是一个保守检测——宁可漏报不可误报。
    """
    conflicts = []
    judgments = [
        (review.seat_id, opinion)
        for review in reviews
        for opinion in review.opinions
        if opinion.form == OpinionForm.JUDGMENT
    ]
    for i, (seat_a, op_a) in enumerate(judgments):
        for seat_b, op_b in judgments[i+1:]:
            if seat_a == seat_b:
                continue
            if op_a.about == op_b.about and _claims_contradict(op_a.claim, op_b.claim):
                conflicts.append(SeatConflict(
                    about=op_a.about,
                    opinion_a=op_a,
                    seat_a=seat_a,
                    opinion_b=op_b,
                    seat_b=seat_b,
                ))
    return tuple(conflicts)

def _claims_contradict(claim_a: str, claim_b: str) -> bool:
    """极简矛盾判断：一条含肯定词，一条含否定词。"""
    positive = ("应", "必须", "需要", "要", "可以", "支持")
    negative = ("不应", "不能", "不要", "不可", "反对", "禁止")
    a_pos = any(w in claim_a for w in positive)
    a_neg = any(w in claim_a for w in negative)
    b_pos = any(w in claim_b for w in positive)
    b_neg = any(w in claim_b for w in negative)
    return (a_pos and b_neg) or (a_neg and b_pos)
```

**为什么用极简关键词匹配**：
- 这是机械检测（和 `contradiction_pairs` 同模式），不依赖模型
- 保守策略：漏报比误报好（误报会让用户看到假冲突）
- 未来可以升级为 LLM 判断，但 v1 用规则足够

## 十、不做的

| 不做 | 原因 |
|------|------|
| L1 决策去重 | 决策来自文档正文（用户确认），不存在"同槽位多值" |
| L3 灵感去重 | 每条灵感都是独立发现 |
| L4 摘要去重 | 每轮一条，天然唯一 |
| 材料选块按比例分配 | 当前 FCFS 够用，改比例分配需要更多设计 |
| MEMORY_LINE_LIMIT 改 token 预算 | 需要 tokenizer 接入，是大工程 |
| 席位间自由对话 | 锚定效应 + 成本不可控 |
| 冲突检测用 LLM | 机械规则足够，LLM 判断增加成本和不确定性 |
