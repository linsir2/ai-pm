## 2. 口径（每条：建议 + 备选 + 为什么）

1. **检查要"看得见真数据"**：用**真跑库的副本**起后端（L3 那个项目有 3 轮 / 4 版 / 3 份材料 /
   8 棵功能树），而不是空库。空库只能看空态，看不出"数据对不对"。
   备选：现造数据（要跑真模型，慢且贵）。**副本永远不写原库**（用 `cp`，记下来源）。
2. **每屏问同样 6 个问题**（这样"看过"才可比较）：① 数据是不是来自真后端（有没有空态误报） ·
   ② 有没有溢出/裁切/竖排/重叠 · ③ 空态/错误态/加载态说的是不是人话 · ④ 交互元素是不是原生
   `button`/`input` 且**有可访问名** · ⑤ 键盘可达（Tab 顺序 + focus 可见） · ⑥ 中文排版
   （行高 / 标点 / 数字等宽）。
3. **截图只做"同机前后对照"**，不做跨机器基线：字体与 DPR 会变。固定 `deviceScaleFactor=1`、
   固定 `window-size`，并在报告里记 **Chrome 版本号**。
4. **发现即记录，记录即处置**：报告里每条发现三选一——`已修（附提交）` / `明确不修（附理由）` /
   `另立一批（附触发条件）`。**不许出现"看过了、没事"这种没有截图的结论**。
5. **失败态文案走纯函数**（`failureLine(round)`），组件只负责画——这样"从哪继续"这句话能被单测钉住，
   而不是靠肉眼。
6. **顶栏修法**：≤1240 收次要项（推送状态缩成圆点 + `title`、暗色缩成图标、"已经复述完你的话"
   收进复述卡），≤980 保证**不换行不溢出**（必要时允许横向滚动容器）。备选：把中断点整体提到 1180——
   治标，且 1100 这一档本来就该能用。
