## 1. 结论先行

1. **"必填"这个词在本项目里有三份说法**（`产品设计说明书` §2.6 / `schema.required` /
   `context.FIELD_PRESSING`），互相不一致——**这是本条的本质**，不是"再补一句提示词"。
2. 真跑数据坐实了机制：**代码标了 `required` 的 6 个字段 90–100% 有内容；
   没标的 4 个字段 10–53%；`priority` 是 0/30**。模型唯一的"该写什么"信号就是字段表那一行。
3. **但"再派活"不是免费的**：三个容器（主张 20 / 提案 60 / 问卷 5）在现配置下**都已打满**——
   问卷几乎每批 5/5、轮内队列还积压 0–20 条。所以本批的口径是**分流**：
   **能推导的走"该写"、只有用户能定的走"该问但不出题"、其余留 warn**，一次只动一个字段。
4. 顺带收一条**判据措辞与实现不一致**（`01` §4 第 6 章"有功能却没有任何 steps" vs
   `readiness._kind_presence` 只看 s6 自己）——**不改代码行为**（实现更贴 P36 拍板的口径 A），
   改措辞 + 加护栏用例。

## 2. 现有设计 vs 现在实现

### 2.1 字段的"水位"三处不一致

| 说法 | 在哪 | 内容 | 谁在消费 |
|---|---|---|---|
| 设计说明书 §2.6 | `.codex/docs/过程记录/产品设计说明书.md` | 名称/一句话/优先级/目标/角色/**用户故事**/主流程/异常/输入输出/验收 = **必填**（依赖"无则写无"） | 只被人引用（P36/P37/P38 都引过） |
| 代码真相源 | `domain/authoring/schema.py::FEATURE_FIELDS` | `required=True` 只有 **6 个**：name / one_liner / goal / audience / exceptions / acceptance | `readiness._feature_gaps`（→ blocker）；`/schema`；前端只读 title |
| 提示词压力 | `application/context.py::FIELD_PRESSING` | 只有 `main_flow` 一句 | `FEATURE_FIELDS_TEXT`（两个智能体共用） |

§2.6 的"必填"是**内容标准**；`required` 是**交付门槛**（缺一条 = 一条阻塞）。
P37 拍板"不升必填"是对的（升上去 P30 的 0 阻塞车道立刻破），但它**只解决了不升**，
没解决"那这些字段该由谁说、说到什么程度、看不见怎么办"——这才是本批要补的。

### 2.3 三个容器的水位（决定"能不能再塞"）

| 容器 | 上限 | 实测 | 结论 |
|---|---|---|---|
| `claims` | 20（`schemas.py:91`） | 34 轮里多条 = 20 | **打满**：让分析者多切主张会挤掉别的判断 |
| `proposals` | 60（`schemas.py:228`） | P37：中位 31 / p90 65 / 最大 90，**17% 超限** | 有中位余量，**p90 悬** |
| 问卷 | 每批 5 题 / 每轮 2 批 | **几乎每批 5/5**；轮内队列剩 0–20 条 | **全满**：新题只能挤掉现有的或落 s11 |

**这条数据推翻了一个直觉方案**："让 `priority` 出题问用户" —— 名额已经 100% 占满，
新题要么挤掉队列里积压的 10–20 条（那些才是只有用户能答的缺口），要么直接进 s11 变未决。
**所以 `priority` 本批不出题。**

### 2.4 `01` §4 第 6 章的措辞与实现不一致

| | 内容 |

## 3. 决定

| 项 | 决定 |
|---|---|
| 真相源 | **以 `schema.FEATURE_FIELDS` 为准**；`产品设计说明书` §2.6 标注为**历史草案**（不构成现行判据） |
| 三档 | `required`（就绪度 blocker，现有 6 个）· **`expected`（该写/该问，warn + 提示词压力，新增）** · 其余（不表态） |
| `priority` | **不出题、不硬编**：用户明确说了才写（P0/P1/P2）；没说就留空，靠 warn 让用户看见 |
| `user_story` | **走"该写"**（能从 goal/audience 推导，属 `derived`）；本批只上这一个字段 |
| `io` / `dependencies` | **下一批**（一次只动一个变量，才有归因） |
| 就绪度 | 新增一条 **warn**（`feature_field_expected`），**不升 blocker**，按 (s5, code) 折叠成一条 |
| `/schema` · API · 前端 | **一个字不动**（`expected` 是提示词口径，不进结构投影） |

## 4. 数据流与架构图

```
用户原话
  │
  ▼
[Analyzer] ── 字段表（含新增的 expected 那两行）+ 归位表
  │            · 有依据的功能内容 → claim{target:{s5, feat, field}}
  │            · 优先级：用户说了才落；没说**不落**
  ▼  claims（上限 20，本批不新增主张类型）
Round.write_scope（功能字段放宽到功能级）
  ▼
[Integrator] ── FEATURE_FIELDS_TEXT（同一份字段表）+ LIMITS_TEXT
  │            · 缺 user_story 的功能 → 补一条（derived，带 refs）
  │            · 缺 priority → **不出题**（问卷名额满）
  ▼  questionnaire（≤5/批） │ draft（≤60）
草案卡 ──确认──▶ 文档
  ▼
[ReadinessChecker] ── 新增 warn：feature_field_expected（不挡交付）
  ├→ 提示词（render_readiness，三个智能体都看到 → 下一轮补）
  ├→ 界面就绪度抽屉（用户看得见）
  └→ 导出（附录 C 未完成项）
```

分层不变（`05-DDD架构.md`）：改动落在 `domain`（字段规格 + 判据）、`application`（提示词渲染）、
`infrastructure`（提示词文本）三层，**依赖方向不变**（domain 仍不 import 任何外部包）。

## 6. 真跑验证与阈值

三条线：**L2 两轮**（4 功能 / 8 功能各一）· **L5 两轮**（1→3 功能）· **整轮 eval 10 条**。

| 指标 | 阈值 |
|---|---|
| `user_story` 覆盖率 | 20% → **≥ 60%** |
| 提案溢出率（>60 条） | 17% → **≤ 25%**（超了就回退本批，先扩容再派活） |
| 问卷题目数 / 挤掉的题 | **不变**（本批不出 priority 题；5/批仍满也正常） |
| 阻塞数 | **不回退**（0 阻塞的车道仍 0） |
| eval | **10/10 不回退** |
| `priority` | 只在用户明确说了的轮次里出现；**默认值一次都不许写** |

## 7. 成功之后是什么样

- **就绪度抽屉**多一行（提示，不阻塞）：
  `s5 功能字段还有该写的没写：order-export：用户故事；login-wechat：用户故事`
- **提示词**里三个智能体都看得到这一行 → 下一轮整合者优先补它（有依据），没依据就出题。
- **导出第 5 章**每个功能多一行：`- **用户故事**：作为〈运营专员〉，我想要〈按时间筛选导出〉，以便〈每天下班前拿到对账表〉〔E3 E9〕`
- **优先级**：只有用户说过才出现（`- **优先级**：P0`）；没说就仍缺，但清单里列着——
  **系统不替他拍板，也不假装他是 P1**。
- **不挡交付**：`ready = blockers == 0` 的判定一个字没变。
