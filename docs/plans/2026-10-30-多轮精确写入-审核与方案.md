## 1. 用户已拍板

- 条目级前置条件：文档别处改变，不应一律让整张草案过期。
- 每条 Proposal 记录实际生成输入的版本号，复用不可变 Version.snapshot，不复制旧正文落库。
- AI 草案遇到已占用单值字段的 add，按唯一现有条目精确转 replace；领域 ADD/upsert 契约保留。
- accepted 是选择集合，执行顺序恢复为草案顺序；多个 replace 的已有顺序语义保留。
- 按当前值比较：同 ID/归属/text/refs/结构完全恢复基线时允许，不增加历史代次计数器。
- 无基线旧草案保留读取，写入需通过现有 dig 重生成；不猜生成版本、不补成当前版本。
- TRACE_MODEL 保持默认关闭，修正“零记录=零调用”的文案。
- 历史重复保留 v3 新要求，经真实模型草案确认清理。
- 用户要求重新审视可省略写入控制字段：不得让解析器替模型决定动作。

### 网络交叉核验

- RFC 6902 §3/4.3/4.6/5：顺序操作、replace 目标必须存在、test 旧值、原子失败。借契约思想，不替换现有 WriteInstruction 或引入 JSON Patch 库。
- RFC 9110 §13.1.1：If-Match 防 lost update；必须在动作前检查。我们的自有确认端点使用现有 409 体系，不冒称实现 HTTP If-Match。
- PostgreSQL 18 §13.2.1/13.3.2：READ COMMITTED 的无条件 UPDATE 不会重新计算 Python 候选；FOR UPDATE 应覆盖读改写短事务。
- OpenAI Structured Outputs：required 键与 nullable 值是两件事；schema adherence 仍可能有语义错误。
- Anthropic Building effective agents 附录 2：改接口参数和边界，让错误更难表达；不要以增加代理替代明确契约。

## 3. 新契约：各层只负责自己的判据

### 3.1 模型声明动作，系统盖地址与基线

保留一个 ProposalDraft 类型，不改通用归一化引擎为多分支 union。
当前 normalize.py 对多模型 union 不递归归一/摘占位符，贸然换 union 会弄丢已有容错。

- `op` 必填、无默认值；缺键/null/非法枚举都进入已有报文重装出口。
- `entry_id` 键必填且可为 null：add 明确给 null；replace/remove 给非空现有 ID。
- add 给旧 entry_id、replace/remove 给 null 均拒绝；不猜动作、不靠正文找目标。
- target/text/evidence_refs 仍必填；remove 可明确给 text=""，正文由真实删除对象补齐。
- 空 body target 不默认归到功能章；TargetDraft 对章节槽/功能字段的说明与 target_of 实际能力对齐。
- origin_type/kind/rationale 的现有可选语义保留：来源按账本校验，字段 kind 按 FieldSpec/模板派生。
- 结构字段缺失与“给了但指错地址”分开：前者重装，后者沿用丢一条+留痕。
- `base_version_no` 不由模型填写；生产生成入口根据实际读取的 Document.current_version 盖章。

### 3.2 规范化覆盖三条生产路径

`normalize_proposal(proposal, document)` 是创建时的纯函数，不在投影或确认时调用。

1. 已占用单值功能字段恰好一条：add→replace，保持 proposal_id/text/refs/origin，只改 op/entry_id。
2. 空单值字段仍 add；多值、章节槽、偏好、普通正文仍 append。
3. 单值字段若已有多条，不能任取第一条，报告结构冲突。
4. replace/remove 必须唯一定位 entry，模型 target 必须与真实归属一致；不一致留痕拒收。
5. remove.text 一律为其基线的真实旧正文；删除理由仍放 rationale。
6. 新提案盖实际基线；已盖章的模型提案进入最终合流时保留原基线，不能按新文档重新盖章。
7. 模型生成、机械主张/答案/未决清理、模拟评测都经过该路口。旧卡读取不经过它。
8. E 括号清洗后再比较实际待写文本，堵“原始文本不同、清洗后一样”的重复洞。
9. 既有多行 overlap 仍只作标注；机械落地的整文本精确重复也需可见且默认不勾，不能吞输入。

### 3.3 条目级前置条件

每条 Proposal 加 `base_version_no: int | None`；旧载荷缺键为 None，只读兼容。
WriteInstruction 同步透传版号。不可变版本已有 text/refs/块结构，直接复用。

| 操作 | 对锁定后的当前文档检查什么 |
|---|---|
| replace/remove | 基线 ID 唯一存在；当前仍是同 Entry；text 与 refs 相等；真实 owning block、祖先归属、field/kind、D5 标记相同 |
| 多值 add | 真实承载块及祖先身份/结构未变，新 entry_id 不存在；不比较同字段其他 Entry 的 text/refs |
| 空单值 add | 上述结构检查＋仍为空；同一批选择两个同空单值字段 add 拒绝，任一单选可执行 |
| 缺失目标的 add | 比较逻辑去处及已存在祖先；目标从缺失变成存在、或父块换了，需要重新整合 |
| 偏好 | 同一套 Entry 比较，区域必须是 preference；它没有 D5 块标记 |

- 无关字段变化允许；同字段另一个 Entry 的普通 replace 也不自动挡住 append。
- 不宣称语义上任意自动合并：同块手改受 D5 影响，结构创建/删除可能需要重生成。
- 按用户拍板的当前值口径，完全恢复基线可通过；不检查历史存活代次、不用墓碑冒充历史值。
- 不重建旧墓碑，不把随机新块编号的分配差异视为正文冲突。
- 模型调用期间发生变化不改提案基线；冲突项可见，未选冲突项不挡其他选择。
- 所有 selected 先对同一份批次起始状态核验，再执行；第二个 replace 不拿第一个修改后的值对旧基线比较。
- allow_manual_override 只豁免 D5 的显式保护，不豁免陈旧前置条件。
- 结果态检查 selected add 是否造成同去处的精确重复；能明确执行的 remove/replace→add 顺序按最终候选结果判断，不静默跳过、不自动合并 refs。
- 只检查所选新增造成的重复，不因此自动清理旧重复数据。

### 3.4 用户确认的是那张卡

- ConfirmRequest 增加必填 draft_id，沿现有路由/命令/node/use_case/committer 传递。
- p01 等 ID 只在草案内唯一，不能单独证明用户看见的是哪张卡。
- accepted 先查 ID，再 set 化，按 draft.proposals 顺序恢复；重复请求 ID 不执行两遍。
- 重复 remove 的旧合并规则保留；先检查每个所选原提案基线，再合并，不能吃掉不同基线。
- 创建草案时只合并同 entry_id、同基线的 remove，不同基线保留供用户选择。给现有
  merge_duplicate_removes 增加创建时的“仅同基线”条件；确认逐条核验后仍按旧规则合并。
- 同条多个 replace 保留顺序，卡上显示后者覆盖前者；危险组合不假装每个候选都独立。
- 建议竞争组默认不勾，只是要求主动过目；用户显式同选多个 replace 仍按既有顺序执行。
- 建议 DTO 的 requires_review 只表示机械过目需求，不改 origin_type；前端在原有
  origin_type 非 proposed、无 simulation_based、无 overlap 的判据上叠加 !requires_review。
- before 来自历史版，永远不取当前新文冒充旧文。当前陈旧警告只对待确认草案计算，不能把
  已确认后的正文变化反过来标成历史卡片的写入冲突。

### 3.5 短事务与存储一致性

- 增加 DocumentReader.get_for_update 和 EvidenceReader.get_for_update，复用 RoundReader 的显式锁读先例。
- confirm/manual/rollback 的文档读改写共用文档行锁；EditEntry 在读取旧 refs 和账本之前先锁文档。
- 所有发 E 的写事务首次读账本就锁，不能只在 save 时锁。项目创建的新账本仍在创建事务中初始化。
- 锁顺序：需要 Round 的路径先锁 Round，再 Document，再 Ledger；不涉及的锁跳过。研究/取料等只锁自己的控制行和 Ledger，不反向锁 Document。
- 必须覆盖隐式写锁：所有“发 E 后保存 Round”的事务都先 Round.get_for_update，再读 Ledger。
  具体包括 StartRound.analyze、SubmitOpening、Decide/RecoverWebRequest、RunSeatRound 的编号汇合、
  IntegrateRound、SubmitAnswers、RoundContextPreparer、模拟材料/模拟评测落库；不能保留先锁 Ledger
  再等待 Round.save 的反序。建新 Round 的 INSERT 是首次控制行建立，不伪造对不存在行的锁读。
- 模型、联网、向量检索都不包在这些锁事务里；不能把 shared PgConnection 扔进 to_thread。
- 普通 Document.get 用一条 SQL 同时取 document 与按版本排序的版本行，保证同一语句快照。
- 新版本与内容一起提交。历史版本重放可幂等；版本碰撞若已有内容与待存版本不一致必须失败，不吞成成功。
- 确认在局部浅拷贝候选上执行一次 Document.apply，再验新增重复，通过才 save；Document 成员为 frozen/tuple、apply 只换属性，原读聚合不被候选失败改动。
- 文档/版本/记忆/Round 任一步失败都回滚，无成功事件、无成功摘要。

### 3.6 替换对上下文与证据的影响

- replace 只换一个 Entry 的全部 text/refs，保留 ID、顺序和 owning block；不会自动搬字段。
- 未改的句子/步骤必须出现在完整新 text 内；不会自动逐行合并。prompt 加完整 old→new 示例。
- 保留旧句子的提案需引用支持这些旧句子的 E；不自动把所有旧 refs 并进去，避免已推翻的旧结论成为当前依据。
- 当前正文是结果，不是新证据；旧 refs 与旧正文仍留在不可变历史版本。
- 当前文档优先于历史摘要/记忆；用户明确“把旧规则改成 X”不应自动被当成尚未拍板的两侧矛盾。只对真实未决冲突出题。
- document_state 保留完整正文/层级/ID/refs；entry_ids 改成精简的“ID→真实target”索引，不再重复旧正文。
- prompt 修订原有规矩，不能保留一条“只提全新内容”再叠一条相反的 replace 规则。
- 静态前缀会一次性重暖；不增加额外编辑代理，不改模型预算或自动扩大上下文。

### 方法与复用清单

- 创建规范化函数：只有创建时使用，消费者为模型装配、机械合流、模拟评测；不是确认时自动改动作。
- Document 历史 Entry 定位：消费者为装配真实地址、确认旧值、DTO before、精简地址索引。拒绝多命中，不取第一条。
- 前置条件核验：确认/模拟落库/当前卡片警告共用一处规则；不会重算 overlap 的历史快照。
- 继续复用 Document.apply、to_write_instruction、FieldSpec/TemplateAdapter、merge_duplicate_removes、现有 UoW、版本快照与精确定位函数。
- 不增加语义相似度硬裁决、第二份文档存储、自动改文档工具或通用 patch 框架。

### dry_run 与选择门禁的分工（独立评审修正）

- 当前 dry_run 把全部候选一起 apply，组合失败会进入整包重装；这会吞掉“单选任一条可用”的卡片。
- 新口径：dry_run 仍是纯内存预览、不写文档。先保留全体原候选；若全选的前置条件/组合/结果
  判重过不了，返回“全部候选不能同时写入，未生成全选结果预览”，随后仅报告当前已确认正文的缺口。
  不宣称一个不存在的写后结果，不丢候选，不因此重装整包。
- 真正的拒绝只在确认端对 selected 生效；schema 缺控制字段、未知出处等原有报文修复仍生效。
- dry_run 与确认复用同一个 Document.apply 和结果检查。预览中合并 remove 只改变瞬时计算，
  草案构造仍保留不同基线的 remove。
- 最终机械合流后重新做完整候选预览，不能沿用仅模型那批的缺口数冒充最终草案的结果。

## 5. 数据流与架构图

```text
实际 Document@vN ──完整正文/ID/refs──> Integrator
        │                              │ 显式 op/entry_id/target/text/refs
        │                              v
        └────> 创建规范化 ──────────> Proposal(base_version_no=N)
                ↑                      │
     机械落地@vM / 模拟评测@vK          ├─ JSONB，只有版号新增
                                       └─ DTO 从对应 Version.snapshot 取 before
                                                   │
                                     草案 old→new / 过目提示
                                                   │
                                用户选择 {draft_id, accepted IDs}
                                                   v
                              短事务：Round → Document 锁
                                      逐条旧状态前置条件
                                      固定草案顺序 / 合并 remove
                                      候选 Document.apply
                                      新增结果精确重复检查
                                                   │
                         document + version + memory + round 原子提交
                                                   v
                             doc.changed → 重读 → 下一轮当前文档

所有发 E 的写路径：控制行 → Ledger 锁 → 发号/保存 → 提交
```

成功形态：修改一个四步流程时原 Entry ID 保持，只换第一步，其余三步仍在；新独立规则新增一条。
别处修改不抹掉；相关旧值变了返回明确冲突，不偷偷改新内容。历史版本与当前头始终相等。

## 6. TDD / RIPR 具体用例

RIPR 是 Reachability / Infection / Propagation / Reveal，不是把四个 R 写成“回归”。
每一行都要先在旧实现下看到预期失败；pytest 与 jsdom 不能代替真 PG/真模型/真机。

| 用例与层 | R：走到哪里 | I：注入/触发差异 | P：传播到哪里 | Reveal：精确 oracle |
|---|---|---|---|---|
| schema 写控制字段 | 真实 parse_lenient | 缺 op、缺 entry_id、null op、add 指旧 ID、replace 空 ID | 正常报文修复通道 | 不生成默认 add；明确 field/path 错误；合法 add(null ID)/replace/remove 正例通过 |
| target/id 对账 | assemble | entry 在 s1，target 写 s2 | 卡片与 to_write_instruction | 错条留痕，不写 s1；正确条照收；章节槽~2 与 preference 也核对 |
| 删除展示 | assemble→DTO | remove 文本写另一句话或留空 | 删除卡 | 都显示真实基线正文，entry_id/refs 不被展示文案改掉 |
| 单值转换 | 模型和机械两入口 | occupied one_liner/add | Proposal→确认 | op=replace、旧 ID 保持；text/refs/origin 不变；空字段/add、多值/add 正例 |
| 机械 bypass | 真 IntegrateRound 合流 | 未被模型引的主张/答案落在 occupied single 或重复多行 | 持久化草案/默认勾选 | 输入不被丢；single 规范化；多行 overlap 可见、默认不勾；提案基线是真实生成输入 |
| selected 集合 | committer | 相同集合但逆序/重复 IDs | 最终正文 | 固定草案顺序；最后 replace 一致；一个 ID 不写两遍；remove→replace 不可执行时全回滚 |
| 跨基线 remove | 创建合流→确认 | 同 entry 的 remove@N/remove@M，N已陈旧 | 草案选择/确认 | 两条都留；只选M可过，只选N冲突；同基线仍合并；确认核验后可合并有效同目标删除 |
| 全候选预览 | assemble→dry_run→草案 | remove与replace分别可用、全选不可用 | 草案而非重装循环 | 卡片保留两候选＋组合告警；不报虚假的写后补齐度；任一合法单选仍能确认 |
| 空单值多 add | commit | 两候选同空字段，单选/双选 | Document/Version | 各自单选都可写；双选明确冲突，不能只剩后一条 |
| 相关陈旧 | 原卡等待/模型 gate | 同 ID text 或仅 refs 改变 | ConfirmDraft | 409，正确 proposal/base/current，文档/版本/Round/memory 不半写 |
| 无关修改可合并 | 相同基线两份草案 | 另一字段或同字段另一 Entry 普通 replace | 两次确认 | 两笔内容都在，版本连续；append 不因无关 entry 文本变化拒绝 |
| 结构/回退/D5 | 前置条件 | 目标删/换 ID/改 parent、D5 变、值完全恢复 | 确认与模拟 | 换身份/旧值冲突；完全恢复基线可过；override 不豁免陈旧；未选坏项不挡好项 |
| duplicate 三种来源 | selected 候选 apply | 基线后新重复、同批两 add、replace 产同文＋add | 保存前校验 | 原子冲突，无静默跳过；remove 旧同文后 add 若结果唯一则按明确顺序通过；近义改写不机械硬丢 |
| 草案身份/老卡 | HTTP→runner | dig 后新 p01，提交旧 draft_id；旧 Proposal 缺基线 | 确认端 | 409，不写新 p01；旧卡可读、写要求重生成；不猜版号 |
| sim 独立基线 | 真 RunSimReview | 原卡@N，评测输入@K，调用中目标又变 | 发 E/augment 前 | 新提案基线=K，旧提案仍=N；相关变更失败无新 E/无 runs 增量；无关变更不全卡拒绝 |
| 新字段序列化/投影 | 真 repository 往返 | 新 base/旧缺键、历史正文后来变化 | DTO before | 新版号守恒，旧 None；before 来自历史版不漂；复用 EntrySnapshotView |
| PG 丢更新/混合读 | 两真实连接/SQL门控 | 两读旧版本，A提交插在B读/写中间 | current/history | 持锁后读新状态；head=last snapshot；版本连续唯一；普通 get 只有完整旧或完整新 |
| PG 账本 | 两真实连接、两写 UoW | 都要发下一个 E | 两轮 refs/账本 | 不同 E、两条事实均在；失败全回滚；真实 lock wait 证据，不用 gather 同步函数假并发 |
| frontend | 真实 payload/hook/component | old→new、冲突/竞争、切换草案重用 p01 | 选择与 HTTP body | 默认规则可验；body 对应所见 draft；旧值/refs可见；跳到精确 Entry |
| 真模型多轮 | 独立真实项目/API+浏览器 | R1建流程；R2只改一步；R3新增独立规则；R4改回一项 | 完整确认后文档 | 原ID/完整流程/新增数/refs/版本与预期一致，无拼接；非目标条目逐字保持；截图核验 |

并发测试必须两条 PG 连接/不同 backend PID；使用 Event 门控和 pg_blocking_pids 确认真等待。
修好行锁后，不能继续用“两边锁后读完再 Barrier”的旧复现调度，否则测试会人为死锁。

既有测试迁移必须逐项列明：省略控制字段 fixture 补显式合法值；append 用例从单值 one_liner 改到
多值 main_flow，原 3/4 判据保留；remove 任意文案保留的旧 oracle 与真实删除对象展示冲突，单独说明。
不得放宽断言、删负例、用 fake 自动盖基线，或把全绿当模型行为已可靠。

## 7. 评审与交付顺序

1. 审核本文，先解决控制字段/默认过目策略的最终拍板，主链不先写实现。
2. 存储切片：一致读、Document/Ledger 锁，红→绿→独立审查。
3. 提案契约切片：控制字段、系统基线、三入口规范化，红→绿→审查。
4. 确认切片：draft 身份、条目比较、顺序/候选结果守卫，红→绿→审查。
5. 卡片/上下文切片：before、精确跳转、默认过目、去掉重复正文，红→绿→审查。
6. pytest/ruff、架构契约守卫、Vitest/tsc、API parity；数字按实际执行结果，不引用旧 session 数字。
7. 独立测试项目真模型四轮＋localhost:8080 浏览器截图，核验真实文档与版本而非测试 fixture。
8. 经用户批准的清理提案落旧项目，再只读比较三个字段与版本 diff。
