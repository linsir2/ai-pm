## 0. 这一族的两条与共同根

| | 现状 | 症状 |
|---|---|---|
| **M5** 输出侧阀门 | 60 条 = **schema 硬上限**（`application/agents/schemas.py:491` `max_length=60`）；提示词已告知（`integrator.py:91-93`）；**但 `max_tokens` 代码里根本没设** → 撞的是**供应商默认**输出上限 | §11.0.42：**17% 的整合调用写了 >60 条** → 重装一次修好 59%，其余**真截断** → **最多一次丢 16 条提案，用户拿不到**（只在留痕里） |
| **M6** 总量闸门 | **22 个上限散在 6 个模块**（只做了契约化 `tests/contracts/test_limits.py`） | 没人能回答"这一轮最多吐多少、为什么是这个数、谁跟谁对过账" |

**共同根**：上限之间**没有互相校对**，每一处各自拍 → 咬人的地方永远是**事后**。

## 1. 实测（`scripts/measure_integration_output.py`，应用自己的库 27 次真实整合调用）

```
回包 token（供应商报的实际值）：P50 4168 · P95 6589 · P99 7048 · max 7146
单条提案字符：P50 276 · P95 418 · P99 536 · max 1275      换算 0.936 token/字
→ 单条提案 P95 ≈ 391 token
→ max_tokens = P99 × 1.2 = 8457
→ 条数上限 N = min(60, 8457 ÷ 391) = 21     （实测条数中位 13、最大 29）
```

**自洽性**：N=21 时最坏 21 × 391 = 8,211 ≤ 8,457 ✓（就算每条都按 P95 算也装得下 ✓）；
N=21 高于实测中位 13 ✓（多数调用不受影响）；N ≤ 60 ✓（schema 硬上限不被突破 ✓）。
