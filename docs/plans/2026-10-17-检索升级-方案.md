> 状态：**实现推迟**（2026-10-17 拍板）。本文件是"等有语料/真查询再建"时的最终方案。

## 1. 库选型（调研结论，全部带出处）

### 1.1 中文分词：**jieba**（唯一零摩擦选项）

| 项 | 事实 |
|---|---|
| 版本/许可 | `jieba==0.42.1`（2020-01-20），**MIT** |
| 依赖 | **纯 Python，无第三方依赖、无 C 扩展、词典随包**（无需联网下载） |
| 用法 | `cut_for_search` 官方定位"适合构建倒排索引"（精确 + 长词再切，召回更高） |
| 维护 | 2020 后冻结；纯算法、无依赖，冻结风险低 |
| 出处 | https://pypi.org/project/jieba/ · https://github.com/fxsjy/jieba |

**淘汰的竞品**（都因硬约束）：
- 需编译/框架：`pkuseg`（C 扩展）、`LAC`（paddle）、`HanLP`（torch/TF）、`spaCy zh`（Cython+模型）、`jieba_fast`（C+Swig）。
- 许可摩擦：`thulac`（商用需单独许可）、`HanLP` 模型 CC BY-NC-SA（禁商用）。
- 停更且质量弱：`SnowNLP`（2015 停）。
- 外部服务：`boson-nlp`。

### 1.2 检索引擎：**SQLite FTS5**（内置，不引新引擎）

- FTS5 自 SQLite 3.9.0 起内置；CPython 的 Windows/macOS 官方安装包**已编译进 FTS5**，Linux 用系统 libsqlite3（Debian/Ubuntu 默认开）。本机实测 3.51.0 **可用**（已验：建表/MATCH/bm25/增删改全过）。
- **内置 tokenizer 都不切中文**：`unicode61` 把连续 CJK 当**一个 token**（实测 `MATCH '权限'` 匹配不到 "权限模型"）；`trigram` 只做 ≥3 字子串；`porter` 对中文无意义。→ **必须应用层预分词**（jieba）。
- 出处：https://sqlite.org/fts5.html

**淘汰的引擎**：
- 外部服务（直接排除）：Meilisearch、Typesense、Quickwit、Sonic、Zoekt。
- `tantivy-py`（嵌入式 Rust，有 wheel）：**无内置中文分词**（只有 ngram），且要维护 **SQLite 之外第二个索引目录**（两处同步、无事务一致）。
- `Whoosh`（原版 2016 停；whoosh3 单人复兴）；`python-xapian`（GPL + 系统装库）。
- SQLite 的 `simple` 扩展（wangfenjin，C++，带 jieba/拼音）：**功能最好但无 pip wheel、要手动分平台 `.so`、macOS arm64 官方包缺**、依赖 `load_extension`。→ **不用**（除非将来明确要拼音）。
- 出处：https://github.com/wangfenjin/simple · https://github.com/quickwit-oss/tantivy-py

### 1.3 停用词：**不处理**（实验定案，见 §5）

索引侧与查询侧都**不删**——查询用 OR，天然容忍多余/缺失 token（实测"插停用词"类查询
OR 15/15 全中）。曾考虑的 `stopwordsiso`（MIT）**砍掉**：收益被实测否掉，少一个依赖。
出处（原候选）：https://github.com/stopwords-iso/stopwords-iso

### 1.4 阶段 2（语义，可选，等关键词证明不够再上）

- 向量：**`sqlite-vec`**（**同库同文件**，MIT/Apache-2.0，0.1.9；pre-v1，注意 breaking；需 `enable_load_extension`）。
- embedding：**`fastembed` + `BAAI/bge-small-zh-v1.5`**（ONNX **无需 torch**，512 维 ~90MB，MIT）。
- 融合：**手写 RRF**（`score = Σ 1/(60+rank)`，约 10 行）——没有值得引的 RRF 库，而 FTS5 已给 BM25。
- **淘汰**：`chromadb`/`lancedb`/`faiss`/`qdrant-local`（都引入**第二套存储**，等于第二真相源）；
  "整锅端"的 `haiku.rag`（MIT，活跃）虽已打包 sqlite-vec+FTS+RRF，但它要**自己拥有语料/存储**，与本仓材料表 + `MaterialRetriever` 协议冲突。
- 出处：https://pypi.org/project/sqlite-vec/ · https://qdrant.github.io/fastembed/examples/Supported_Models/

## 2. 阶段 1 设计：FTS5 + jieba 预分词

**接口零改**：`MaterialRetriever.search(*, project_id, query, limit)` 签名与语义不变，只换实现类。

**为什么是"影子表"而不是 external-content**：要给 FTS 喂的是 **jieba 预分词后的空格串**，而 external-content 会**原样读源列**（读不到分词结果）。所以用普通 FTS5 表存 token 流，**由 store 在同一事务里维护**（不用触发器——触发器里没法调 Python 的 jieba）。

**表**（`schema.sql`）：
```sql
CREATE VIRTUAL TABLE IF NOT EXISTS material_chunks_fts USING fts5(
  chunk_id UNINDEXED,   -- 便于按 id 删/改（实测：DELETE/INSERT by chunk_id 可行）
  tokens,               -- jieba 预分词后的空格串
  tokenize = 'unicode61' -- 按空格切；token 已是词
);
```

**分词对称（唯一的正确性命门）**：`index_tokens(text)` 一份，索引侧与查询侧**都调它**（同一 `jieba.cut_for_search`、同词典）。查询侧每个 token 加双引号转义 FTS 语法。

**排序**：`bm25(material_chunks_fts)`（**用真表名，不是别名**——实测别名会报 `no such column`）；`score = -bm25`（越大越好，与现约定同向）。

**写路径维护**（全在 `materials.py`）：`_write_chunks`（insert，97/149/197 三处共用）顺带写 FTS；三处 `DELETE FROM material_chunks`（109/129/170）换成也删 FTS 的 helper。

**回填**：`database.migrate` 幂等段——`material_chunks` 有行而 FTS 空时，逐块分词写入（可重复跑）。

**启动预热**：jieba 首次加载词典 1–3s → 组装点预热一次（`jieba.initialize()`），不落在首个查询上。

**装配**：`container.py:283` 换一行 `SqliteLikeRetriever` → `SqliteFtsRetriever`（`SqliteLikeRetriever` 保留为 v1 + 回归网）。

## 4. 数据流

```
材料入库（put/replace/refresh）── _write_chunks
   │  每块：INSERT material_chunks   +   INSERT material_chunks_fts(chunk_id, index_tokens(heading+text))
   ▼  （同一事务）
查询 GET /projects/{id}/search ── SearchProject ── MaterialRetriever.search
   │  query ── query_tokens（jieba，每个 token 加引号）── MATCH 'q1 OR q2 OR …'
   ▼
   SELECT ... FROM material_chunks_fts f JOIN material_chunks c ON c.chunk_id=f.chunk_id
              JOIN materials m ON m.material_id=c.material_id
   WHERE f MATCH ? AND m.project_id=? AND m.owner_id=?  ORDER BY bm25(f)  LIMIT ?
   ▼
   MaterialHit（score=-bm25，excerpt 以首个命中 token 定位）── 老路一字不动
```

## 5. 3 个调优项：**已用本地实验定案**（2026-10-17，推翻"待语料"）

**实验**（用真库 46 条真实观察当语料，8082 字；每篇按标点切一段纯中文 8–14 字，
造 3 类查询：**逐字子串** / **同词换序**（词序打乱）/ **插停用词**（词间插"与"），
量 top1 与 recall@5；15 篇 × 3 类）：

| 方法 | top1 | recall@5 |
|---|---|---|
| **LIKE（现状 v1）** | 10/45 | **15/45** |
| jieba-FTS **AND** | 36/45 | 39/45 |
| **jieba-FTS OR** | **39/45** | **45/45** |
| trigram（无 jieba） | 10/45 | 15/45 |

**结论（三条调优项一次定完）**：

1. **查询构造 = OR**（不是 FTS5 默认的隐式 AND）。OR 在 top1 与 recall 上**双双最优**
   （45/45 vs 39/45）。实读原因：**jieba 分词是上下文相关的**——同一串字在片段里与在
   全文里可能切成不同 token，AND 会因"某个 token 不在全文 token 集里"整条不命中。
2. **停用词不用处理**。OR 天然容忍多余/缺失 token——"插停用词"那类查询 OR 15/15 全中；
   引 `stopwordsiso` 的收益被这条实测否掉（**砍掉这个依赖**）。
3. **trigram 实测 ≡ LIKE**（都是"只做子串"，两类改写在 trigram 上也 0/15）——它没解决
   任何失效模式，还涨索引。**jieba 是唯一有效的**（`simple` 要 `.so` 分发，仍不用）。

**残余（诚实记）**：本实验的查询词都取自文档本身（保证词面命中），测的是**词法**检索的
天花板；**语义鸿沟**（换成完全不同的词去问）任何词法方法都解决不了——那是阶段 2（向量）
的事，门未开。语料仅 46 条短文，方向性结论稳，绝对数字当量级看。

## 6. RIPR（实现时用；先写测试后写实现）

| # | R | I/P | 绿的标准 |
|---|---|---|---|
| 1 | 分词对称：索引与查询同一函数 | 同串两边分词 | 结果逐字相同（防"不对称→静默零命中"） |
| 2 | 中文词命中：查询词能命中含它的块 | 块 "权限模型"，查 "权限" | 命中（LIKE 命中不了） |
| 3 | 跨词序命中：查 "模型权限" 命中 "权限模型" | 同上 | 命中（词级倒排 + OR） |
| 3b | 词间插停用词也命中：查 "权限与模型" 命中 "权限模型" | 同上 | 命中（OR 容忍多余 token） |
| 4 | 项目/owner 隔离不变 | 别项目有同词块 | 不返回（回归锚） |
| 5 | 按 chunk 增删改索引同步 | 写入→改→删 | MATCH 结果对应变化 |
| 6 | 回填幂等 | 老库（有块无 FTS）跑 migrate | FTS 补全；再跑不重复 |
| 7 | 空查询/通配符安全 | `""` / `100%` / `a"b` | 空回空；特殊字符不报错 |
| 8 | 排序：更相关的在前 | 两块，一块多次命中 | `score` 与顺序同向 |
