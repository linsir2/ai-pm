## 0. 为什么要真跑、为什么先写死判据

M6 的代码级核验全绿（后端 1082 · 前端 182 · ruff · tsc · 架构守卫），但有三件事**只有真模型能给答案**：

① 每轮多出的那一次 Curator 调用（以及两处提示词各 +≤20 行）**到底花了多少**；
② 模型攒下来的记忆**是不是可信**（有没有编内容、有没有把功能细节记进去）；
③ 记忆真的进了提示词之后，**"换了个说法的重问"有没有降**（`m1.db` 那条现场的对症验证）。

判据先写死，免得事后找理由（这个项目的规矩：`P28` §3·T0 / `P37` §6）。

## 2. 探针怎么改（相对 M4 那一支，只改三处）

1. **确认时把记忆提议一起勾上**：`RoundCommand(kind="confirm", …, accepted=…, accepted_memory=tuple(m.proposal_id for m in view.memory_proposals))`——
   不勾的话记忆永远不落库，这一趟什么都测不到；
2. **开留样**：`replace(settings, trace_model=True)` → 跑完直接查 `model_calls` 表拿**每次调用的 purpose / 耗时 / ok**（调用数与耗时是阈值里唯一的两条硬数字）；
3. **多打两行观测**：每轮的 `memory_proposals`（条数 + 每条 kind/text/refs）、确认后的记忆条目数、以及**第 2 轮提示词里 `$project_memory` 的实际内容**（从留样表里抓那段）。

## 3. 预注册判据（跑之前就写死）

| 指标 | 阈值 | 不过怎么办 |
|---|---|---|
| 每轮模型调用数 | 190 量级 → **≤ +2**（Curator 1 次；多的只能是重试） | 查是不是提示词太长导致重试 |
| 整合耗时中位 | 不上涨 **> 10%**（对比 P38 后的 48.1s） | 先砍注入行数（20 → 10），再谈回退 M6c |
| 提示词新增 | **≤ 20 行 × 2 处** | 渲染限量没生效，先修限量 |
| 记忆条目数 | **≤ 60** | 容量护栏本该拦住，拦不住就是 bug |
| 整轮 eval | **10/10 不回退** | 回退 M6c（保留 M6a/M6b：它们不改模型输入） |
| 阻塞数 | **不回退**（0 阻塞车道仍 0） | 同上 |
| 记忆质量（人工核） | 抽 ≤10 条：**不许有** ① 无出处的 ② 功能细节/过程记录 ③ 与正文冲突却写反的 | 有一类就记成发现，**当场不改**（先量后改） |
| 观测（不当门槛） | 跨轮/同轮近义重问条数（0.3–0.6 档 + 人工核 5 条） | 只记，不改 |

## 4. 数据流（这一趟走的就是产品那条路，只有"勾"是多出来的）

```
L1 第 1 轮原文 → start → 席位 → 跳过问卷 → 【Curator 出记忆提议】→ 草案卡
  → confirm(accepted=全部, accepted_memory=卡片上那几条) → 同一个事务：文档 + 记忆

  → confirm → 导出 Markdown
统计：model_calls（purpose/耗时/ok）· rounds.payload.memory_proposals / accepted_memory_ids
      · project_memory.payload（最终记忆）· 导出里第 6 章
```
