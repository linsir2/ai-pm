# P31 方案 · 导出附录 A 只列"本文引用过"的出处

> **状态**：已执行（见文末"执行结果"）。

> **性质**：口径修正 + 一处过滤。**不动正文、不动 schema、不动端点、不动提示词、不动前端**。
> **与 P30 的关系**：P30（全量真跑审计 + 运行时接管）是另一份待拍板方案，本批与它无依赖。

`〔E…〕` 的那个编号。

## 2. 根因（一句话）

**`_appendix_a` 排的是"项目账本全量"，不是"这份文档的出处"。**

```
ExportMarkdown → ledger = EvidenceReader.get(project_id)   ← 项目级、跨所有轮次
                                                              ↓
_appendix_a(ledger)  →  for evidence in ledger.evidences(): 全排
```

账本是**项目级、只增、跨轮**的（`05-DDD架构.md` E1：编号全局唯一、只增、永不复用）。
它装的不只是"进了文档的东西"，还有：

- 用户提过但没被采纳的主张（`user_input`）；
- 席位给过、但被用户点了"不要"或被 `unaccounted` 判为没交代的判断（`agent_derived`）；
- 回答过的问卷（`card_answer`）——即便对应的提案没被采纳；
- 跳过的题 / 没排上的题 / 撤下未决项这些机械动作的记账（`system_default`）；
- 更早轮次（含没确认到底的轮次）留下的一切。

所以在真跑里，附录 A 有一半以上是"正文里根本没有的编号"。对读者来说，
这些编号既没有落点（在正文里找不到它），又稀释了真正的出处——把一份 1 万字的文档
变成"正文 5 千 + 出处 5 千"，而其中 6 成是查不回去的。

**这不是"该带多少字"的问题，是"附录在服务谁"的问题。**
附录 A 的用途（`DESIGN.md` R3：编号是产品唯一的信任机制）是"读者看到正文里那个 `E12`，
翻到附录能知道它是谁说的"。**正文里没出现过的编号没有这个需求。**

## 3. 口径

**附录 A = 本文引用过的编号 + 一行"还有多少条没进本文"的实话。**

1. **准入**：编号出现在 `DocumentView` 的任一条目 `refs` 里就算"本文引用过"——
   13 章正文（含功能子树字段）**与偏好区**都算（偏好区本来就会在附录 B 里带自己的 `〔E…〕`）。
2. **顺序**：仍按账本顺序（即编号顺序），不重排、不分组——查编号要一眼找到。
3. **格式不动**：一行仍是 `- E编号 · kind · [外部指称 · ]一句话摘要`（60 字上限、不带 `raw_span`，遵守 `04` D5）。
4. **不静默省略**：正文一条出处都没引用时写"（本文没有引用任何出处）"；
   账本里还有没被引用的条目时，末尾加一行
   `（另有 N 条出处没有被本文引用——未被采纳的提案、被跳过的题与更早的轮次都留在系统里，可按编号查）`。
   **它们的文本一个字都不进交付物。**
5. **确定性不动**：过滤只读 `DocumentView` 与账本，同一份输入永远同一份字节。

## 4. 为什么不做别的（考虑过、否掉）

| 候选 | 为什么不做 |
|---|---|
| 把附录 A 单独出一个文件 / 改成可选下载 | 交付物形态是 `01` §7.3 定的（一份 Markdown）；改形态要动端点与前端，收益不比过滤大 |
| 缩到 30 字摘要、或改成表格 | 只是把 8 千字压到 6 千，治标；真正多余的是条目数，不是每行长度 |
| 只列 `席位判断 / 外部材料`，不列 `用户输入` | "用户输入"正是可追溯链的终点，砍它等于砍掉信任机制本身 |
| 连"依据链上的上游编号"一起带出来 | 附录本来就不表达链（只给编号+kind+摘要，没有 `derived_from` 列）；链在系统里的出处查询里看 |
| 给附录加上限（如只列前 100 条） | 会在正文里留下"有编号、附录里查不到"的洞，比现在更糟 |
| 把账本按文档裁剪（改聚合） | 账本是唯一真相源且只增（E1/E2），**不能**为了导出瘦身而改它 |

## 6. 边界（本批不做）

- 不动账本聚合（不裁剪、不归档）——E1/E2 一个字不改；
- 不动正文形态（每一条内容照旧挂编号）；
- 不动 `摘要 60 字` 这个上限；
- 不动 s11 未决清单（它是正文内容，不是附录——L2 那份里它是 7 3xx 字符，
