# 02 · 项目现状全景

> 本分册回答"我到底有什么"：把项目的技术资产逐条盘点出来，并把每条资产**对应到 JD 关键词**。
> 所有结论均来自对代码、设计文档、实验脚本与验收记录的逐条核对，带真实文件路径。

---

## 0. 项目是什么

**PM Studio**：单用户本地 Web 应用。产品经理把零散想法倒进来，系统用**领域专家席位**整理成结构化产品文档；**AI 只出草案，用户确认后才写入**，每次改动产生一个版本。

- 后端：Python 3.13 + FastAPI + LangGraph + LiteLLM + SQLite（FTS5 + sqlite-vec + jieba）+ Redis（可选）
- 前端：React 18 + Vite 6 + TypeScript strict + vitest（零第三方 UI 依赖）
- 规模：后端约 38.7k 行 Python；前端约 75 个组件；257 个测试文件；684 次提交；90 份设计计划文档

## 1. 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│  frontend/   React + Vite：文档区（约 70%）+ 闭环区 + 弹出层     │
│    api/ 唯一 HTTP 出口 · state/ 纯函数 reducer · 零业务判断     │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTP + SSE
┌───────────────▼──────────────────────────────────────────────┐
│  api/    FastAPI：HTTP 动作入口 + SSE 推送口（按 owner 裁剪）    │
├──────────────────────────────────────────────────────────────┤
│  infrastructure/   LangGraph 图 · LiteLLM 网关 · SQLite 仓储     │
│                   席位/角色/工具目录（TOML）                     │
├──────────────────────────────────────────────────────────────┤
│  application/   用例编排 + agent + 上下文渲染 + 装配            │
├──────────────────────────────────────────────────────────────┤
│  domain/    authoring · provenance · round · memory · ports   │
│             （零外部依赖，由 AST 守卫强制）                      │
├──────────────────────────────────────────────────────────────┤
│  harness/  运行时控制平面（最内层，零业务词）                    │
│             信封 · 结构化调用 · 归一化 · 失败分类 · 韧性 · 网关   │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向单向且由守卫强制**：`harness` 只许 import 自己 + `pydantic`/`litellm`/`pybreaker` + 标准库，反向一行都不许。守卫实现见 [test_harness_imports.py](file:///workspace/ai-pm/backend/tests/architecture/test_harness_imports.py)，文档里记录了一次"守卫本身静默失效"的修复（集合成员判断 vs 前缀匹配）。

## 3. 前端能力（常被低估的加分项）

- **零第三方 UI 依赖**：React 18 + TS strict + vitest，仅自托管拉丁字体子集。
- **5 个顶层视图 + 三栏工作台 + 3 个闭环页签 + 4 内联抽屉 + 5 悬浮抽屉**；主闭环、工具层、交付（就绪度/版本/导出）、记忆、探索、讨论、模拟、管理后台全部有界面。
- **业务判断全部下沉到纯函数**（`payload.ts`/`status.ts`/`progress.ts`/`readiness.ts` 等），组件不做业务判断。
- **前后端接口双向零差**：`check_api_parity.py` 校验后端 OpenAPI ↔ 前端 `client.ts`。
- **设计系统**：`DESIGN.md` 是唯一真相源，`tokens.css` 是唯一实现。

> 对应 JD 关键词：全栈 / 工程化闭环 / 产品落地。

## 4. 诚实边界（写进简历前必须知道）

这些**不是缺陷，是如实告知**，写简历时要主动说清，否则面试会被拆穿：

1. **单用户本地应用**：SQLite 只允许一个写事务，**不承诺高并发写入**（多 worker 的真实收益是读吞吐、SSE 分发、argon2 并行）。
2. **无外部向量数据库**：用 SQLite（FTS5 + vec0 + jieba）搭混合检索——这是**优势**（零运维、可复现）也是**关键词劣势**（ATS 里没有 Milvus/Qdrant 命中）。
3. **部分设计明确不做**：MCP 读/写侧、卡片结构化引用候选、思维链展示等（`04-未决.md` 有据可查）。
4. **设计文档与代码存在漂移**：如模板管理 UI 已实现但 `06-前端.md` 仍标"未实现"（建议回改文档，符合"双真相源明令禁止"的规矩）。

## 5. 一句话总结

> 这是一个**单用户本地 Web 应用**里的完整 RAG + 记忆 + 评测工程：没有引入向量数据库/外部检索服务，用 SQLite 单库搭出混合检索；用真语料 A/B 定参数；用配对增量与符号检验做检索验收；把"记忆"做成可追溯、可确认、可治理的注意力预算系统；并用 AST 守卫 + 架构测试 + 混沌矩阵把"生产级"落到可验证的层面——**全链路带量化证据与诚实边界**。
