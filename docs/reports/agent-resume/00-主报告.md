# 主报告 · PM Studio 的「Agent 开发工程师」简历化分析

> 本报告回答一个问题：**这个项目在 Agent 开发工程师的招聘市场里到底处在什么位置？该在哪里优化、该补什么功能，才能让简历从"一个 PM 工具"变成"一个生产级多 Agent 系统"？**
>
> 结论可能出乎意料：**你的项目技术深度并不低，低的是"被看见"和"被翻译"。**
>
> 目标岗位定位：**国内应用落地层**。分析基于 5 个并行子任务的代码深挖 + 直接核验 + 多来源 JD/简历调研，每条结论都带出处（见各分册）。

> ✅ **2026-10-22 实施结果**：三件 P0 **已全部落地并验证**——
> README（对外门面 + 9 张真实截图）、Docker + CI（工程化 + 15 条防静默失败守卫）、
> **MCP 只读侧 + 模型自主调**（2026 最热关键词，**真模型 + 真 MCP server 跑通**）。
> 详见 [04-优化建议与落地蓝图.md](04-优化建议与落地蓝图.md) 开头的"实施结果"表。

## 一句话定位（可直接放进简历标题/摘要）

> **设计并实现了一个"AI 只出草案、人确认才写入"的多 Agent 产品文档生成系统**：自研运行时控制平面（统一信封 + 结构化输出归一化 + 失败分类权威表 + 熔断/隔离舱/重试预算），用 AST 依赖守卫强制 DDD 分层；10 个领域化 Agent 经 LangGraph 编排完成"输入 → 主张 → 席位意见 → 问卷 → 草案 → 确认 → 版本"闭环，并配套可追溯账本、混合检索（FTS5+向量）、跨轮记忆治理与 18 个混沌/容错 e2e 测试。

---

## 核心结论（5 条）

### 结论 1：你的技术深度已经是头部水平，问题不在"内容少"

代码规模：后端约 38.7k 行 Python（DDD 六层）、前端约 75 个组件（React 18 + TS strict）、257 个测试文件、684 次提交、90 份设计计划文档。更关键的是**深度**：熔断/隔离舱/重试预算三件套、结构化输出归一化引擎、失败分类单点权威表、混合检索融合算法、跨轮记忆治理、架构守卫（含"守卫自己有没有效"那一层）——**这些是绝大多数候选人根本没听说过的东西**。

> 详见 [02-项目现状全景.md](02-项目现状全景.md)。

### 结论 2：最致命的缺口是"没有 README"

`Glob **/README*` 核验结果：**仓库根目录没有任何 README**。HR/面试官 7 秒扫描 GitHub，看不到 README 就等于项目不存在。这是**投入产出比最高**的一件事。

### 结论 3：第二梯队缺口是 MCP / Docker / Eval 三件套

| 缺口 | 核验 | 为什么重要 |
|---|---|---|
| **无 MCP** | 全仓 `grep -i mcp` 零命中 | 2025-2026 最热关键词，海外 JD 明确要求"亲手写过 MCP server" |
| **无 Docker/compose** | 无 `Dockerfile` | "可运行 Demo"是强信号；面试官 clone 下来 5 分钟跑不起来的项目会被直接跳过 |
| **Eval 未产品化** | `backend/evals/` 有 11 用例但未做成可复现 benchmark | JD 明确要"自动化评测流水线"，你已有 80% 的料，只差最后一公里 |
| **无 Reranker** | 无 RAG 重排（仅"题号重排"） | RAG 全链路缺一环 |
| **无 CI** | 无 `.github/` | 工程规范性 |
| **无可观测性** | 无 OTel/LangSmith/Langfuse | JD 的 Observability 分区完全空白 |

> 详见 [03-JD对照与差距分析.md](03-JD对照与差距分析.md)。

### 结论 4：你其实已经在做"评测"，只是没把它当卖点

`backend/evals/` 已有 11 条真模型用例 + `assertions.py`（12 条结构断言、纯函数、不看文案只看形状）；`03-案例与验收.md` 有检索质量验收清单（配对增量 + 符号检验）。这是**很多候选人完全没有的能力**——但你的 README 不存在，所以它现在一钱不值。

### 结论 5：真正的简历问题是"把业务外壳当成了主角"

你描述项目时说的是"帮产品经理整理文档的工具"——这是**业务描述**。而 JD 想听的是**技术描述**：多智能体编排、RAG、记忆治理、韧性工程、可追溯。同一份代码，两种讲法，面试官的反应天差地别。

> 详见 [05-简历改写与面试弹药.md](05-简历改写与面试弹药.md)。

## 优先级路线图

### 🔴 P0：不做就是硬伤（投入产出比最高）

| # | 事项 | 为什么 | 预期简历收益 |
|---|---|---|---|
| P0-1 | **写 README**（定位 + 架构图 + 快速开始 + 截图位 + 量化指标） | 没它项目等于隐形 | 从"看不见"到"第一眼就有内容" |
| P0-2 | **Dockerfile + docker-compose** | 可运行 Demo 是强信号 | "5 分钟跑起来"直接拉开差距 |
| P0-3 | **工具层包成 MCP Server** | 命中最热关键词，且**贴合你现有架构**（`infrastructure/tools/` 已有 TOML 工具目录） | 技能栏多一行"MCP"，且讲得出细节 |

### 🟠 P1：补上就是"王者段位"

| # | 事项 | 为什么 | 预期简历收益 |
|---|---|---|---|
| P1-1 | **Eval 流水线产品化**（可复现 benchmark + 指标看板） | JD 明确要求；你已有 80% 的料 | "有评测体系"是资深岗溢价点 |
| P1-2 | **加 Reranker**（cross-encoder 重排） | RAG 全链路补全 | 技能栏"RAG pipeline"完整 |
| P1-3 | **CI（GitHub Actions）** | 工程规范性 | 仓库专业度 |
| P1-4 | **默认分支规范化**（`new-branch` → `main`） | 细节观感 | 面试官会注意到 |

### 🟡 P2：锦上添花

| # | 事项 | 为什么 |
|---|---|---|
| P2-1 | **可观测性**（OTel / Langfuse 埋点） | 补 Observability 空白 |
| P2-2 | **架构博客**（"为什么图不是真相源"） | 面试谈资 + 对外影响力 |
| P2-3 | **回改设计文档漂移**（模板管理 UI 已实现但文档仍标"未实现"） | 符合你"双真相源明令禁止"的规矩 |
