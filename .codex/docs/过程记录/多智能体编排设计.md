# 多智能体编排设计

> 状态：设计稿 · 2026-09-21 · 待裁决
> 回应：矛盾检测与缺失信息整合应该由专门的智能体做，不是代码；以及"并行产出信息包 → 整合 → 出问卷"
> 这条主链路到底怎么设计。附七个用户场景。

---

## 一、我上一版错在哪

我把"张力检测"和"去重"写成纯代码，当成一个机械步骤。这错得很具体：

**代码只能做字面比较，而矛盾往往不是字面的。**

举一个代码永远查不出来的例子：同一份文档里，

> s8 性能：导出要求 1 秒内返回
> s8 成本：单次导出成本不超过 0.01 元

这两个字段写在不同的 target 上，措辞毫无重叠，代码的字符串比较和 target 比对都不会报警。
但它们**真的打架**——1 秒返回意味着常驻计算资源，成本约束意味着必须复用/排队。
只有懂业务的智能体才能看出这是一组矛盾。

反过来，代码还会**误报**：两个席位用不同措辞说同一件事（"量级"和"数据规模"），
字面不相似，代码判成两条独立缺口，于是问卷里出现两道重复题——正是你要避免的。

所以结论是：**整合、去重、矛盾判定，全部由智能体做；代码只做两件事——结构校验和候选召回。**

## 二、代码与智能体的分工（这条边界要钉死）

| 谁 | 干什么 | 为什么是它 |
|----|--------|-----------|
| **代码** | ① 结构校验：schema、证据引用、门禁里可机械判的部分<br>② 候选召回：把"两两比对"的爆炸复杂度压成几十个候选对 | 这些是**确定性的、可穷举的**，交给模型既慢又不准 |
| **智能体** | 一切需要语义判断的：归一化到 target、合并、去重、判定是否真矛盾、取舍、措辞 | 这些是**判断**，代码只会字面匹配 |

一句话：**代码负责把规模压下来，智能体负责拍板。**

以矛盾检测为例，它是两层的：

```
第 1 层（代码 · 召回）
  找出值得看的候选对：同一 target 上的不同结论 / 同一 feature 内的新增与既有冲突 /
  字面高度重叠 / 涉及同一指标
      ↓ 通常几十个候选，不是几百个
第 2 层（整合者 · 判定）
  逐个判定：真矛盾？还是措辞差异？还是范围重叠而非冲突？
  跨字段的语义矛盾（"1 秒返回" vs "成本 1 分钱"）就靠这一层抓出来
```

## 三、角色编制（八个角色）

| 角色 | 类型 | 职责 | 输出包 |
|------|------|------|--------|
| **Analyzer 解析者** | 智能体 | 切分输入、定性（七种标签）、初归位 | `claims` `placement` |
| **领域席位**（N 个） | 智能体 | 用自己的专业视角发现缺口、风险、质疑 | `finding` |
| **守卫席位**（范围守卫、陌生人读者） | 智能体 | 常驻，盯边界打架与外部可读性 | `finding` |
| **Integrator 整合者** | 智能体 | 归一化、合并、去重、归类，产出**矛盾问卷**与**缺失信息问卷** | `conflict_form` `gap_form` |
| **Writer 撰写者** | 智能体 | 把已确认信息写成草案，不引入新信息 | `draft` |
| **Reviewer 审阅者** | 智能体 | 独立审草案是否超出证据 | `review` |
| **Memory Curator** | 智能体 | 维护文档级 PROJECT.md（核验/合并/删除/新增） | `project_md_patch` |
| **Validator 校验器** | **代码** | schema、证据、门禁可判项、候选召回 | `violation` `candidate_pair` |

### 3.1 Integrator 的产出边界：只出两类问卷

你说"并行产出信息包，然后整合一下，输出问卷"——这个"整合"必须是一个**有判断力的角色**。
但它的产出边界必须钉死：

> **Integrator 只产出两类问卷：① 矛盾问卷 ② 缺失信息问卷。它不碰草案。**

草案那条线是 Writer → Reviewer → Validator，与整合者**互不交叉**。
整合者既不写正文，也不裁决矛盾，也不决定文档怎么写——它只负责把散落的 finding
变成"值得问人的问题"。

它为了产出这两类问卷，内部做四件事（都是手段，不是额外产出）：

1. **归一化**：把每个 finding 映射到 target（章节 + 字段）。映射不出来的打回给提问席位。
2. **合并与去重**：同一 target 的问题合并；与文档已有内容重复的丢弃；与历史问卷重复的丢弃。
3. **归类**：把这个 finding 归进"矛盾"还是"缺失信息"。判定依据是——
   是否存在两个相互冲突的结论？是则矛盾，否则是缺失。
4. **降级**：噪音踢掉，次要问题降级为清单项，只把值得打断用户的问题放进问卷。

**它是唯一有权产出问卷的角色**（`emits: conflict_form, gap_form`）。其他席位只能产出
`finding`——这保证了问卷质量只有一个责任人，不会五个专家各弹各的卡。

### 3.2 权限矩阵

| 角色 | 能产出 | 能读 | 能写文档 | 能写 PROJECT.md |
|------|--------|------|---------|----------------|
| Analyzer | claims, placement | 输入 + PROJECT.md + 章节状态表 | ✗ | ✗ |
| 领域席位 | finding | 同上 + 自己章节（可申请扩读） | ✗ | ✗ |
| 范围守卫 | finding | 同上，**不受 read_scope 限制**（必读 s2 + s4） | ✗ | ✗ |
| Integrator | conflict_form, gap_form | 全部 finding + 状态表 + 历史问卷 | ✗ | ✗ |
| Writer | draft | 已确认主张 + 证据账本 + 目标章节 | ✗ | ✗ |
| Reviewer | review | draft + 证据账本 | ✗ | ✗ |
| Memory Curator | project_md_patch | changed_block_ids + 卡片结论 | ✗ | ✗（只能提议） |
| Validator | violation, candidate_pair | 任何包 | ✗ | ✗ |
| **确认端点**（代码，非智能体） | — | — | **✓ 唯一** | **✓ 唯一** |

最后一行是全系统的结构性保证：**八个角色全都不能写文档，写入路径只有确认端点一条。**

## 四、一轮的完整编排

```
输入（首轮输入 / 问卷答案）
   ↓
Analyzer：切分 + 定性 + 初归位
   ↓
开场卡（复述 + 席位提名 + 遗留阻塞项 + 预期管理）          ← 中断 1
   ↓
┌──────────── 并行，互不可见 ────────────┐
│  领域席位 × N    范围守卫    陌生人读者*  │
└──────────────┬────────────────────────┘
               ↓ 各自产出 finding 包
Validator（代码）：候选召回，生成候选对
               ↓
Integrator：归一化 → 合并去重 → 归类（矛盾 / 缺失）→ 降级
               ↓
        问卷（两组：矛盾组 + 缺失信息组，按章节排序，≤12 题）  ← 中断 2
        ↓
用户作答
        ↓
答案当作新输入 → 复用同一套编制（按影响面缩编）：
  Analyzer 重新切分 + 定性
    → 相关席位重新发现
    → Integrator 再整合
    → 若仍有矛盾或缺口 → 第二次问卷                    ← 中断 3（可跳过/可延展）
        ↓  直到不再产生新问题
Writer：生成草案  ⇄  Reviewer：挑刺（≤2 轮）
        ↓
Validator：schema + 证据引用 + 门禁可判项
        ↓
草案卡                                                      ← 中断 4
        ↓
确认 → 【图外】确认端点写入 → 版本快照
        ↓
Memory Curator：提议 PROJECT.md 变更（逐条确认）
```

`*` 陌生人读者只在首次构建与交付前各跑一次。
并行阶段的时间由**最慢的那个席位**决定，不是席位耗时之和。

## 五、七个用户场景

每个场景都说明同一件事：**同样的八个角色，在不同形状的输入下派上不同的人、问出不同的问题。**

### 场景 1 · 首次构建：一段散话

**输入**："想做订单导出，运营每天要用，量不大，月底要上。"

**提名**：数据规模席、权限与角色席、范围守卫、陌生人读者。

**关键发现**

- 数据规模席：**"量不大"是无依据的自我判断**，标记为猜测（不是事实），必须转成带验证方式的假设
- 权限与角色席：没人说过谁能导出、导出给谁看——这属于数据外流风险
- 范围守卫：**"月底要上"与"量大必须异步"存在潜在冲突**（时间约束会逼出降级方案）

**整合结果**：3 道题按章节分组——s8 量级、s3 权限、s4 月底范围取舍。

**这轮的意义**：把一句"量不大"从一个会被写进文档的伪事实，变成一条待验证假设。

### 场景 2 · 增量加功能：撞上旧边界

**输入**："再加个每天定时导出。"

**提名**：范围守卫（常驻）+ 数据规模席（导出相关）。

**关键发现**：范围守卫直接指向 s4 的"本版不做定时导出"（范围守卫常驻、不受 read_scope
限制，就是为这一刻准备的）。

**整合结果**：1 道矛盾题——改非目标 / 维持不做 / 暂不决定（选 C 则落成开放问题）。

**这轮的意义**：**边界被显式裁决，而不是被静默推翻。** 这是这个产品存在的理由。

### 场景 3 · 用户给的是技术方案，不是需求

**输入**："我想用 Redis 做导出任务队列。"

**关键判断**：这是**技术方案**。PM 通常不该定方案，而系统也不该直接把它写进 s9。

**处理**：方案被临时定性为"偏好/建议"，先反问它服务的目标——

> Q1 你要队列是为了什么？○ 不阻塞页面 ○ 支撑更大的数据量 ○ 失败可重试 ○ 其他
> Q2 如果只是"不阻塞页面"，用已有的后台任务机制是否足够？

**整合结果**：2 道题，先问目标再谈方案。

**这轮的意义**：如果目标是"不阻塞页面"，队列可能是过度设计；如果目标是"支撑 50 万条"，
队列才是必需。**先问目标，再落方案**——这条能挡住大量被 PM 随手写进文档的技术债。

### 场景 4 · 同一段输入里自相矛盾

**输入**："导出要快，最好 1 秒内返回，但数据有几十万条。"

**关键发现**：这是**输入内部矛盾**（不是跨轮矛盾）——几十万条与 1 秒返回在同步实现下不可兼得。
（代码召回的候选对会命中"同一段输入内的指标冲突"，Integrator 判定为真矛盾。）

**整合结果**：1 道取舍题——

> ○ 接受 1 秒返回：必须常驻资源，成本上升
> ○ 接受异步：点导出后后台跑，完成后通知（更省钱，但不是"1 秒"）
> ○ 还没想好，先记成开放问题

**这轮的意义**：矛盾在**进入正文之前**被拦下，而不是等工程师看到文档后跑来问你。

### 场景 5 · 用户只给目标，不给功能

**输入**："想让运营少干点重复劳动。"

**关键判断**：这是**目标级输入**，没有功能可归位。硬凑一个功能是最糟的处理方式。

**处理**：Analyzer 把它定性为"目标"，归到 s2；Integrator 出题引导出功能——

> Q1 你说的重复劳动主要是哪一类？
> ○ 每天手工导数据 ○ 对账核数 ○ 打发货单 ○ 其他（可写）
> Q2 这件事现在每天花多少时间？（用来判断值不值得做）

**这轮的意义**：**不硬凑功能。** 先立目标，再从目标里长出功能——这也保证了每个功能
都能关联到一条目标（门禁要求）。

### 场景 6 · 文档已经很大，只加一个小功能

**输入**："订单列表加个备注字段。"

**提名**：只请 2 位——数据模型席 + 陌生人读者。数据规模席、合规席、性能席都不请。

**关键发现**：备注长度上限？谁可见（内部备注还是客户可见）？

**整合结果**：2 道题。

**这轮的意义**：**成本随改动影响面缩放。** 不是每轮都跑五个专家十二道题。
一个字段的改动就两支席位两道题——这条决定了产品在真实使用中会不会被嫌重。

### 场景 7 · 交付前（每份文档只跑一次）

**动作**：陌生人读者跑最后一次（只读文档，不看上下文）+ 阻塞项清零 + 门禁判定。

**典型产出**

- 陌生人读者："我读到第五章说导出 1 万到 10 万行，但全文没说这个数字是怎么来的。"
  → 命中 s10 那条一直没有验证方式的假设 → 转成阻塞型开放问题
- 门禁：s8 成本约束仍是空的，阻挡升级到"已确认"

**这轮的意义**：**这是单用户系统里唯一的外部检验。** 没有第二个人读文档时，
让一个空白读者替工程师先读一遍。

## 六、待裁决

1. Integrator 的"丢弃"（去重之外的过滤）要不要在界面上留痕？我倾向要——
   可查"这条为什么没进问卷"，否则用户无法判断是不是漏问了。
2. 场景 3 里"把技术方案临时定性为偏好"这个动作，要不要先过一道复述卡让人确认？
   我倾向要（走统一入口不变式），代价是多一次打断。
3. 答案轮（复用编制）的终止条件怎么定？我倾向：默认最多两轮问卷（输入轮 + 答案轮各一次），
   超出部分降级为开放问题，但允许用户主动说"继续深挖"。
