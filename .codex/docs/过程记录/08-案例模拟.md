# 08 · 案例模拟（两轮走完主闭环）

> 用途：用两个真实形状的输入，把主闭环从头走到尾，检验"席位只出问题、内容来自用户"
> 这条边界站不站得住。
> 范围：只用到 v1 的角色（Analyzer / 领域席位 / Integrator / Locator + Writer / Validator）。
>
> **2026-09-22 注**：本文按"席位只出问题、内容全部来自用户"的旧模型写的。
> 该模型已改：席位现在**也要推导内容候选**（标 `derived`，带依据与理由）。
> 案例的骨架与结论仍成立，但两处会变——席位会直接提出验收标准草案、异常边界草案，
> 而不是只问；草案卡上会按"你说的 / 它推的 / 它提议的"分三组。

## 案例 A · 从零开始，一轮里塞了三件事

### A1 用户输入（第一轮，原样）

> 想做个订单导出的功能，运营每天都要用，最好能按时间筛选，数据量大概几万吧。
> 另外登录页太丑了，顺便改一下，支持微信登录。月底必须上线。

### A2 切分与定性（Analyzer，一次调用）

| 编号 | 主张 | 标签 | 初归位 |
|------|------|------|--------|
| E1 | 要做一个订单导出功能 | 需求 | s5 |
| E2 | 运营每天都要用 | 事实 | s3 |
| E3 | 最好能按时间筛选 | 需求 | s5 |
| E4 | 数据量大概几万 | **猜测** → 升格为假设 | s10 |
| E5 | 登录页太丑 | **偏好** | 偏好区（不进正文） |
| E6 | 登录页要改一下 | 需求 | s5 |
| E7 | 支持微信登录 | 需求 | s5 |
| E8 | 月底必须上线 | 约束 | s10 |

注意 E4 和 E5 旁边会自动打警示：猜测不能当事实写进正文，偏好不好写成需求。

### A3 开场批（4 张卡）

```
卡1 复述理解
   E1 订单导出功能        [需求] → s5功能
   E2 运营每天要用        [事实] → s3用户
   E3 按时间筛选          [需求] → s5功能
   E4 数据量大概几万      [猜测] → s10假设  ⚠
   E5 登录页太丑          [偏好] → 偏好区   ⚠
   E6 改登录页            [需求] → s5功能
   E7 支持微信登录        [需求] → s5功能
   E8 月底必须上线        [约束] → s10
   我理解错了吗？标签和去处都能改。

卡2 本轮写范围
   建议：s5 功能需求 / s3 用户与受众 / s10 假设约束依赖
   这轮不改的章节，AI 不会动。

卡3 席位编制（预选 4 位，可删）
   ☑ 数据规模与性能   你提到"导出"和"几万条"，量级决定同步还是异步
   ☑ 权限与角色       导出涉及谁能看、能不能带客户信息出去
   ☑ 前端交互         这轮包含登录页改造
   ☑ 业务规则         微信登录、时间筛选都有状态与边界要定

卡4 遗留阻塞项
   无（第一轮）
```

### A4 用户在这一步做了三件小事

1. 把 E5 的标签从"需求"改成"偏好"（系统原来的判断就是偏好，他只是确认）
2. 在卡1 的备注里写："E6、E7 是另一件事，跟导出没关系"
3. 席位全留，确认开跑

> 这一步的价值：系统原来会把三件事混在一批提案里，用户一句话就分清了。
> **这仍然是一轮，不是三轮。**

### A5 席位并行发现（互不可见）

**数据规模与性能席**

- F1（缺信息）：E4 是估的，不能当事实。它是同步导出和异步任务的分界点（1 万行以内可同步，10 万行以上必须异步），必须问清量级。
- F2（缺信息）：导出超时容忍多少？没有这个数，s8 的性能条目写不出来。

**权限与角色席**

- F3（缺信息）：谁能导出？谁能看到全量订单？导出文件和页面看的权限不一定相同。
- F4（缺信息）：导出内容包含客户手机号等敏感字段吗？要脱敏还是要审批？

**前端交互席**

- F5（缺信息）：微信登录要覆盖哪些端？只 PC，还是含移动端？这决定要不要额外资质与回调地址配置。
- F6（缺信息，与 F1 重叠）：导出这个动作的数据量大概多少，决定进度提示还是要排队。

**业务规则席**

- F7（缺信息）：时间筛选是必填还是可选？口径按创建时间还是支付时间？

### A6 Integrator 整合

**合并**：F1 与 F6 指向同一个目标字段（s8 性能上限），合并成 Q1，`asked_by` 保留两个席位。

**归类**：全部是缺信息，没有矛盾（因为 E4 已经被标成猜测，不算与其它内容冲突）。

**排序**：按章节排，不问顺序。

**降级**：合并后 6 题，一批最多 5 张卡，第 6 题（F7 时间口径）降级为清单项，
放进问卷下方的只读列表，可一键接受默认值。

### A7 问卷（一批 5 张 + 1 条清单项）

```
▾ s8 非功能需求
  Q1 单次导出的最大行数是多少？            [数据规模席 + 前端交互席]
     ○ 少于 1 万  ○ 1万–10万  ○ 超过 10 万  ○ 不确定
     为什么问：1 万行可同步导出；10 万行以上必须异步，是两套实现。
  Q2 一次导出最多能等多久？                [数据规模席]
     ○ 10 秒内  ○ 1 分钟内  ○ 可以等几分钟（后台跑）

▾ s7 数据与接口
  Q3 导出文件里包含客户手机号吗？           [权限与角色席]
     ○ 包含，需要脱敏  ○ 包含，需要审批  ○ 不包含

▾ s3 用户与受众
  Q4 谁能执行导出？                        [权限与角色席]
     ○ 运营专员  ○ 运营专员 + 主管  ○ 所有登录用户

▾ s6 业务流程与交互
  Q5 微信登录要覆盖哪些端？                [前端交互席]
     ○ 只 PC  ○ PC + 移动  ○ 还没想好

清单项（可一键接受默认值）
   · 时间筛选是必填（默认），口径按创建时间
```

### A8 用户作答与回灌

Q1 选"1 万 – 10 万"；Q2 选"1 分钟内"；Q3 选"包含，需要脱敏"；
Q4 选"运营专员 + 主管"；Q5 跳过；清单项接受默认。

回灌（答案当作新输入，走同一个入口）：

| 编号 | 内容 | 来源 |
|------|------|------|
| E9 | 量级在 1 万到 10 万之间 | Q1 |
| E10 | 单次导出可等待 1 分钟 | Q2 |
| E11 | 导出含客户手机号，必须脱敏 | Q3 |
| E12 | 导出权限限运营专员与主管 | Q4 |
| E13 | 时间筛选必填，口径按创建时间 | 清单项 |

**Q5 被跳过** → 按题面写明的后果，落成 s11 开放问题（记录型，不挡交付）：
"微信登录的覆盖端未决定（待决人：PM）"。

### A9 落位（Locator）

| 主张 | 落到哪 |
|------|--------|
| E1、E3、E13 | 新增 feature 子树 `feature#order-export` |
| E6、E7 | 新增 feature 子树 `feature#login-wechat`（第二件事） |
| E2、E12 | s3 用户与受众 |
| E4 + E9 | s10 假设：量级 1 万–10 万（若超过，改异步） |
| E11 | s7 数据与接口 + s8 安全 |
| E10 | s8 性能 |
| E8 | s10 约束 |
| E5 | 偏好区（**不进正文**） |

### A10 成稿与校验

Writer 按落点写提案，每条挂 `evidence_refs`。
Validator 检查：证据编号都存在；`target` 都在写范围内；没有无编号断言。

结果：通过，但门禁标出两处缺口：

```
⚠ feature#order-export 缺验收标准（必填）
⚠ feature#login-wechat 缺验收标准（必填）
```

**按 3A 的取舍：标出来，但不阻止写入。** 这两条会在下一轮开场批的"遗留阻塞项"里出现。

### A11 草案卡与结果

草案卡里 3 条提案：新增 `feature#order-export` 子树、新增 `feature#login-wechat` 子树、
补充 s3 / s7 / s8 / s10 若干条目。用户全部"要"。

结果：文档 v0.1 生成，变更 block 14 个；s11 多一条开放问题（微信登录覆盖端）。

**这一轮的看点**：一次输入里的三件事在一轮内走完；猜测升格为假设；偏好被隔离；
两个席位问同一件事被合并；超量的第 6 题降级成清单项；跳过的问题落成开放问题；
缺口被标出来但没有把用户卡死。

## 案例 B · 增量加功能，同时撞上旧边界

前提：文档已在 v0.1，s4 的"本期不做"里有 E22：**本版不做定时导出**。

### B1 用户输入（第二轮）

> 运营说还是每天固定时间自动导出比较好，我想用 Redis 做个队列来做这件事。

### B2 切分与定性

| 编号 | 主张 | 标签 | 初归位 |
|------|------|------|--------|
| E14 | 运营要每天固定时间自动导出 | 需求 | s5（**与 s4 冲突**） |
| E15 | 用 Redis 做队列 | **技术方案**（不是需求，先降级为建议） | s9 待定 |
| E16 | 这是运营提出的 | 事实 | s3 |

### B3 开场批

```
卡1 复述理解
   E14 每天固定时间自动导出   [需求] → s5功能
   E15 用 Redis 做队列        [技术方案] → 待定，先问你要它解决什么
   E16 运营提出的             [事实] → s3

卡2 本轮写范围
   建议：s5 功能需求 / s4 范围与边界 / s9 技术方案
   注意：要动 s4，因为你上轮定过"不做定时导出"。

卡3 席位编制
   ☑ 数据规模与性能   定时导出与手动导出共用实现时的量级与并发
   ☑ 技术方案         你提了 Redis，需要确认它解决的是哪个问题
   ☑ 权限与角色       定时任务跑起来后，导出的数据发给谁

卡4 遗留阻塞项
   · 微信登录覆盖端未决定（上一轮 Q5 跳过）
```

### B4 席位发现

**技术方案席**

- F8（矛盾/质疑）：E15 是**方案**，不是需求。先问它要解决什么：不阻塞页面？支撑更大数据量？
  失败可重试？不同答案对应的技术选择完全不同，Redis 只在其中一种里是必要的。
- F9（缺信息）：引入 Redis 等于新增一个需要运维的组件（进程、持久化、监控）。
  本地跑和"要能扛住挂掉"是两种成本。

**数据规模与性能席**

- F10（缺信息）：定时导出与手动导出是否共用同一套筛选与权限？共用则实现会分叉，不共用则两套规则。

**权限与角色席**

- F11（缺信息）：定时导出产出的文件发给谁？还只是放在系统里等人来下？

**Integrator**（代码先做候选召回：E14 的"定时导出"命中 s4 的 E22）

- 归类：F8 判为**矛盾**（与 s4 已确认的非目标冲突）；F9、F10、F11 为缺信息。

### B5 问卷（4 张）

```
▾ s4 范围与边界
  Q6 ⚠ 你上轮定过"不做定时导出"，这轮的"每天定时导出"与它冲突，改哪个？
     A 之间的依据：第 2 轮输入 E14
     B 之间的依据：s4 本期不做 E22
     ○ 改非目标，本版做定时导出
     ○ 维持不做，本需求记入后续
     ○ 暂不决定，记入开放问题

▾ s9 技术方案
  Q7 你要队列是为了解决什么？     [技术方案席]
     ○ 不阻塞页面（导出时还能干别的）
     ○ 支撑更大的数据量
     ○ 失败可重试、不丢任务
     ○ 其他（可写）
  Q8 接受新增一个需要运维的组件（Redis）吗？   [技术方案席]
     ○ 接受，本机跑就行   ○ 接受，但要能扛住重启   ○ 不接受，换方案

▾ s5 功能需求
  Q9 定时导出与手动导出共用一套筛选和权限吗？   [数据规模席]
     ○ 共用   ○ 各自独立   ○ 还没想好
```

### B6 用户作答与回灌

Q6 选**改非目标**；Q7 选"失败可重试、不丢任务"；Q8 选"接受，本机能扛住重启就行"；Q9 选"共用"。

| 编号 | 内容 | 来源 | 类型 |
|------|------|------|------|
| E17 | 本版做定时导出（原非目标撤销） | Q6 | **改判型** |
| E18 | 队列的目标是失败可重试、不丢任务 | Q7 | 补全型 |
| E19 | 接受本机 Redis，需容忍重启 | Q8 | 补全型 |
| E20 | 定时与手动共用筛选与权限 | Q9 | 补全型 |

E17 是改判型：它推翻了 s4 里一条已确认的非目标。系统要做三件事：
① 从 s4 的非目标里移除 E22；② 把 s4 的"本期范围"补一条；③ 在版本记录里写明
"v0.2 撤销了 v0.1 的某条非目标，依据 E17"。

### B7 落位、成稿、校验

| 主张 | 落到哪 |
|------|--------|
| E14、E20 | 新增 feature 子树 `feature#scheduled-export` |
| E17 | s4 范围与边界（删一条非目标、加一条本期范围） |
| E18、E19 | s9 技术决策（`reasons` = 失败可重试；`alternatives` = 不用队列、直接同步） |
| E16 | s3 用户与受众 |
| E19 的另一面 | s7 依赖：新增外部依赖 Redis |

Validator 通过。门禁照旧标出"新 feature 缺验收标准"。

### B8 草案卡与结果

4 条提案：新增 `feature#scheduled-export`、s4 撤销一条非目标并补一条本期范围、
s9 新增一条技术决策（含备选）、s7 新增一条依赖。用户全"要"。

结果：文档 v0.2；版本记录里显式写着"撤销了 v0.1 的非目标，依据 E17"。

**这一轮的看点**：与旧边界冲突时不是静默放开，而是出一张必须二选一的矛盾题；
技术方案先被降级为建议、先问目标，再决定落进 s9；改判型答案触发了对既有内容的修订，
并且这次修订在版本历史里留了痕；新增功能是长出一棵新子树，而不是重写已有内容。

## 两个案例共同验证的三条

1. **一轮绑定一次输入，不绑定一个句子**。案例 A 的 8 条主张、3 件事，共享同一轮三次中断。
2. **席位只出问题，内容来自用户**。两个案例里，所有写进文档的内容都能追到某条输入或某个回答；
   席位的每一条输出都变成了题目、而不是段落。
3. **规范化只重组，不产生新信息**。案例 A 里"运营每天用"被写成用户故事句式（重组），
   但"数据量几万"没有被写成"约 5 万条"（那是提升确定度，必须问）。
