# 记忆层 · PROJECT.md 维护 · 门禁条款设计

> 状态：设计稿 · 2026-09-21 · 待裁决
> 回应四点：每轮独立、PROJECT.md 由记忆层提取、摘要更新的成本、门禁判不了怎么办。

## 一、每轮独立：你是对的，我上一版说错了

我上一版说"会有未完成的问题、需要靠席位继续盯着"，这个说法是错的。你的反驳成立：

**一轮结束就是完整的。** 确认过的内容进正文，没决定的以开放问题形态进 s11，
两条路都有归宿，不存在"半成品悬空"。**文档本身就是跨轮的记忆载体**，
流程层不需要另外背一份，也不需要让某个席位跨轮继续盯。

我原来想保住的东西（"上轮没答的问题别忘了"）确实存在，但它的正确位置不是席位，
而是**开场卡**：

```
开场卡 = ① 理解复述（本轮输入的七种标签）
        + ② 席位提名（按本轮输入匹配）
        + ③ 遗留阻塞项（从 PROJECT.md 直接读，通常 0–3 条）
        + ④ 预期管理（告诉他后面还会被打断两次）
```

第 ③ 项就是答案：**开放问题在文档里是一等公民，不需要靠"某个席位碰巧在场"来兜住它**
——每轮开场直接把它端上桌问你。这比"强制带席位"便宜、可靠，而且不违反"每轮独立"。
（如果一项开放问题连着几轮都被你跳过，它会一直留在 PROJECT.md 的阻塞项里挡交付，
直到你回答或者明确降级为记录型。）

## 二、PROJECT.md 由记忆层提取（单独的智能体）

这个分工是对的，命名上叫 **Memory Curator（记忆整理者）**：

| 项 | 内容 |
|----|------|
| 触发时机 | 每轮结束（草案确认落盘、版本快照生成之后） |
| 输入 | ① 本轮的 `changed_block_ids`（**不是全文档**）② 现有 PROJECT.md ③ 本轮的卡片结论与裁决 |
| 输出 | **结构化的变更指令集**：`{op: add/update/merge/delete, id, text, 理由}` |
| 权限 | `write_document: false`；**也不能直接改 PROJECT.md**，只能提议 |
| 硬约束 | 遵守收录规则：不写功能细节、不写过程记录、每条 ≤2 行、超了就拆或删 |

它有独立的判断标准，跟其他席位不同：**别的席位问"这份文档还缺什么"，
它问"这次运行里有什么教训值得影响以后每一轮"。**

它的输出同样走草案卡——因为 PROJECT.md 写错的代价是**污染以后所有轮次的判断**，
比文档正文写错更严重。所以它的门槛要高，写入要慢。

### 2.2 它不只是追加，它负责维护

你强调的这点很重要：**它要不断核验、检查、合并。** 所以每轮的完整动作是四步，
而不是"往后面加一条"：

| 动作 | 做什么 | 判据 |
|------|--------|------|
| **核验** | 现有每条教训是否仍然成立、是否还适用 | 事件已过去且结论已变成代码约束 → 候选删除 |
| **合并** | 把重复、相近的条目合成一条更抽象的 | 两条讲同一件事 → 保留更抽象的那条 |
| **删除** | 没用的直接清出去 | ① 已变成代码里硬约束的 ② 内容已进正文的 ③ 连续 5 轮未被引用的 |
| **新增** | 本轮沉淀出来的教训 | 必须满足"会影响未来判断" |

关键点：**输出变更指令集，而不是重写全文。** 每条指令带理由，用户在界面上看到的是
diff（新增 2 条、合并 1 组、删除 1 条），而不是一份全新的 100 行文件——否则他不会读。

### 2.3 容量预算：100 行左右

按你的要求，PROJECT.md 保持 **100 行左右（超过 120 行触发强制压缩）**。预算怎么分：

| 区块 | 预算 | 说明 |
|------|------|------|
| 摘要 | 3 行 | 固定 |
| 章节状态表 | 13 行 | 固定（机械生成） |
| 铁律 | ≤10 行 | 只在极少数情况下增加 |
| 教训 | ≤60 行 | 约 15–20 条，每条 ≤2 行 + 来源行 |
| 阻塞项 | ≤10 行 | 未清的开放问题，清掉即删除 |
| 收录规则 | 4 行 | 固定 |

**教训区的 60 行才是真正的战场。** 每轮都可能新增，所以必须持续压缩：

- **抽象化**：把具体事件压成通用原则。三条关于静默失败的教训 → 一条
  "失败必须显式声明，空返回不等于无发现"
- **过期化**：已经写进代码约束里的规则，从教训区删掉（代码已经保证了，不需要再提醒）
- **引用计数**：每条教训记录"最后一次被引用/命中的轮次"，连续 5 轮没被引用 → 候选删除

被删掉的内容不销毁——归档到文档附录的"历史教训"里，需要时可查。

## 三、摘要更新的成本问题（你问得对，逐条答）

你质疑的是："摘要如果每轮都要更新，成本岂不是很高。"

我原来的设计确实有问题——我把它写成"13 章摘要每轮维护"，那等于每轮都要重算 13 章。
修正后的答案是：**不是每轮全量重算，而是只处理变化量；而且变化量是数据库告诉我们的，
不是模型判断的。**（这不叫"按需提取"——按需需要判断，增量不需要，版本快照直接给出答案。）

### 3.1 拆成两半

**机械部分（零模型成本，纯代码算）**

每个章节一行状态，全部可以从 block 树直接算出来：

```
s5 功能需求   | 4 个功能 | 缺：2 个功能无验收标准     | 最后改动 v0.7
s8 非功能需求 | 6 条表态 | 缺：成本约束未答           | 最后改动 v0.7
s3 用户与受众 | 1 个角色 | 缺：次要受众              | 最后改动 v0.2
```

block 数量、缺失字段、最后修改版本——这些是**结构性事实**，代码算，模型别碰。

**语义部分（唯一有成本的地方）**

每章一句"这章讲了什么"。它只在**该章节的 block 集合发生变化**时重算，
而"哪些章节变了"由版本快照的 `changed_block_ids` 机械推导。

### 3.2 成本实算

| 时刻 | 重算量 |
|------|--------|
| 首轮 | 13 章一次（一次性全量） |
| 之后每轮 | **只重算本轮改动的章节**，典型 1–2 章 → 1–2 句 |

也就是说，稳态下一轮的摘要成本是**一两句话**，不是一个全景重写。
而且它和 Memory Curator 的其他工作可以合并成同一次调用。

### 3.3 章节状态表并入 PROJECT.md

不再单独搞"13 章摘要层"这个中间层。状态表直接作为 PROJECT.md 的一节存在，
由 Memory Curator 统一维护。这样：

- 席位必读的东西只有**一份**（PROJECT.md），不是两份
- 状态表和总结论永远同源，不会出现"摘要说这章齐了、PROJECT.md 说还没齐"
- 少一层就少一处会腐坏的地方

## 四、陌生人读者：跑两次（已定）

首次构建时一次 + 交付前一次，总共两次。中间不跑——因为中间轮次的文档本来就还不完整，
让一个空白读者去读半成品，他列出来的困惑大多来自"还没写到"，是噪音。

## 五、门禁判不了的条款：三种处理的利弊

问题引出：门禁里有些条款机器判不了，比如"至少存在一个被**认真考虑过**的备选技术方案"。

### 选项 A：每次都问人（变成卡片）

**利**

- 判据不放水，不会静默通过
- 决定权在人手里，符合"AI 不替人做判断"的原则
- 把隐性标准显性化，用户至少知道有这个维度

**弊**

- 每轮多出几张无法验证的卡，用户会疲劳
- **问人并不比不问更可靠**：疲劳之后用户会一路点"是"，这种"是"没有任何信息量
- 更糟的是，这类问题看起来像"系统在敷衍我"——"你觉得你的备选方案认真吗？"
  这个问题本身就没人能诚实回答
- 一旦用户开始无脑点"是"，**整条门禁的可信度都会被拉低**，包括那些真正机械可判的条款

### 选项 B：降级成提示，不挡交付

**利**

- 零打扰，用户的注意力只花在真问题上
- 门禁保持"全部可机械判定"，所以**门禁变绿这件事本身是可信的**——这是它最大的价值

**弊**

- 这类质量维度长期没人管，会稳定地空洞下去
- 提示会被无视（提示的天花板就是"被忽略"）

### 选项 C（我推荐）：把条款改写成可机械判定的形状

关键洞察：**绝大多数"判不了"的条款，是因为它写成了形容词。**

> "至少存在一个被认真考虑过的备选技术方案"
> ↓ 改写
> "s9 至少存在一条 decision block，且该 block 的 `reasons` 与 `alternatives` 两个字段非空"

改写后它**是**可判定的——存在性、字段非空，代码就能查。"认真"这个词没有任何信息量，
它只是在掩盖"我不知道怎么验"。

再比如：

| 模糊条款 | 改写后（可机械判定） |
|---------|-------------------|
| 目标要清晰 | s2 的每条目标必须带 metric 字段或"可观测现象"字段 |
| 异常处理要考虑周全 | 每个 feature 的 异常与边界 字段至少 2 条 |
| 要有验收标准 | 每个 feature 至少 1 条 acceptance，且每条含"给定—当—则"三段 |
| 备选方案要经过认真考虑 | s9 ≥1 条 decision，且 reasons 与 alternatives 非空 |

**剩下真正改写不掉的**（例如"这件事对用户是不是真的重要"、"这个目标值是不是拍脑袋定的"）——
它们不属于门禁，属于**决策风险**。应该进 s11 风险与开放问题，由人显式登记，
而不是混在门禁里假装能被检查。

### 三者对比

| | A 每次问人 | B 降级提示 | C 改写条款 |
|--|-----------|-----------|-----------|
| 打扰程度 | 高（每轮） | 无 | 无 |
| 门禁可信度 | 被拉低（混入软判据） | 保持 | 保持且可检查 |
| 该维度会不会长期空洞 | 不会，但得到的是假答案 | 会 | 不会（变成可查的字段） |
| 实现成本 | 低 | 低 | 中（要想清楚怎么改写） |

**结论：C 为主，A 只在"改写之后仍然不可判定、且后果严重"的极少数条款上使用，
B 不用**——因为提示等于放弃。

顺带一条流程约束：**新增任何门禁条款前，先问"这条谁来判：代码还是人"。
如果答案是"人的感觉"，那它不该进门禁。** 这条已经写进 PROJECT.md 的教训里。

## 六、已裁决（2026-09-21）

1. **教训区的合并与删除：也要逐条确认。** 即 PROJECT.md 的每一次改动
   （新增 / 更新 / 合并 / 删除）都必须逐条过人的确认，不做批量。理由是 PROJECT.md
   会污染以后每一轮的判断，改错的代价高于确认的成本。
2. **附录里的历史教训：给席位读取权限。** 席位可以检索归档，避免重复犯旧错。
   代价是这部分也要计入读取预算，所以归档条目标题要能自解释。
3. **引用计数：不引入时间阈值**，保持"连续 5 轮未命中即进入删除候选"。
