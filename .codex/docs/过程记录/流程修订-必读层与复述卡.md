## 〇、术语澄清：PROJECT.md 是**文档级**的

PROJECT.md 不是这个仓库自己的上下文文件，而是**产品里的一个结构**：

```
一份产品文档 = blocks 树（13 章骨架 + 内容）
             + PROJECT.md（这份文档的总纲、铁律、教训、阻塞项）
             + 版本快照序列
```

每份文档都有自己的 PROJECT.md，随文档一起存、一起版本化、一起交接。
它的作用是：**任何智能体不必读完这棵树，就能拿到这份文档最浓缩的真相。**

（仓库根目录下那份 `PROJECT.md` 是 ai-pm 这个代码仓库的开发上下文，跟 CLAUDE.md 同类，
同名但不同层，不要混。本设计文档里统一称"文档级 PROJECT.md"。）

## 一、读全还是读局部：你说得对，我那个设计会丢信息

我原来给席位设 `read_scope`（只读它负责的章节）是想省上下文，但你的质疑成立：
**席位只读两章，它凭什么判断这件事和别处没关系？** 数据规模席看不到非功能需求那节，
就可能漏掉已经写好的性能约束，然后重复提问或者给出冲突建议。

修正为三层，从"保证读全"到"按需读细"：

```
第 1 层  文档级 PROJECT.md   必读，全席位。薄（一屏），是这份文档的浓缩真相
第 2 层  章节摘要            必读，全席位。13 章各一行，说明每章当前有什么、缺什么
第 3 层  章节全文            按需。席位默认读自己负责的章节，可以申请扩读
```

- **第 2 层是关键补丁**。13 章摘要（每章一行：有什么、缺什么）成本极低，
  但能让任何席位在**不读全文**的情况下知道"别处已有什么"，从而避免越界提问和重复提问。
- **`read_scope` 从"天花板"改成"默认值"**：席位如果判断需要读别处，可以发起一次
  扩读请求（一次工具调用），扩读被记录在案。默认省上下文，但**不许因为省而漏**。
- 扩读会被记入该席位的运行记录，所以"谁读了什么"是可审计的。
- **例外：guard 类席位不受 `read_scope` 约束**（范围守卫必读 s2 + s4 + 本轮相关章节），
  原因见第四节。

## 二、强制 AI 只能输出规定内容

这条要落成机制，不能落成提示词。四个动作：

**① 输出白名单。** 每类信息包（claims / placement / finding / draft / review）都有固定的
字段集合，多余字段**直接拒绝**（strict 模式），不做"顺便保留"。

**② 无内容必须显式声明。** 席位没有发现时，必须返回 `findings: []` **加一条理由**
（"输入已给出量级与并发上限，无需追问"）。**不允许静默空返回**——这条直接来自
PROJECT.md 里那条真实教训。

**③ 失败就是失败。** 解析失败 → 打回重试一次 → 仍失败 → 该席位本轮标记失败，
整轮 run 进入失败态可重试。不静默降级，不"跳过这个专家继续跑"。

**④ 拒绝的可见性。** 席位被拒绝的输出、被 Validator 拦下的草案，都要在界面上可见
（"数据规模席的输出被拒绝，原因：缺少证据编号"）。用户看得见约束在起作用，
才会相信"AI 不能乱写"不是一句承诺。

## 三、流程开头的理解复述卡

你的提法比我原来的"复述确认"更明确：**把它做成流程的第一步，专门确认七种标签。**

### 3.1 卡片长什么样

```
┌ 理解复述卡 · 共 6 条 ────────────────────────────────┐
│ E1 想给订单列表加个批量导出            [需求] → s5功能   │
│ E2 运营每天都要用                      [事实] → s3用户   │
│ E3 最好能按时间筛选                    [需求] → s5功能   │
│ E4 数据量大概几万吧                    [猜测] → s10假设  ⚠ │
│ E5 我觉得导出 PDF 比较好看             [偏好] → 偏好区   ⚠ │
│ E6 月底前要上                          [约束] → s10     │
│                                                       │
│ 我理解错了吗？标签可以直接改，去处也可以改。               │
│ 确认后我才去找专家，所以这里错了，后面全错。               │
└───────────────────────────────────────────────────┘
```

- 每条一行：编号 + 原文 + 标签（可下拉改）+ 去处（可改）
- 两类必须带警示标记：被判为**猜测**和**偏好**的（因为这两类处理方式最特殊）
- 低置信度的标签也标出来，让用户优先看这几条
- 用户可以：改标签、改去处、删掉一条、补一条

### 3.2 为什么必须放在流程开头，而不是中间

因为**它是所有后续判断的地基**。如果把 E4 那句"数据量大概几万"当事实处理，
后面数据规模席会基于它给出"同步导出即可"的建议，Writer 会把"同步导出"写进主流程，
整份文档的一半都建在一个没验证的估计上。在地基处纠正一次，胜过在下游纠正十次。

### 3.3 和席位提名合并成一张开场卡

原来的设计里，流程开头有两次打断：先确认理解，再确认席位。这两件事都基于同一份切分结果，
分开问纯属浪费。合并成**一张开场卡**：

```
┌ 开场卡 ────────────────────────────────────────────┐
│ ① 我理解你要做这 6 件事（见上，可改）                    │
│ ② 我建议请这 4 位专家：                                │
│    ☑ 数据规模与性能  — 你提到"批量导出"，他会问最大行数与并发 │
│    ☑ 权限与角色     — 导出涉及谁能看谁能改                 │
│    ☑ 范围守卫       — 盯"本期不做"有没有被打架              │
│    ☑ 陌生人读者     — 只读文档，找出它看不懂的地方           │
│ ③ 开跑后中途还会再问你两批问题（补充信息 + 矛盾裁决）        │
└───────────────────────────────────────────────────┘
```

一次打断解决三件事：**理解确认、编制确认、预期管理**（告诉他后面还会被打断几次）。

## 四、跨轮关系：你说的对，但要精确一点

你的原话是"每轮之间应该没有瓜葛了吧，都在第一轮落地了，即便有问题，也通过卡片提问了"。

**同意一半，另一半要精确化：**

### 4.1 去掉的部分（你对）

轮与轮之间**不再有挂起的提问**。撤掉此前设计里的两个机制：

- 撤掉"同一问题跨轮重问最多 2 次"
- 撤掉"提问-回答最多 3 轮后强制收敛"的跨轮循环

理由正如你说的：一轮里该问的都问完了，没答的已经在卡片里落成了开放问题。
跨轮追着问只会让用户觉得被纠缠，而且第一轮的上下文早凉了。

一轮内部仍然允许补问一次（回答可能引出新矛盾），但这是**同一轮内**的，不跨轮。

### 4.2 我加的那道"跨轮一致性比对"是多余的，撤掉

你的反驳成立：**席位本来就要读文档现状，有矛盾它自然会提出来，不需要额外加一道关卡。**
我把它设计成一个独立工序，等于假设"席位不看上下文"，这跟我们刚刚定下的必读层直接矛盾。

撤掉独立工序，改为一致性由两处**天然产生**：

- **席位发现阶段**：每个席位读的是"本轮输入 + 文档级 PROJECT.md + 13 章摘要 + 自己的章节
  （可扩读）"，所以它是在**已知现状**的条件下做发现。发现"这条和已确认内容打架"就是
  它的本职工作，不需要再教它一次。
- **代码层机械兜底**：张力检测除了比对席位之间的分歧，再比对新草案与既有结构——
  例如新增 feature 的名字/语义命中 s4"本期不做"清单，直接标记为冲突候选。
  这一层不靠模型判断，只做机械匹配，用来兜住"席位全都漏了"的情况。

唯一需要保留的**保障**是前面第一节那条例外：**范围守卫常驻，且不受 `read_scope` 限制。**
因为"边界被打架"这件事必须有至少一个始终在场的角色盯着——它读 s2 + s4 + 本轮相关章节。
这不是一道工序，是一个席位的常驻职责。

---

### 4.3 每轮可以是长任务，这改变了什么

你说"每轮对话都可以是长任务"——这条要写进设计，它带来三个要求：

1. **一轮内的进度必须可见。** 长任务跑三五分钟是常态，用户需要看到"数据规模席已完成 /
   权限席在跑 / 陌生人读者待启动"，而不是一个转圈图标。
2. **必须可中断可恢复。** 关掉页面、第二天再回来，未完成的 run 要能续跑（checkpointer
   按 thread 恢复），不能从头再来。
3. **席位之间不该串行等待。** 独立发现阶段并行跑，只有整合（Integrator）阶段需要汇合。
   一轮的时间下限由此变成"最慢的那个席位的耗时"，而不是五个席位之和。

## 五、修订后的流程

```
每轮（轮与轮之间没有挂起的提问）

ingest
 → split + 定性（七种标签）
 → 开场卡（理解复述 + 席位提名 + 预期管理）        ← interrupt 1
 → 独立发现（席位并行；必读文档级 PROJECT.md + 13 章摘要，
             读自己的章节，可申请扩读；范围守卫不受限）
 → 张力检测（代码：席位分歧 + 新草案 vs 既有结构）→ 定点辩论（仅冲突对）
 → 卡片组（补充信息 + 矛盾裁决，带候选答案）        ← interrupt 2
 → 回答 → 变成新证据编号 → 本轮内增量检查（≤1 次补问）
 → 草案（席位产出，带 evidence_refs）→ Validator 机械校验 → 失配则打回重做
 → 草案卡                                          ← interrupt 3
 → 确认 → 图外写入 → 版本快照 → 门禁报告
 → 提议文档级 PROJECT.md 的新增教训（草案卡，同样要人确认）
```

三轮中断，不多不少：**开场卡 / 问题卡组 / 草案卡**。

一轮的时间由**最慢的席位**决定，而不是席位之和——独立发现阶段并行跑。
