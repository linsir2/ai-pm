## 第一部分 · 注册层

### 1.1 为什么值得有注册层（而不是写死在代码里）

你提注册层的直觉是对的，但理由不只是"可扩展"。真正的理由是：

**注册表是权限的载体。** 前面定下的硬约束——"AI 不能写文档"——如果靠提示词实现，
它随时可能失效；如果靠注册表实现，它就是一个字段：席位注册项里 `write_document: false`，
而写入接口只认"确认端点"这一个调用方。**席位在物理上没有写的路径，不是它答应不写。**

第二条理由：注册表让席位可以被**度量**。哪个席位问的问题你总是跳过、哪个席位你总是采纳，
这就是席位权重的来源（也就是最小可用的记忆层）。

### 1.2 三类注册项

**① 席位（agent）**

```jsonc
{
  "id": "seat.data_scale",
  "name": "数据规模与性能",
  "category": "domain",              // domain | guard | quality | structure
  "trigger": {                        // 提名器就是拿这个字段做匹配
    "any_of": ["涉及批量数据处理", "涉及导出/导入", "涉及报表", "提到数据量或并发"]
  },
  "owns_sections": ["s5", "s8"],      // 他的发现必须落在这些章节
  "read_scope": ["s4", "s5", "s7"],   // 他能读哪些章节（默认不是全文档）
  "emits": ["finding"],               // 他能产出哪类信息包
  "must_ask": ["单次最大行数", "峰值并发", "超时容忍"],
  "silence_when": ["输入中已明确给出量级与并发上限"],
  "write_document": false,            // 硬约束：所有席位一律 false
  "network": false,
  "cost_hint": { "questions": "2-4", "model_tier": "standard" },
  "source": "ai_nominated"            // ai_nominated | user_added
}
```

**② 工具（tool）**

```jsonc
{
  "id": "tool.evidence_ledger",
  "name": "证据账本",
  "category": "tool",
  "effects": "read_write",            // readonly | read_write | external
  "requires_confirmation": false,      // 有副作用的工具必须为 true
  "callable_by": ["structure", "guard"]
}
```

**③ 校验器（structure / guard）**

纯代码，同样登记在注册表里，但执行者是代码不是模型：schema 校验、证据引用校验、门禁校验、
张力检测。登记的目的是让它们在界面上可见——用户能看见"这次是谁在拦我"。

### 1.3 权限模型（单用户系统里权限意味着什么）

这里没有多租户、没有角色。权限只有四个维度，而且都是**为了约束 AI，不是为了约束人**：

| 维度 | 作用 | 默认值 |
|------|------|--------|
| `read_scope` | 席位能读哪些章节 | 只读它负责的章节 + 它依赖的上游章节 |
| `emits` | 能产出哪类信息包 | 只能是 finding（发现），不能是 draft（草案） |
| `write_document` | 能不能直接改文档 | **全部 false** |
| `network` / `requires_confirmation` | 能不能外联、要不要人点头 | 一律收紧 |

`read_scope` 收紧有个副作用收益：**席位看不到全部文档，就不会越界提意见**。
范围守卫不需要读第五章的验收标准细节，它只需要读 s2 和 s4。

## 第二部分 · 用户不知道要选哪些智能体，怎么办

### 2.1 先把这个"问题"拆开

你说的困境是真的：让用户在 200 个 agent 里挑，等于没给他选择。但这里有个更根本的判断：

> **用户不知道要选哪些智能体，这不是产品缺陷，这是产品的机会。**

如果用户知道该请哪些专家、该问哪些问题，他就不需要这个产品了——他自己就是那份文档。
所以正确的问法不是"怎么让用户选对"，而是**怎么让用户不需要选**。

### 2.2 四条机制

**① 提名器把"选人"变成"匹配"（默认路径）**

注册表里每个席位带 `trigger` 字段。编排层读完输入做的是**关键词 + 语义匹配**：
输入里出现"批量导出"，命中 `seat.data_scale` 的触发条件；出现"月底上线"，
命中 `seat.scope_guard`。产出的是**提名表**，不是菜单。

用户看到的是**理由**，不是选项：

> 我建议请这四位。其中**数据规模**席是因为你提到"批量导出"——他会问单次最大行数和并发，
> 因为 1 万行可以同步导出、10 万行必须走异步任务。要不要去掉他？

**② 默认全选，用户做减法不做加法**

认知成本在这里极不对称：让用户"删掉不需要的"几乎零成本；让他"从列表里挑出需要的"成本极高。
所以提名表默认**全选**，用户的动作是否决。

**③ 用户想加人时，按类别浏览，每个候选一行说清"他会问你什么"**

不列 agent 的名字（"数据规模专家"这种名字对用户没有信息量），列**他会问你的问题**：

```
领域类
  数据规模与性能   会问：单次最大行数？峰值并发？超时怎么办？
  权限与角色       会问：谁能看？谁能改？谁审批？
  合规与数据外流   会问：数据里有客户名或金额吗？要给外部看吗？
守卫类
  范围守卫         会问：这条和你上次说不做的那条冲突，改哪个？
  证据守卫         机械检查每条断言有没有来源（不问你）
质量类
  陌生人读者       会问：这份文档里我看不懂这三处，是你漏了还是理解不同？
```

**④ 用户说不出自己是什么领域时，用三个是非题做领域雷达**

有些 PM 会说"我也说不清这算什么领域"。这时候不要让他选，让他答三个是非题：

1. 这个改动会碰**外部数据**吗（别人的数据、客户名单、钱）？
2. 这个改动会碰**权限**吗（谁能看、谁能改、谁审批）？
3. 有**人在等结果**吗（运营每天要用、客户投诉了、老板要报表）？

三个答案的组合能覆盖绝大多数产品的风险面，直接映射出该请哪几类席位。
**问领域特征，而不是问领域名称**——因为用户答得出前者，答不出后者。

### 2.3 谁选的这件事必须被记录

每个席位标记 `source: ai_nominated | user_added`，有两个用处：

- 出卡时标注"这条是 AI 建议加的席位提出来的"，用户据此判断该不该重视
- 用户总是跳过的席位降权，总是采纳的席位升权——这是最小可用的记忆层

## 第三部分 · 结构化用户输入（核心问题）

### 3.1 先把两件事分开

你说的"结构化"，可能指两种完全不同的东西：

- **输入的结构化**：给用户一个表单或模板，让他按格式填 —— **这个方向是错的**。PM 脑子里
  有想法但没整理过，你给他一张表，他填出来照样是糊的，而且他会在第二步就放弃使用。
- **输入被结构化**：用户随便写，系统把它**转化**成结构 —— **这个方向是对的**。

结论：**入口永远不设限，出口必须严格。** 该被规范的从来不是用户的输入格式，
是**输入到信息的转化率**。

于是"什么样才算规范"有了答案：**一条信息只有通过了下面六条判据，它才算规范。**

### 3.2 六条合格判据（尽量可机械判定）

注意：判据是对**每一条原子主张**检查的，不是对整段话。

| # | 判据 | 不合格的样子 | 合格的样子 | 谁能判 |
|---|------|------------|-----------|--------|
| 1 | 可归属 | "要做得更好用" | 能落到 13 章某一节；落不下的进开放问题 | 代码 |
| 2 | 可判定 | "体验要流畅" | "导出 5 万行需在 60 秒内完成" | 半机械 + 席位 |
| 3 | 原子性 | "支持按时间筛选并导出 Excel 并邮件通知" | 拆成三条独立主张 | 半机械 |
| 4 | 有出处 | 没有编号的转述 | 带证据编号，可跳回原话 | 代码 |
| 5 | 前提外显 | "数据量不大，同步导就行" | 拆出假设：量级 < 1 万；若超了需改异步 | 半机械 + 席位 |
| 6 | 决定有主 | "不做定时导出"（没人认领） | 记录谁在什么时候定的；无主则标为暂定 | 代码 |

"半机械"的意思是：代码能查出**可疑**（句子含"并/和/以及"、出现"大概/应该/差不多"、
没有量化词），但判得准不准要交给席位。**代码负责发现可疑，席位负责判到底。**

### 3.3 四步转化

```
自由文本
 └─ ① 切分：一句话拆成 N 条原子主张，逐条编号 E1、E2……
     └─ ② 定性：给每条主张打标签（见 3.4，最关键的一步）
         └─ ③ 归位 + 补全：映射到章节字段；缺的字段进缺口清单
             └─ ④ 复述确认：产出一个"可被反驳的版本"给用户挑错
```

第 ④ 步要说清楚它为什么不是提问：**提问要求用户从零组织语言；复述只要求他挑错。**
后者的认知成本低一个数量级，而挖信息的效率高得多——因为人纠正别人的错误，比凭空陈述容易。

### 3.4 定性：七种标签（这一步决定整份文档的确定性）

用户的话里混着七种完全不同的东西。**不把它们分开，文档就一定不可信。**

| 标签 | 例子 | 去处 | 处理规则 |
|------|------|------|---------|
| **事实** | "运营每天都要用" | s1 / s3 | 必须有出处，并标注是"用户陈述"而非"已验证" |
| **需求** | "要能按时间筛选" | s5 功能需求 | 缺验收标准时出卡 |
| **目标** | "确保考虑到了方方面面" | s2 目标与非目标 | 必须逼出可衡量的判据，否则只是愿望 |
| **约束** | "目标是单用户"、"用 python" | s10 | 直接进，不必问 |
| **偏好** | "我觉得导出 PDF 好看" | **不进正文**，单独存偏好区 | 只在多个方案都可行时用来打破平局 |
| **猜测** | "数据量大概几万吧" | s10 假设 | **强制**转成假设 + "若不对会怎样" + 一条验证方式 |
| **决定** | "不做定时导出" | s4 / s11 | 必须记录决策者与时间；无主则标为暂定 |

这七条里，最有价值的是**偏好**和**猜测**这两类：

**偏好混进需求** → 工程师会去做一个"你觉得好看"但没人需要的东西，而且它会被写进验收标准。
**猜测混进事实** → 整份文档的确定性从这一行开始崩塌，因为后面所有的设计判断都建立在
"数据量大概几万"这个没验证的估计上。

所以系统对这两类必须硬性处理：**偏好隔离，猜测升格为假设。** 这是我认为"啥样子才算规范"
最实际的答案——不是格式规范，是**性质分离**。

### 3.5 同一句话的两种输入（对照）

**散的样子**（用户真实会写的）：

> 想给订单列表加个批量导出，运营每天都要用，最好能按时间筛选，数据量大概几万吧，
> 我觉得导出 PDF 比较好看，月底前要上。

系统转化后：

| 编号 | 原子主张 | 定性 | 去处 | 缺什么 |
|------|---------|------|------|--------|
| E1 | 订单列表加批量导出 | 需求 | s5 | 验收标准、异常与边界 |
| E2 | 运营每天都要用 | 事实 | s3 | 角色只有一个人，缺次要受众 |
| E3 | 能按时间筛选 | 需求 | s5 | 时间范围是必填还是可选 |
| E4 | 数据量大概几万 | **猜测** → 假设 | s10 | 验证方式；若超量要改异步 |
| E5 | 导出 PDF 比较好看 | **偏好** | 偏好区 | —（不进正文） |
| E6 | 月底前要上 | 约束 | s10 | —（直接进） |

**规范的样子**（转化后给用户看的复述）：

> 我理解你要做的是：给订单列表加批量导出（E1），运营每天用（E2），支持按时间筛选（E3），
> 月底前上线（E6）。
> 有两条我没有写进正文：**导出 PDF 是你的偏好**（E5），我记下来了，如果 CSV 和 PDF 都可行
> 我会优先 PDF；**数据量几万是你的猜测**（E4），我不能把它当事实——它决定同步导出还是异步任务，
> 差一个数量级就是两套实现，所以我把它写成了一条待验证的假设，并会问你一句：这个量级是怎么估的。
> 另外缺三样，我已经列成卡片：导出量级（问题 1）、时间范围是否必填（问题 2）、**导出失败时
> 你希望运营看到什么**（问题 3）。

这就是"规范"的成品形态：**每条信息有编号、有性质、有去处，缺口被明确列出来而不是被 AI 补上。**

### 3.6 输入成熟度 L0–L4

为了让用户知道自己离"能开发"还差多远，给一个分级（显示在输入框旁边）：

| 级别 | 名称 | 判据 |
|------|------|------|
| **L0** | 散话 | 原始倾倒，未切分。**系统永远接受 L0** |
| **L1** | 可切分 | 能拆成原子主张，每条有编号 |
| **L2** | 可归位 | 每条都能落到章节（或明确落到开放问题） |
| **L3** | 可判定 | 需求类主张都带可检验的判据 |
| **L4** | 可交付 | 门禁 12 条全绿（机器判的部分） |

关键设计：**入口永远接受 L0，但交付必须到 L4。** 中间每一级跃迁都对应一个明确的动作：
L0→L1 是切分，L1→L2 是归位，L2→L3 是逼问，L3→L4 是门禁收口。
这四级同时也就是"当前还差什么"的进度提示。

注意 L 级别和"文档完成度百分比"不是一回事：L 级别说的是**输入质量**，
完成度说的是**文档填满程度**。用户可能输入很规范（L3）但文档只填了 40%。

## 第四部分 · 三块怎么咬合

```
用户自由输入（L0）
   ↓ 注册表提供候选能力（席位 / 工具 / 校验器）
提名器按 trigger 匹配 → 提名表（默认全选，用户做减法）
   ↓ 席位冻结为本轮编制
各席位独立发现（受 read_scope 约束，均无 write_document 权限）
   ↓ 代码做张力检测
定点辩论（仅冲突对）→ 裁决卡
   ↓
卡片组（阻塞卡 + 清单项，带候选答案）→ 用户回答 → 新证据编号
   ↓ 席位出草案（draft 包，带 evidence_refs）
Validator 机械校验（schema / 证据 / 门禁可判项）
   ↓ 不通过 → 打回席位或降级成卡
草案卡 → 用户确认 → 图外写入 → 版本快照
   ↓
状态判定：L1→L2→L3→L4，未通过项进下一轮卡片
```

## 第五部分 · 待裁决

1. **席位权重**要不要 v1 就做？不做的话，用户跳过的席位下一轮还会照问（体验差一点，
   但不影响链路）。
2. **偏好区**要不要独立成文档的一部分？我倾向独立：它是给你的偏好存档，
   不应该污染交给工程师的正文，但也不能丢。
3. **L 级别**要不要显示给用户？显示了有"打游戏通关"的推进感，但也可能让人把注意力
   从"文档写好了没"转移到"分数刷够没"。
