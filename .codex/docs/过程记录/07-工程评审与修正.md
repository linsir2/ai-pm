## 一、范围挑战（Step 0）

把主闭环摊开看，它其实塞了两类东西：

**骨架**（直线、可恢复、可判定）：输入 → 读文档 → 复述 → 落位成稿 → 确认 → 写入 → 版本

**质量增强**（可分支、可失败、可以后加）：席位并行发现 → 整合 → 补充问卷

我原来把两类画成一条线，于是增强环节的失败处理、终止条件、读取范围全都污染了骨架。
**先跑通骨架再加增强**，是这一版最该做的范围收敛。

## 二、问题清单

### 结构性（不改就没法实现）

**1 · 没有写范围，等于让模型决定"写哪儿"**
影响：`02` 的时序里，提案的 target 由第 10 步 Writer 直接给出；`05` 的 Validator 只校验
"target 在 s5 内"，没有任何东西限制它只能写用户同意改的地方。文档明明有 13 章，
模型可以往任何一章塞内容，而用户只在最后看到结果。
**这是"AI 不能直接改文档"的旁路**：它没直接改，但它替你决定改哪里。
- 1A 加最小 Scope：开场批里让用户圈"本轮改哪几章"（默认推荐值），写入强制校验在范围内。
- 1B 不加，靠草案卡兜底（用户看到每条落点再决定要/不要）。
- 1C 折中：不设选择器，但草案卡必须逐条显示落点，且落点在 s5 之外时标红。

**2 · 缺"落位"环节，Writer 一个人干了两件事**
影响：main 的设计里，"说什么"（M8 共识生成）与"怎么说成符合文档结构的话"（M28 成稿器）
是两个模块。我这里把它们合并进 Writer，于是没有任何一步负责回答：
这条主张是新增一个 feature 子树，还是改某个字段？改哪个 block？
结果就是模型在黑箱里决定文档结构，而文档结构是这个产品最硬的资产。
- 2A 拆出 Locator（可单测：主张 + 骨架 → 落点），模型只在规则判不了时介入。
- 2B Writer 兼任，但必须显式输出落点理由，供用户判断。
- 2C 不改，接受"结构由模型决定"。

**3 · 终止条件是掩盖，不是解决**
影响：我写了"最多两轮问卷，之后的问题降级为开放问题"。但降级之后没有任何东西阻止
带空洞的文档被确认：草案卡照常出现，用户可以照常点"要"，于是文档里留下一条
没有验收标准的功能——而门禁被我排到了"以后"。
**v1 因此没有"什么算写完了"的判据。**
- 3A v1 加最小门禁（只查必填字段非空与验收标准存在），不通过就在草案卡上标出来。
- 3B 不设门禁，但草案卡上写明"这条依赖 Q7（未答）"，把判断交回用户。
- 3C 都不做，接受空洞（不可接受，仅列出以防万一）。

### 数据语义

**4 · 证据账本只会增，没有修订与作废语义**
影响：用户改标签（开场卡）、用户答"改判型"答案，都会让旧证据失效。
我只写了"编号永不复用"，没写"旧编号怎么办"。结果是：要么就地改标签（丢历史，
追溯链断裂），要么新旧并存（同一件事两条互相矛盾的证据，谁都不知道该信哪条）。
- 4A 账本只增，修订 = 新编号 + `supersedes` 指向旧编号；读取时只认最新未作废的。
- 4B 就地改标签 + 记一条版本变更（简单，但丢"当时是怎么理解的"）。
- 4C 整本账本版本化（重）。

**5 · Integrator 的"降级为清单项"没有落地对象**
影响：问卷那批卡最多 5 张，超出的问题降级成"清单项"——但清单项是什么数据对象、
怎么确认、要不要写进文档，全都没定义。这条路径目前是悬空的。
- 5A 定义"清单项"= 只读列表，随问卷一起展示，可批量接受（生成证据）。
- 5B 取消降级，超出就分批出第二批问卷。
- 5C 直接丢弃（不可接受）。

**6 · 统一入口缺执行者**
影响："答案走统一入口"意思是答案也要切分定性。但用户答的是选择题（"选 C"），
从"选 C"到"一条主张"之间需要语义映射（C 的含义可能是"暂不决定，记入开放问题"）。
我的流程里没有任何角色承担这个映射，Analyzer 直接处理自然语言时会丢结构。
- 6A 由 Analyzer 承担映射，规则写在题面上（每个选项自带"选它意味着什么"）。
- 6B 由 Integrator 在出题时预先生成映射（选题 → 主张模板），Analyzer 只做润色。
- 6C 让 Writer 直接消费选项，不做主张化。

### 状态与恢复

**7 · 相位机不闭合，失败重试与恢复点都没定义**
影响：`04` 的 phase 枚举里没有"答案轮"的等待态；`02` 说"关掉页面回来继续"、
"失败可重试"，但没说从哪继续。实际实现时只能整轮重跑，用户会重答已经答过的题。
- 7A 相位 = 等待点（awaiting_opening / awaiting_form / awaiting_confirm），
  另存 `last_completed_step`，重试与恢复都从那个点续跑。
- 7B 只存一个"最后完成的步骤 id"，相位由它推导（更省，但读起来绕）。
- 7C 事件溯源重放（重）。

**8 · 席位"空返回"的校验者没定**
影响：我写了"空返回必须显式声明 + 理由"，但没说谁来验——如果由模型自己保证，
这条约束等于没有。真实风险是：席位因为怕被罚，随便写个"无进一步问题"糊过去。
- 8A 代码强制：席位输出必须有 `findings` 与 `basis` 两个字段，`findings` 为空时
  `basis` 必填且长度有下限；不合规即判失败。
- 8B 由 Integrator 复核席位是否偷懒。
- 8C 不处理。

**9 · 没有预算与裁剪**
影响：一轮要调模型 N 次（Analyzer 1 + 席位 N + Integrator 1 + Writer 1，加可能的补问）。
文档长起来、席位数一多，成本不可控，而 v1 没有任何裁剪机制。
- 9A v1 只做粗粒度预算：席位数量上限 + 上下文按章节截断，超限即失败可重试。
- 9B 完整做（借 main 的 M13/M24 思路：谁决定带什么 + 谁决定带多少）。
- 9C 不管，先跑通。

### 产品一致性

**10 · v1 里用户其实没有任何改内容的途径**
影响：开场卡只能改标签与去处，草案卡只有"要/不要"，文档只读。三处叠加的结果是
**用户只能接受或拒绝，不能修改**。这与"用户可手改 block content"这条需求直接冲突
（我把它排到了以后）。
- 10A v1 开文档手改（一次保存 = 一版）；卡片保持"要/不要"。
- 10B 草案卡允许"改文案再要"（要回答"卡片改的和文档改的谁优先"）。
- 10C 维持现状，明确承认 v1 只能通过"再说一轮"修正。

### 不在范围内（NOT in scope）

| 项 | 为什么不做 |

## 四、修正后的流程

```
一轮（Round）

① 收集        输入 + 读文档（章节状态表 + 本轮相关章节）
                        ↓
② 切分定性    主张清单 E1..En（账本只增）
                        ↓
③ 开场批       最多 5 张卡                                  ← 中断 1
                卡1 复述理解（标签/去处可改）
                卡2 本轮写范围（改哪几章，默认推荐）
                卡3 席位编制（默认全选，可删）
                卡4 遗留阻塞项（从上一轮开放问题来）
                        ↓
④ 席位并行发现 → 候选（代码只做字面筛选）
     → Integrator 整合（归一化 / 合并去重 / 归类 / 降级成清单项）
     → 问卷（无题则跳过，直接进 ⑤）                          ← 中断 2
                        ↓
⑤ 作答与回灌   答案按选项自带的含义映射成主张 → 新证据（可 supersedes）
     未答项 → 开放问题；命中必填字段 → 标阻塞
     （允许一次回环：⑤ 之后可再出一次问卷，超出的全部显式化）
                        ↓
⑥ 落位         Locator：每条主张 → 章节 / block / 是否新增 feature 子树
⑦ 成稿         Writer：按落点写提案（内容 + 依据 E 编号）
⑧ 校验         Validator：证据存在？字段合法？落点在写范围内？必填项齐？
                不通过 → 回 ⑦（一次）；仍不过 → 降级成问人的卡
                        ↓
⑨ 草案批       1 张卡（提案数组，逐条 [要][不要]）
                每条标注：落点 + 依据编号 + 是否依赖未答问题                ← 中断 3
                        ↓
⑩ 确认写入     事务写入 → 版本快照 → doc.changed
```

### 相对旧流程的六处改动

| # | 改动 | 修正了哪个问题 |
|---|------|---------------|
| 1 | 开场批加入**写范围卡**，写入被强制在范围内 | 问题 1 |
| 2 | 拆出 **Locator**（落位）与 Writer（成稿） | 问题 2 |
| 3 | v1 加**最小门禁**：必填字段与验收标准是否为空，结果标在草案卡上 | 问题 3 |
| 4 | 账本**只增 + supersedes**，读取只认最新未作废 | 问题 4 |
| 5 | 定义**清单项**为只读列表，可批量接受 | 问题 5 |
| 6 | 相位改为**等待点驱动** + `last_completed_step`，重试与恢复从该点续跑 | 问题 7 |

### 相位与恢复

```
collecting → awaiting_opening → discovering → awaiting_form
   → applying → drafting → awaiting_confirm → writing → done
                                    ↘ failed(可重试，从 last_completed_step 续)
```

run 表存两样东西：`phase`（读给人看）与 `last_completed_step`（读给机器用）。
恢复 = 从 `last_completed_step` 的下一步开始，已冻结的卡片组不重问。

## 五、失败模式（Critical gap = 无测试 + 无处理 + 静默）

| 失败模式 | 有测试口径？ | 有处理？ | 用户看得见？ | 判定 |
|---------|------------|---------|------------|------|
| 席位返回不可解析 | 无 | 整轮失败可重试 | 是 | 需补测试 |
| 席位空返回且理由敷衍 | 无 | 代码强制 basis 字段 | 否 | **关键缺口** |
| 用户答完问卷，答案映射错主张 | 无 | 无 | 否 | **关键缺口** |
| Locator 把内容落错章节 | 无 | 草案卡显示落点 | 是（靠人看） | 需补规则测试 |
| 写入时文档已被改动（将来有手改） | 无 | 版本冲突检测（v1 无手改则不触发） | 是 | 记入待定 |
| 模型调用超预算 | 无 | v1 无预算机制 | 否 | **关键缺口** |
| 服务重启在写入事务中间 | 无 | 事务要么全生效要么全不生效 | 是 | 需补测试 |

## 六、完成摘要

- 范围挑战：**建议把席位/整合降为第二层**，先跑通"输入→复述→落位成稿→确认→写入"直线
- 架构评审：10 个问题（结构性 3 个）
- 数据语义：3 个问题
- 状态与恢复：3 个问题
- 产品一致性：1 个问题
- 不在范围内：已写（6 项）
- 已经存在：已写（6 项，来自 main 分支）
- 关键缺口：3 个（席位空返回校验、答案映射、预算）
- 并行机会：前端 / 后端领域层 / 编排层 三条 lane 可并行（详见下节）
- 未决决策：问题 1、2、3、10 需要人拍板

## 七、实现并行机会（三条 lane）

| Lane | 内容 | 依赖 |
|------|------|------|
| A | 领域层：block 树、schema、证据账本、版本、Validator | 无 |
| B | 编排层：Analyzer / 席位 / Integrator / Locator / Writer | A 的接口 |
| C | API + 前端：输入区 / 文档区 / 卡片区 + SSE | B 的接口 |

A 与 B 的接口（几个函数签名）先定，然后 A、B、C 可以并行开工。
