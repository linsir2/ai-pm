## 0. 这份文档解决什么

> **两份文档的分工**：本文件是**契约的唯一真相源**——每个契约有哪些字段、字段干什么、谁写谁读、有什么不变量，只在这里写一次。`PRD.md` 回答"做什么、为什么这么做"，不重复任何字段级定义。两份冲突时以本文件为准。
>
> **工程与实现**（包结构、守卫、依赖怎么强制）在 `ARCHITECTURE.md`；**裁决背景**在 `DECISIONS.md`。

解耦分三层：**模块 → 契约 → 数据流**。模块内部怎么实现（用什么框架、串行还是并行、prompt 怎么写）全部自由。跨模块传的东西不能自由变——那是契约。

**一条纪律**：每个字段都必须能说出它的消费者（谁读它、在哪一步用到）。说不出的一律删掉。不为"将来可能需要"预留字段。

**一条约定**：给契约加字段是兼容的，下游不认识就忽略；改字段含义、删字段是不兼容的，要过一遍所有消费者。

### 0.1 契约分三层，只定前两层

| 类型 | 是什么 | 例子 | 什么时候定 |
|---|---|---|---|
| **层间契约（宏观）** | 一个层交给另一个层的东西 | Scope / 文档 / 版本 / 卡片 / 事件 | **现在定** |
| **编排层内部通用语（中观）** | agent 与 agent 之间传什么 | 信息包 / 讨论轮 / 思路候选 | **也要现在定** |
| **模块内部（微观）** | 每个 agent 的 prompt、DAG 怎么画、缓存策略、用什么框架 | — | 写代码时再定 |

中观这层容易被漏掉：它不对外，但它**跨 agent**。不固定形态，M8 就汇总不了，M28 就落不了位。所以它跟层间契约一样必须先定死。

## 1. 系统里只有两个入口

**主闭环——一场长任务。** 不是"一问一答就出结果"，而是一个可以持续很久的过程：

用户输入 → **M13 组装上下文** → 系统带着上下文复述理解 → 用户确认或纠正 → 系统工作（讨论、查资料、生成、完善）→ **过程中发现缺信息或有冲突，就冒出一组卡片等用户裁决** → 用户裁决完，继续完善 → 反复直到没有问题了 → **最后出一张填充卡确认** → 写入文档。

> 注意顺序：**先组装上下文，再复述理解**。不带上下文复述就是抄一遍用户原话，没有价值。复述里必须包含只有读了文档才知道的信息。

**卡片组是中途的裁决机制，不是输出的终点。** 只在"卡住了"的时候出现。填充卡是收尾，最后才来。

**讨论区**：用户输入 → 角色轮流发言（每个角色各说一次，界面展示每个角色想完之后的最终输出）→ 一轮结束，出现「整理成提案」按钮 → 整理成思路候选 → 用户勾选 → 带进主闭环当输入。

**唯一存在的按钮是讨论区那个。** 文档侧没有"补空白""补这块"之类自动触发的按钮；一切生成都由用户输入触发。

**通信层为什么存在**——这里有个容易搞混的边界：

- **智能体之间**怎么调度、谁在什么时候读写共享状态 = **编排层内部的事**，不对外暴露。
- **层与层之间**的流转 = 必须有通道，否则这么多层没法协同运转。

所以通信层提供两个机制：**黑板**（共享状态放在哪）和**事件流**（状态变了怎么通知）。黑板本身不需要新契约——它承载的都是已有契约的对象（记忆、结论、卡片组）。编排层怎么用黑板，是它自己的设计。

## 3. 契约明细

每个字段都标了：**作用**、**谁写**、**谁读（在哪一步用到）**。

### C1 Scope（范围）

**范围的职责只有一件：改哪儿。** 特调（谁来改）已经去掉——角色选择归讨论区。

**读范围固定是全文**，不做推导、不占字段。文档短，全带上最省事也最不容易错。

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `selected_fields` | **写范围**：用户在目录树上选的 schema 字段 | 用户 | M20 强制只允许写这些字段；界面高亮 |
| `base_versions` | 这一轮**开始读文档时**全部 block 的版本快照（`block_id → version`）。读范围固定是全文，快照就取全文 | 开始生成时 | M20 提交时比对**要写入的那些 block**，对不上就先问用户 |

**怎么选**

- 在**目录树上选**，粒度是 **schema 字段**，不能选到细 block
- 允许多选
- **每轮重新选**：每次用户输入都要带着选区。轮内的循环（出卡 → 裁决 → 继续完善）沿用同一份选区，不重选
- **什么都没选**：正常走主闭环，不限制写范围；由 M28 在最后整合时推导落位，产出提案数组。保护只剩卡片确认

**规则**

- 写范围是"**允许改**"不是"**必须改**"——圈了 3 个字段只改了 1 个，没问题
- **AI 不能写选区外的字段**。如果发现别处有问题（比如选的是功能清单，但目标本身写错了），在卡片里提出来问用户要不要一起改
- 目标 block 在生成期间被改或被删 → 提交时版本对不上 → 出一张卡问用户，不静默覆盖

> **为什么快照取全文而不是只取选中字段**：选区只约束"写哪儿"，读范围一直是全文。如果快照只覆盖选中字段，"什么都没选"这一档就没有任何版本可比，M20 的冲突检测会直接失效——而这恰恰是最需要它的时候（无选区时可以写到任何字段）。

**变更影响面**（改了 A，B 可能过时）——这件事分两层，只有一层需要 AI：

第一层是**必然的**，用硬表，不靠 AI 判断。字段只有 9 个，依赖关系有限且确定：

| 改了 | 可能过时 |
|---|---|
| 项目是什么 | 目标 / 用户与场景 |
| 目标 | 功能清单 / 验收条件 / 风险 |
| 用户与场景 | 功能清单 / 验收条件 |
| 功能清单 | 依赖与边界 / 验收条件 / 风险 |
| 依赖与边界 | 功能清单 / 风险 |

填充卡确认**之前**，系统拿这次改动的字段去查表；下游字段已经有内容，就在卡片上多一句提示——"目标改了，验收条件可能过时，要不要一起看"。

第二层是**语义上的松关联**（改了目标里某个概念，功能清单某条措辞可能要调）。这个表算不出来，由 AI 提，但**只作为建议**，不阻断、不自动改。

分工的意义：确定性的部分有硬约束兜底，不依赖 AI；不确定的部分让 AI 提。既不会"全靠 AI 不可控"，也不会漏掉必然的关联。

**不变量**

- AI 只能写 `selected_fields` 里的字段，**M20 强制**，不靠提示词自觉。
- 有选区时，每条提案的 `target_label` 必须落在选区内。
- **选区在轮内不变**。

### C2 Block / Document（文档）

文档是按模板字段分区的 block 树。

**Block**

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `block_id` | 唯一标识 | 创建时 | 全局引用 |
| `parent_id` | 父子关系，空 = 顶层 | 创建时 | M2 渲染目录树 |
| `schema_label` | 这个块属于哪个模板字段 | 创建 / 写入时 | M20 定位；M28 落位 |
| `content` | 正文 | 用户 / M20 | M13 进上下文；M2 展示 |
| `version` | 每次修改 +1 | 每次写入 | M20 检测冲突 |
| `source_card_id` | 谁写的，空 = 用户手写 | M20 | 审计：AI 写的都能追到一次用户确认 |

**Document**

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `doc_id` | 文档标识 | 创建时 | 全局 |
| `project_id` | 归属哪个项目 | 创建时 | M1；记忆层按项目隔离 |
| `template_id` | 用了哪个模板 | 创建时 | M28 校验字段名合法；M2 渲染分区 |

顶层块由 `parent_id` 为空推出，不单独存；同级顺序由数组顺序表达，不占字段。

### C3 Document Version（文档版本）

用户手动编辑和 AI 写入**共用同一条版本时间线**。

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `version_id` | 版本标识 | 每次产生版本时 | 回退时指定目标 |
| `doc_id` | 属于哪个文档 | 同上 | 查历史 |
| `seq` | 递增序号 | 同上 | 排序、判断先后 |
| `snapshot` | 这一版的完整内容 | 同上 | 回退时恢复 |
| `trigger` | 三个值：`manual` 手动编辑 / `submit` 卡片确认 / `rollback` 回退 | 同上 | 界面区分版本来源 |
| `group_id` | 由哪组卡片确认产生（手动编辑和回退时为空） | 同上 | 审计：这版对应哪组卡片 |
| `target_version_id` | **只有 `rollback` 用**：这版是从哪一版退回来的 | 同上 | 审计：回退本身也要留痕（AC8） |

**不变量**

- 回退是**产生一个新版本**，不删除也不篡改历史（I8）。
- **改动与回退的原子单位 = 一个文档版本。** 一次改动产生一个版本，版本就是回退的粒度，所以"回退到改动之前"= 回退到目标版本。
- 三种 trigger 各自对应一次改动：`submit` = 一次卡片组确认（整组一次事务，改几处也只有一版）；`manual` = **一次显式保存**；`rollback` = 一次回退动作。
- 因为 `submit` 版本上带 `group_id`，"撤销某次 AI 写入"是可表达的：查到该 `group_id` 产生的版本，回退到它之前那一版。

### C4 Agent Packet（信息包）

角色输出的统一形态。它是**编排层内部的通用语**——不对外，但因为要跨 agent 传（M8 汇总、M28 成稿都要读），形态必须固定。

**分两半：信封统一，内容是一组主张。**

> 参照：A2A 协议把智能体之间的消息定义成 `Message { role, parts[] }`，`parts` 里每一部分可以是文本、文件或结构化数据。**统一信封 + 有限几种内容形态**，是这类系统的通行做法。不是"每个 agent 一套结构"，也不是"所有 agent 挤进一个固定结构"。

**信封**（所有信息包完全一样）

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `packet_id` | 标识 | 角色 | 被 Citation 引用 |
| `round_id` | 属于哪一轮 | 角色 | M8 按轮取包；M25 复盘 |
| `role_id` | 谁产出的 | 角色 | 界面显示"这是谁说的" |
| `claims` | 主张数组，见下 | 角色 | M8 汇总；M28 成稿 |

**主张 Claim**（一个包可以有多条，这才是各角色真正不同地方）

| 字段 | 作用 | 谁读 |
|---|---|---|
| `claim_id` | 这条主张的标识 | **审查角色的 `challenge` 要指名反对哪一条（C15 的 `claim` 引用）**；M8 合并去重时指代；界面给每条主张编号 |
| `statement` | 这条主张说了什么（一句话） | M8 合并去重判分歧；M28 成稿；卡片展示 |
| `kind` | `proposal` 提议 / `challenge` 反对 | **M8 只把 `proposal` 当内容候选**，`challenge` 用来判断有没有分歧。不分这两个，反对意见会被当成内容写进文档 |
| `target_label` | 建议落到哪个字段 | M28 落位；为空时 M8 归类，或产一张卡片问用户 |
| `citations` | 这条主张自己的依据（C15） | 卡片展示；审计 |

**为什么 `kind` 和 `target_label` 在主张上而不是包上**：一个角色一轮里常常既提议又反对，它的主张也可能分别落到不同字段。放包上表达不了。

**每个角色的"特制"体现在哪**——不在结构上，在三处：它**关注哪些字段**、它的**领域知识**（在 prompt 和它挂的 skill 里）、它**说什么**。

两个例子：

```
# 交付规范 agent
claims: [
  { statement: "交付物必须包含接口文档", kind: proposal, target_label: "功能清单" },
  { statement: "上线前必须通过压测", kind: proposal, target_label: "验收条件" }
]

# 领域分析 agent
claims: [
  { statement: "该领域用户最常抱怨的是流程太长", kind: proposal, target_label: "用户与场景" },
  { statement: "这类产品通常需要合规模块，建议纳入风险", kind: proposal, target_label: "风险" }
]
```

**结构完全一样，内容完全不同。**

**为什么不给每种角色定义不同的包结构**：① M8 要逐条合并、去重、判分歧，结构各不相同就得为每种写一套比较逻辑；② 加一个角色就要改契约，而契约的价值恰恰在稳定；③ 角色之间差的确实是"说什么"，不是"结构长什么样"。

**不变量**

- 每条 claim 要么有 ≥1 条 citation，要么显式声明无来源。不允许"看起来有依据"但实际没有。
- **不保存思考过程**，只保存结论。

### C5 Material Packet（材料包）

进入生成链路的外部信息，统一成这一种形态，让 M13 组装上下文时不必区分来源。

**来源只有三个**：检索命中你自己的资料、联网搜到的、讨论区聊出来的。

> 注意：**上传解析不是来源，是准备动作**。流程是"上传 → 解析 → 进资料库"，之后被检索命中的那一刻，才以材料包的形式出现，那时 `source_type = retrieval`。用户直接粘贴的一段话也不是材料包，那是用户输入，直接进上下文。

**讨论区那一路怎么变成材料包**：用户勾选的思路候选（C6）在下一轮主闭环组装上下文时转换过来，字段对应关系是：

| C6 字段 | → | C5 字段 |
|---|---|---|
| `claim` | → | `content` |
| `discussion_round_id` + `idea_id` | → | `ref` |
| — | → | `source_type = discussion` |
| — | → | `credibility = low`（由来源推断，不由调用方填） |
| `suggested_label` | 不带进材料包 | 它只在勾选界面上帮用户判断"这条会落到哪"，不是依据；落位由 M28 依据上下文决定 |

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `material_id` | 标识 | 工具 | 被 Citation 引用 |
| `source_type` | `retrieval` 检索 / `web` 联网 / `discussion` 讨论 | 工具 | M13 决定上下文优先级；也决定 `credibility` 的默认值 |
| `content` | 正文 | 工具 | M13 进上下文；M28 当依据 |
| `ref` | 来源锚点：URL / 资料名+位置 / 讨论轮 id | 工具 | 审计；M28 写内容时要带出处 |
| `credibility` | `high` / `medium` / `low`，**由来源推断**：retrieval→high，web→medium，discussion→low | 工具 | M28 判断能不能单独作为写入依据 |

**不变量**

- 进上下文的材料**必须带 `ref`**。没有来源的东西不许进。
- `credibility = low` 的材料**不能单独作为写入依据**，只能当灵感。
- **用户自己挑的算数**：讨论区候选是用户勾选带进来的，写入由它衍生出的内容时，依据链是"用户勾选（`idea`）+ 用户确认填充卡"，不是这条材料的可信度。但材料本身照样标 `credibility = low`，卡片上照样显示它来自讨论区——用户有权知道这条内容的源头是讨论，不是文档或资料。

### C6 Idea Candidate（思路候选）

讨论区和主闭环之间的**唯一交接形态**。一轮讨论结束后，M29 把发言整理成候选，用户从中挑选。**用户挑的是结构化后的候选，不是一屏聊天记录。**

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `idea_id` | 标识 | M29 | 勾选时引用 |
| `discussion_round_id` | 来自哪一轮讨论（讨论轮的 id，与主闭环轮次区分开） | M29 | 追溯；转成材料包时进 `ref` |
| `claim` | 一句话主张，**这是用户真正在挑的东西** | M29 | 勾选界面 |
| `from_packet_ids` | 出自哪几条发言 | M29 | 保证没出处的思路不出现；点开可看原话 |
| `suggested_label` | 建议落到哪个字段 | M29 | **只在勾选界面用**，帮用户判断这条要不要；不带进材料包，落位由 M28 决定 |
| `status` | `pending` 待选 / `selected` 已勾选 / `discarded` 不要 / `consumed` 已被某一轮主闭环用掉 | 用户勾选；`consumed` 由 M13 写上 | 勾选界面；M13 只组装 `selected` 的候选 |

**不变量**

- 每个候选必须能追溯到 ≥1 条信息包（`from_packet_ids`）。不允许出现没有出处的思路。
- **`selected` 的候选只被消费一次**：进了某一轮的上下文之后由 M13 标成 `consumed`。否则同一批候选会被之后每一轮重复带进来，越滚越多。用户想再用一次，就再勾一次。
- **消费发生在"组装上下文那一刻"，不是"用户勾选那一刻"，而且是整批一次性消费、不是逐条。** 所以这一轮如果失败或没产出任何东西，候选已经标成 `consumed` 了，用户要重新勾选。

### C7 Card（卡片）

卡片是**系统在长任务过程中向你求助的一种方式**，用来让用户回应。它不是审批流程的一环。

**它什么时候出现**：系统干活的过程中卡住了——缺信息、或者角色之间有冲突——就把问题整理成卡片抛出来等裁决。裁决完继续干。**填充卡是例外：它是收尾，要等内容都没问题了才出现。**

**每张卡片下面都有输入框**，用户可以点按钮选，也可以直接打字说要改什么。**没有"驳回"这个专门动作——用户说什么就是什么。**

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `card_id` | 标识 | M8 / M28 | 被引用 |
| `kind` | 这张卡要用户干什么，四个值见下 | M8 | 界面决定长什么样 |
| `prompt` | 卡片上展示给用户的话 | M8 / M28 | 界面 |
| `options` | **只有分歧卡用**：备选方案，每个带自己的依据 | M8 | 界面展示；用户选一个 |
| `proposals` | **只有填充卡用**：提案数组，一张填充卡装多条提案，按字段分区渲染。结构见下 | M28 | 界面展示；M20 写入 |
| `answer` | 用户的回应：点按钮选的，或自己打的字 | 用户 | M20 写入；M17 提炼反馈 |
| `status` | `pending` 待回应 / `answered` 已回应 / `skipped` 跳过 | 用户 | 界面；提交判断 |

**`proposals` 里每一条提案**（这是填充卡的核心，一张卡可以有多条）：

| 字段 | 作用 |
|---|---|
| `proposal_id` | 标识 |
| `target_label` | 写到哪个**字段** |
| `op` | `replace` 改写这个字段 / `append` 往这个字段追加 |
| `content` | 提案内容。**`append` 时装增量**（要追加的那条或那几条），**`replace` 时装整段** |
| `state` | `kept` 留下 / `removed` 用户删掉了 |
| `citations` | 这条提案自己的依据（C15） |

**`options` 里每一个备选**（只有分歧卡用）

| 字段 | 作用 | 谁读 |
|---|---|---|
| `option_id` | 标识，用户选的就是它 | 界面回填 `answer`；M8 接着往下算 |
| `text` | 方案本身，一句话说清这个方案主张怎么做 | 界面 |
| `citations` | 这个方案自己的依据（C15）。**分歧卡的责任是摆明分歧，不是给出一个综合结论**，所以每个方案各自带依据 | 界面；用户判断的依据 |

> 分歧卡和填充卡用的是两个字段，不能互换：分歧卡是"选一个"（`options`），填充卡是"要不要"（`proposals`）。

**填充卡的规则**

1. **填充卡永远只有一张**，多条改动装在 `proposals` 数组里，渲染时按字段分区。所以"一组最多 5 张"只约束中途的裁决卡，收尾不会超。
2. 用户可以先看，然后逐条决定**要还是不要**（不要的删掉）。确认时只写 `state = kept` 的提案；全删掉 = 这次不写，允许。
3. **删除 ≠ 跳过**，别混：
   - **删除**（提案级）= 这条我不要，别写。**这同时是一条反馈信号**——AI 提了一条用户不想要的，要记下来喂给复利，否则系统永远不知道它提错了。
   - **跳过**（卡片级）= 这张卡还没想好，先放下，落到"待确认问题"。它区分的是"我暂时不想决定"，不是"AI 提得不对"。
4. **`op` 只有两种：`append` 追加 / `replace` 替换。** 卡片上标明每条是哪种，用户不需要理解它，也不需要改它。
5. **填充卡不提供编辑器。** 卡片上只有"要"和"不要"两个动作。用户想改文案，有两条路：先接受写进文档，再在文档里改（文档本来就可以手动编辑）；或者删掉这条，重新说一次要求。

> 为什么不在卡片里放编辑器：文档本身就是可编辑的，编辑这件事归文档，卡片只负责收敛用户的决定。多一个编辑器会带来"卡片里改的和文档里改的谁优先"这类问题，还得再定一套合并规则。

**四种 kind 分别用哪些字段**

| kind | 什么时候出现 | prompt 里写什么 | 用到的字段 |
|---|---|---|---|
| `understanding` 确认理解 | **每一轮用户输入之后** | 系统**读过文档之后**复述"你要我改哪一块、按什么约束、改成什么样" | prompt、answer |
| `question` 补信息 | 系统缺信息，做不下去 | 要问的问题 | prompt、answer |
| `conflict` 选一个 | 角色之间意见矛盾 | 说明分歧在哪 | prompt、options、answer |
| `fill` 确认内容 | **只在最后，内容都没问题了才出现，永远只有一张** | "这次我打算改动 3 处" + 按字段分区的提案列表 | prompt、proposals、answer |

**为什么理解确认卡每轮都有**：它确认的是**这一轮用户输入的意思**，不是项目级的目标。

**它必须带着上下文复述，否则没有价值。** 用户说"细化一下功能清单"，系统回一句"我理解你要细化功能清单"，那是抄一遍。合格的复述要说出**文档里现在是什么样、你打算按什么约束改成什么样**。

**合格标准（可验收）**：复述里必须包含至少一个**只有读了文档才知道的信息**。做不到就说明 M13 的上下文没组装对，或者系统在复读。

**不变量**

- **一张卡只针对一个议题**：一个冲突，或者一个独立的问题。不同领域、互不相干的疑问不合并到同一张卡上。
- 用户回应的方式有两种：点按钮，或直接在输入框里打字。两者地位相同。
- 跳过的卡片不丢，落到文档的"待确认问题"分区。
- 冲突要**暴露而不是抹平**：分歧卡必须把分歧点摆出来，不能只给一个被综合过的结论。
- **确认理解卡不是填充卡**：它只对齐这一轮用户输入的意思，不写入任何内容。
- **用户纠正理解之后，直接按纠正后的理解走**：更新理解 → 重新组装上下文（纠正可能改变该读什么）→ 直接进入生成。**不再出第二张确认理解卡**，不让用户为同一件事确认两次。

### C8 Card Group（卡片组）

**一组卡片 = 一次裁决。** 系统在长任务里卡住了，把这一批问题整理成一组抛给用户；用户裁决完，整组提交，系统接着往下干。

**它不是输出的终点**，只是中途的一道关卡。整个主闭环可能来回好几组卡片，直到内容都没问题了，才由最后一张填充卡收尾。

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `group_id` | 标识 | 系统 | 被引用 |
| `cards` | 卡片列表，**最多 5 张**（没有例外），数组顺序就是依次回应的顺序 | 系统 | 界面 |
| `state` | `answering` 回答中 / `confirmed` 已确认 | 界面 | **决定能不能改** |
| `round_id` | 这组卡片属于哪一轮 | 系统 | M20 按它取这一轮的 C1 当写范围；M25 复盘的入口 |
| `result_version_id` | 如果这组里含填充卡，提交后产生的文档版本 | M20 | 审计 |

> **为什么不另存一个 `scope_id`**：选区在轮内不变（I18），所以"这一组的写范围"就等于"这一轮的写范围"。多存一份作用域，就多一份和 C1 对不上的可能。

**规则（你明确要的）**

1. **一批最多 5 张，没有例外。** 填充卡**单独成批**（它的批里只有 1 张），不和裁决卡同批——所以"填充卡算不算占名额"这个问题根本不存在。超过 5 张说明问题没拆干净，应该分批问。
2. **每张卡只针对一个议题**：一个冲突，或者一个独立类别的问题。每张卡的信息量可以大，但必须聚焦——不能一张卡拉七件事。
3. 一次可能连着给多张卡片，**在提交之前，可以回到任意一张改**。
4. **提交之后，整组不能再改**。要改就是新一轮。
5. 提交是一次事务：要么全部生效，要么全部不生效。
6. 提交完**不是结束**，系统接着往下完善；只有最后那张填充卡确认完，才算写入文档。

**不变量**

- `state = confirmed` 之后整组不可变。
- 只写入 `status = answered` 的填充卡；`skipped` 的裁决卡在**这一轮写文档的那一次**由 M20 一并追加进"待确认问题"分区（这一轮没写文档，就先留在卡片历史里，下一轮仍查得到）。
- 不含填充卡的卡片组提交后**不产生文档版本**——它只推进任务，不动文档。

### C9 Memory（记忆）

记忆分候选与生效两态。这是防止"一次错误反馈污染以后所有生成"的关键。

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `memory_id` | 标识 | M17 | 被引用 |
| `type` | `fact` 事实 / `decision` 已确认决定 / `lesson` 教训 / `preference` 偏好 | M17 | M13 决定注入方式：决定类常驻，事实类按需 |
| `content` | 正文 | M17 | M13 进上下文；M16 被检索 |
| `status` | `candidate` 候选 / `active` 生效 / `invalid` 失效 / `retired` 退役 | M17 写候选，记忆层标 `invalid`，M30 管晋升与退役 | **只有 `active` 能进常驻上下文**；`invalid` 和 `retired` 都不作为依据 |
| `citations` | 从哪来 | M17 | 无出处的记忆不许入库 |

**不变量**

- 只有 `active` 进常驻上下文；`candidate` 只能被按需检索命中，或干脆不出现。
- 每条记忆必须有出处。
- **失效规则**：记忆引用的 block 被改动后（`doc.changed` 事件），这条记忆改成 `status = invalid`，不再作为依据。否则系统会拿过期共识生成新内容。
- **`invalid` 和 `retired` 是两件事，别合并**：`invalid` 是**被动**的（依据被改了，不由它自己决定）；`retired` 是**主动**的（长时间没用或验证没过，由 M30 判）。两种状态对用户的说法不一样，只有一个是"你改过文档"，另一个是"这条一直没帮上忙"。

> 后续：`weight`（权重）、`confirmed_by`、使用统计等字段留到记忆规模变大、需要排序时再加。现在没有消费者。

### C10 Registry Entry（注册条目）

注册中心把所有**定义类**的东西集中管理：角色、prompt、工具、skill、模板、模型、编排策略。

**但两种东西的要求不一样**：

- **工具和 skill 是要让 AI 自己挑的**，所以必须有 `description` / `tags` / `when_to_use`，否则 AI 没法判断该不该用。
- **角色、prompt、模板这些只是解耦出来统一管理**，有名字和本体就够了，不需要额外的描述字段。

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `id` | 标识 | M27 | 被角色和会话引用 |
| `kind` | 角色 / prompt / 工具 / skill / 模板 / 模型 / 编排策略 | M27 | 分类查询 |
| `name` | 名称 | M27 | 界面 |
| `content` | 定义本体：角色的说明 / prompt 内容 / 工具怎么调 / 模板字段定义 | M27 | 使用它的模块 |
| `description` | 一句话说明它是什么 | M27 | **只有工具和 skill 必填**；给 AI 看的 |
| `tags` | 能力标签，如 `web_search` / `summarize` | M27 | **只有工具和 skill 必填**；AI 挑选的主要依据 |
| `when_to_use` | 什么情况下该用它 | M27 | **只有工具和 skill 必填**；没有它 AI 没法自己选 |
| `owner` | `preset` 预设 / `user` 用户创建 | M27 | 权限：预设角色可定制工具，自定义角色限统一工具池 |
| `status` | `active` 启用 / `retired` 停用 | M27 | 只有 `active` 会被调用 |
| `allowed_tools` | **只有 `kind = 角色` 用**：这个角色能调哪些工具的 id 白名单 | M27 | M23 执行 `canUse`；M10 只在这个范围内挑工具 |
| `allowed_entries` | **只有 `kind = 角色` 用**：这个角色能在哪些入口出现（`main` / `discussion`） | M27 | M23 执行 `canEnter`；M7 讨论区预选、M8 主闭环挑角色都要先按它过滤 |

**权限为什么是两组白名单，而不是一句 `permissions`**：角色对外的限制有两类，混在一起就说不清。一类是**能力**（这个角色能用哪些工具），一类是**场合**（这个角色能不能出现在主闭环里）——比如某些角色只能在讨论区发言，不参与主闭环生成。这两类必须分开表达。

**执行**在 L6 的两个判定：`canUse(role_id, tool_id)`、`canEnter(role_id, entry)`。

**不变量**

- **工具和 skill 缺 `description` / `tags` / `when_to_use` 的，不许注册。** 其他 kind 不要求。
- `tags` 必须是能力词，不是产品词，否则 AI 检索不到。
- 权限的**声明**在这里，权限的**执行**在 M23。
- **`allowed_tools` / `allowed_entries` 只对 `kind = 角色` 有意义**，其他 kind 不要求、也不校验。
- 预设角色可以带专属工具；**用户自定义角色只能从统一工具池里选**——这是**注册时**的校验（M27），不是运行时判断。
- **用户可以自己删掉 skill**，包括系统收割出来的。删了就删了，不搞软删除。角色、prompt 这些同理。

> `kind = skill` 的条目由 M30 复利验证器管理，不允许人工直接置为 `active`。M30 改状态之后发 `registry.updated`（C13）。

### C11 Trace（观测）

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `trace_id` | 标识 | M25 | 复盘入口 |
| `round_id` | 哪一轮 | M25 | 把 trace 和轮次对上 |
| `context_used` | 这一轮带了哪些上下文，含被裁掉的 | M25 | 出问题时看"是不是该带的没带上" |
| `tools_called` | 调了哪些工具 | M25 | 看"是不是没查资料就编了" |
| `final_version_id` | 最终写进了哪一版 | M25 | 把 trace 和文档版本对上 |
| `claims` | **主张留痕**：这一轮说过哪些主张。每条是 `ClaimDigest`——`packet_id` / `claim_id` / `role_id` / `statement` / `kind` / `citations` | M25 | 复盘："这个分歧怎么来的、当时凭什么这么说" |

> **主张留痕的形状归 C11 所有，不是 C4 的形状。** C4 是编排层的内部通用语（层内），
> 契约层不 import 编排层；C11 要的是"能复盘的那几列"，两者字段重合不代表同一个对象。
> 没有这个字段，"要审计走 trace"就是一句空头支票——主张会随轮末的黑板一起消失。

### C12 Blackboard（黑板）

通信层的一半。**黑板是"这一轮任务的共享状态"，事件是"状态变了通知谁"。两者分工是：事件只说"什么变了"，细节回黑板读。**

否则会有两种退化：只发事件不带状态，订阅者拿到通知还得自己再问一圈；只共享状态不发通知，别人不知道什么时候该来看。

黑板按区块划分。**每个区块只有一个直接写者**：

| 区块 | 放什么 | 谁写 | 谁读 |
|---|---|---|---|
| `round` | 这一轮在干什么（形状见下） | 编排层 | 所有层；界面读 `phase` 显示进度 |
| `context` | 这一轮组装出来的上下文（形状见下） | 编排层 | 编排层；M24 裁剪；C11 trace |
| `claims` | 这一轮的 C4 信息包数组 | 编排层 | 编排层（汇总、成稿）。**主闭环界面上不展示它**——它是内部中间态，要审计走 trace；讨论区那边展示的是 C14 的 `utterances` |
| `card_group` | 当前的 C8 实例，含用户的回应 | 编排层 | 卡片界面；M20 |
| `confirmed` | 这一轮已经确认下来的东西：已 `confirmed` 的 C8、由它产生的 C9 候选 | 编排层 | M16 / M17 / M30 |

**为什么写者只有编排层**：黑板是"这一轮的工作台"，谁在维护这一轮，谁就是唯一写者。区块的**内容来源**可以有很多（文档来自存储、材料来自工具层、记忆来自记忆层），但都是把产出**交给编排层**，由编排层统一写进来——否则"这份状态是谁写的"就永远说不清。

接口两个：`read(区块)` / `write(区块, 值)`。**没有 `subscribe`：通知归事件（C13）管。** 两套通知机制并存，用的人会不知道该订哪一个。

**`round` 区块的形状**

| 字段 | 作用 | 谁读 |
|---|---|---|
| `round_id` | 这一轮的标识，**全局唯一**（讨论轮和主闭环轮共用一套 id 空间，靠 `entry` 区分） | C4 / C8 / C11 / C14 都引用它 |
| `project_id` | 属于哪个项目 | 记忆与检索按项目隔离 |
| `entry` | `main` 主闭环 / `discussion` 讨论区 | 界面决定展示哪一套；讨论轮不产卡片 |
| `user_input` | 这一轮用户说了什么（原文） | M8 复述；M13 组装；审计 |
| `scope` | 这一轮的 C1 实例 | M20 强制写范围；界面高亮 |
| `phase` | `assembling` 组装 / `restating` 复述理解 / `working` 生成 / `awaiting_user` 等用户回应 / `drafting` 成稿 / `writing` 写入 / `done` / `failed` | 界面显示进度；失败时和 `generation.failed` 一起说清卡在哪一步（AC12） |
| `ended_at` / `end_reason` | 什么时候结束、为什么结束（写完 / 用户叫停 / 失败） | C11 trace；界面 |

**`context` 区块的形状**

| 字段 | 作用 | 谁读 |
|---|---|---|
| `blocks` | 上下文块数组，见下 | 角色 prompt 组装；C11 `context_used` |
| `dropped` | 被 M24 裁掉的部分 | C11 trace：出问题时要能看出"是不是该带的没带上" |
| `assembled_at` | 组装时间 | 复盘 |

**`blocks` 里每一个上下文块**

| 字段 | 作用 | 谁读 |
|---|---|---|
| `source` | 来自哪：`document` / `brief` / `memory` / `material` / `user_input` / `discussion` | M24 决定裁剪顺序；复盘 |
| `ref` | 对应哪个对象：`block_id` / `memory_id` / `material_id` / `round_id` / `group_id`（用户的卡片回应） | 引用归因（C15）；审计 |
| `content` | 带进来的正文 | 角色 prompt |
| `priority` | 优先级，**`≥ 0` 的整数，越大越先保留**；同值按 `(source, ref)` 排序，保证同一份上下文每次裁出同一个结果 | M13 给数值；M24 只按它排序并裁，不做语义判断 |
| `credibility` | 只有材料有（继承 C5） | M28 判断能不能单独当依据 |

> 上下文块**不是新契约**，它是"这一轮按优先级带上来的东西"的容器：每个块的 `content` 都来自某个已有契约的对象，`ref` 指回那个对象。

**不变量**

- 黑板只放**当前这一轮**的状态。要长期留下的东西，在这一轮结束时写进 L7 存储或 C9 记忆。
- **每个区块只有一个直接写者**（编排层）；其他层只能读。产出来源可以多，写入口只有一个。
- 区块里的对象都是已有契约的实例（C1 / C2 / C4 / C5 / C8 / C9）。黑板定义的是**放哪儿**，不是**长什么样**——`round` 和 `context` 两个区块除外，它们的形状就定义在上面这一节。
- **黑板持久化**（落 SQLite）。介质不再是内存。换来三件事：崩溃后知道上一轮跑到哪、前端可以直接拉当前轮状态、写工作台和写账本能在同一个事务里。
- **只持久化当前这一轮**。轮结束时该落账本的落账本、该落 trace 的落 trace，然后删掉这一轮的区块；`rounds` 里那一条长期保留。
  注意：**不要保留多轮区块**。历史轮次的东西各有各的家（文档与版本在 C2/C3、卡片在卡片历史、消息与摘要在 C17、结论在 C9、用了什么在 C11），再留几轮就是造第三个历史库。
- **写入即广播**：写某个区块时，由黑板按"区块 → 事件"映射自动发事件——`round` → `round.updated`，`card_group` → `card_group.updated`，`context` / `claims` / `confirmed` → **不发**。这样不存在"写了状态、忘了通知"这个失效模式。
- **先提交，后广播**：事件必须在事务**提交之后**发，绝不能在事务里发——否则订阅者回读时读到的是旧状态。
- **活对象放在区块里，冻结出来的东西落账本**：`card_group` 区块装**当前轮的 C8 实例**（含用户的回应）——它还没冻结，账本里没有它的位置；一旦 `state = confirmed`，整组作为卡片历史落 L7，`confirmed` 区块**只放 id**（已确认的 C8 与 C9 候选的 id）。
- **`claims` 区块只有编排层能读**：其中装的是层内对象；其余区块的"谁读"是用途说明，权限上 §5.3 的 `read` 对所有层开放。
- **`context` / `claims` 不存正文**：`context` 只存引用（`ref`）、优先级、可信度、被裁掉的部分，正文按需回源对象取。

### C13 Event（事件）

通信层的另一半。**事件只做一件事：把状态变化通知给关心它的层。**

**它不携带完整数据**——只带"什么变了"和最小定位信息；订阅者要看细节，回黑板读。

> **事件不是智能体之间的通信。** 智能体之间怎么调度、谁把结果传给谁是编排层的内部实现，不走事件。

**谁发事件：状态的生产者。** 订阅者只读，不通过事件反向改产生者。用户动作（点确认、打一句纠正）不是事件——那是界面对编排层的调用，由编排层把结果写进黑板之后再发事件。这样"事件是谁发的"永远只有一个答案。

事件本身的字段只有三个：`type` / `payload`（**最小定位信息**）/ `at`。

**按状态对象划分：一个对象只有一个事件类型。** 改变的性质写进 payload（`phase` / `state` / `status` / `trigger`），订阅者按 payload 过滤。

这样划分是为了消掉两个必然出现的毛病：**同一件事收到两条事件**（比如"文档写了"既发 `doc.updated` 又发 `doc.version.created`），以及**加订阅者时会漏订**——漏订一个事件，那个订阅者就永远不知道该动。

一共 **8 个事件**：5 个状态对象（轮次 / 卡片组 / 文档 / 记忆 / 注册条目）、1 个讨论轮增量、1 个工具调用、1 个失败通知。

| 事件 | 状态对象、生产者 | 谁收 | payload（最小定位信息） | 订阅者拿它干什么 |
|---|---|---|---|---|
| `round.updated` | 轮次（C12 `round` 区块）、编排层 | 主闭环界面、讨论区界面 | `round_id` / `project_id` / `entry` / `phase` / `from_phase` / `end_reason` | 开轮时重置视图；干活期间显示卡在哪一步（`assembling` → `restating` → `working` → `drafting` → `writing` → `done`）；结束时收尾。**开轮就是第一次 `phase` 变化，不再单独发 `round.started`** |
| `card_group.updated` | 卡片组（C8）、编排层 | 卡片界面、M20 文档写入 | `group_id` / `round_id` / `state` / `card_count` / `has_fill_card` | 界面重画卡片；M20 只在 `state = confirmed` 且 `has_fill_card = true` 时回黑板读这一组并写文档。**"用户确认了"就是 `state` 变成 `confirmed` 那一次，不再单独发 `card_group.confirmed`** |
| `doc.changed` | 文档（C2 / C3）、M20 文档写入 | 编排层、记忆层、文档界面 | `doc_id` / `version_id` / `seq` / `trigger`（`submit` / `manual` / `rollback`）/ `block_ids[]` | 编排层：手里那份上下文过时了，下一轮重新组装；记忆层：按 `block_ids` 做引用失效；文档界面：正文和版本列表刷新。**AI 写入、用户手改、回退走同一个事件**，否则"手改之后记忆要不要失效"这种事就会漏 |
| `discussion.utterance_added` | 讨论轮（C14 `utterances`）、M7 讨论编排器 | 讨论区界面 | `round_id` / `role_id` / `packet_id` / `index` | 逐条把发言追加到界面上。讨论区是"一条一条冒出来"的，用增量，不必每次重画整轮 |
| `memory.updated` | 记忆（C9）、M17 / M30 / 记忆层的失效判定 | M16 检索、M30 候选队列、界面 | `memory_id` / `project_id` / `type` / `status` / `from_status` | 更新检索索引；把新候选排进验证队列；记忆面板刷新。**候选产生、晋升、失效、退役都走它，不再单个 `memory.promoted`** |
| `registry.updated` | 注册条目（C10）、M27 注册中心 | M7 / M10 / M23 / M28 | `id` / `kind` / `status` / `from_status` | 换掉手里那份定义：M7 按 skill 选编排策略、M10 按 `tags` 挑工具、M23 执行权限、M28 读模板字段——条目停用之后不能再用旧的。**M30 晋升 / 退役 skill 也走它** |
| `tool.invoked` | 一次工具调用、工具层 | 界面 | `round_id` / `tool_id` / `status`（`started` / `finished`）/ `role_id`（**可空**——检索是记忆层在组装上下文时发起的，那种调用没有角色） | 联网、检索这类几秒到十几秒的操作，界面要显示"正在查什么"，否则看着像死了 |
| `generation.failed` | 这一次生成、Harness（L6） | 界面、编排层 | `round_id` / `step` / `reason` / `retryable` | **三样必须都在**：失败在哪一步、人话的原因、能不能重试。界面展示原因并提供重试；编排层据此把这一轮标成 `phase = failed` |

**为什么失败要单独一个事件、不塞进 `round.updated`**：`generation.failed` 的生产者是 Harness（L6），`round.updated` 的生产者是编排层（L2）。失败细节（哪一步、什么原因、能不能重试）只有 Harness 知道；编排层是**收到之后**才把自己的轮次状态改成 `failed`。谁的状态谁发。

### 覆盖核验：数据流的每一步，事件够不够

把 §7 的每一跳过一遍，看它属于"被事件覆盖"还是"根本不需要事件"。**没有第三条：要么有人需要被通知，要么没人需要。**

| 数据流的哪一段 | 事件覆盖 | 说明 |
|---|---|---|
| 开轮 / 阶段推进 / 用户叫停 / 收尾（§7.1 第 3、10、18、22、28、31 步） | `round.updated` | 界面据此画进度、收尾 |
| 上下文组装与裁剪（第 4–9 步） | **不需要事件** | 没有跨层订阅者：结果编排层马上就用；要回看走 C11 trace |
| 卡片组出现 / 更新 / 冻结（第 11、20、21、24、25 步） | `card_group.updated` | 界面重画；M20 认出 `confirmed + 填充卡` |
| 角色逐个产出主张（第 14–17 步） | **不需要事件** | 主闭环界面不展示角色的逐条主张，它们是内部中间态；要审计走 trace。讨论区的逐条展示由 `discussion.utterance_added` 覆盖 |
| 审查与汇总（第 18、19 步） | **不需要事件** | 内部中间态；结果以卡片形式出现，由 `card_group.updated` 通知 |
| 工具调用（第 6、16 步） | `tool.invoked` | 长操作期间让界面有反馈 |
| 文档写入 / 手改 / 回退（第 28、29、34、35 步） | `doc.changed` | 一条事件覆盖三种来源 |
| 版本冲突（第 27 步） | `card_group.updated` | 冲突的产物就是一张新卡，不需要单独事件 |
| 记忆失效（第 30 步） | `memory.updated`（`status = invalid`） | 记忆层是生产者，自己发 |
| 记忆候选 / 晋升 / 退役（第 32 步、§10） | `memory.updated` | 候选态也要发：不然候选永远没人看见，复利没有闭环 |
| 注册条目状态变化（M30 晋升 / 退役 skill、用户删 skill） | `registry.updated` | M7 按 skill 选编排策略、M10 按 `tags` 挑工具，条目状态变了必须知道，否则会继续用一个已经停用的定义 |
| trace（第 33 步） | **不需要事件** | 回看是用户点开时拉取，不是被推 |
| 讨论区逐条发言（§7.2 第 5 步） | `discussion.utterance_added` | 讨论区界面的主循环 |
| 讨论区结束（第 6 步） | `round.updated`（`entry = discussion`、`phase = done`） | 讨论轮也是轮，共用轮次事件；界面据此显示「整理成提案」 |
| 选角色 / 整理候选 / 勾选 / 带进主闭环（第 2、3、7、8、9 步） | **不需要事件** | 全是用户同步触发的操作，结果直接返回给界面 |
| 生成失败（M26） | `generation.failed` | 见上表 |
| 建项目、导出、上传解析、读简报、看历史 | **不需要事件** | 都是界面发起的同步操作，自己就知道结果 |

### 被否掉的候选事件（为什么不要）

这张表是**证据**：事件少不是漏了，是判断过之后不该存在。

| 候选事件 | 结论 | 为什么 |
|---|---|---|
| `round.started` / `round.finished` | 并进 `round.updated` | 和"第一次 phase 变化""phase 变成 done"是同一件事。拆成三个，订阅者为了画一条进度得订三个事件，再加一个状态又得再加一个 |
| `card_group.confirmed` | 并进 `card_group.updated` | 确认就是 `state = confirmed`。拆开会让人问"updated 和 confirmed 到底订哪个"，而答案是"两个都得订" |
| `doc.updated` / `doc.version.created` | 并成 `doc.changed` | 一次写入同时产生两条，订阅者每次都要收两条再自己去重 |
| `memory.promoted` | 并进 `memory.updated` | 原来的版本只覆盖"晋升"，**退役和失效没有事件**——这就是漏 |
| `claims.updated` | 不设 | 主闭环界面不展示角色的逐条主张（见上表） |
| `context.assembled` | 不设 | 没有跨层订阅者；被裁掉了什么记在 trace 里，按需回看 |
| `card.updated` | 不设 | 卡片只以卡片组的形式出现，一个事件就够 |
| `discussion.started` / `discussion.finished` | 不设 | 讨论轮就是一轮，共用 `round.updated` |
| `idea.generated` | 不设 | 点「整理成提案」是同步调用，候选直接返回给界面 |
| `trace.created` | 不设 | 回看是拉取式的，不需要推送 |

**不变量**

- 事件是**只读广播**：订阅者只能据此回黑板读，不能借它反向改别的层的状态。推送不是调用。
- 事件不承载完整状态；要状态回黑板读。
- **一个状态对象只有一个事件类型**：新加订阅者时，不该出现"它该订哪个事件"这种问题。
- **一个状态变化只发一条事件**：同一件事发两条，订阅者就得去重，迟早有一处忘了去重。
- 事件必须由**状态的生产者**发；订阅者要细节，自己回黑板或存储读。
- **8 个事件全部实现。** 事件是整套流程的骨架，缺一个就有一段流程没人知道。
- **只有一条总线**：所有跨层通知都从它出去，没有第二套通道。黑板是它的一半（状态），事件是另一半（通知）；**改状态会经它广播**，但它上面跑的不止黑板（8 个事件里只有 2 个的源在黑板）。
- **分发方式：进程内**（不引外部中间件）。分发语义：异步、按订阅顺序 await；嵌套发布排队、当前处理器返回后排空；同轮 FIFO。
- **异常隔离**：一个订阅者抛异常，不阻断其它订阅者。否则前端渲染出个小错，就会让"记忆失效"这种链条整段跑不掉。
- **事件流水**：每条 `publish` 都落一张 append-only 表（`event_id` / `at` / `type` / `round_id` / `project_id` / `producer` / `payload`）。它回答的是"这件事到底发了没有"——没有它，这类问题只能靠猜。
- **发布要带身份**：`publish(event, producer)`。每个事件的生产者白名单写在上面的表里（一个事件可能有多个生产者，比如记忆层的候选产生与失效判定），**表外的身份发不出**；同一个白名单也用来判"谁能读 `claims` 区块"。

**身份词表**（六个，事件表里"生产者"那一列写的就是它们）：

| 身份 | 是谁 |
|---|---|
| `orchestration` | L2 编排层（M7 讨论编排器、M8 汇总、M9 卡片组装） |
| `document_writer` | L5 的 M20 文档写入 |
| `tools` | L5 工具层（一次工具调用） |
| `memory` | L4 记忆层（M17 写候选、失效判定、M30 改状态） |
| `registry` | L0 的 M27 注册中心 |
| `harness` | L6 Harness（一次生成失败） |

- **"同一轮内 FIFO"里的"一轮"**：指的是一次 `publish` 引发的整条分发（含它触发的嵌套发布），**与 `round_id` 无关**。同一队列，先进先出。
- **被隔离的订阅者异常去哪**：记一条 WARNING 日志（哪条事件、什么错）。隔离不等于静默吞掉——否则"记忆失效没跑"这种事永远查不出来。
- **循环保护**：一次 `publish` 引发的分发条数有上限（默认 1000）。订阅者之间形成环时抛错并清空队列，而不是把进程挂死。
- **"8 个事件全部实现"指机制**：能构造、能订、能落流水。某个事件暂时没人发（对应的生产模块还没做）不算缺。

### C14 Discussion Round（讨论轮）

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `round_id` | 标识（与主闭环轮次共用一套 id 空间，靠 C12 的 `entry` 区分）。思路候选引用它时写成 `discussion_round_id`，免得和主闭环的轮次混在一起 | M7 | 思路候选引用它 |
| `participants` | 本轮哪些角色。**上限 4 个**；由 M7 预选并给出选它的理由，用户可以在开始前增删换，确认后才开跑 | M7 预选 + 用户确认 | 界面；判断"是不是每人都说过了"；M13 按角色组装各自视角的上下文 |
| `utterances` | 发言：角色 + 信息包 + 界面文本 | M7 | M29 整理候选的原料 |
| `state` | `running` / `finished` | M7 | 决定「整理成提案」按钮什么时候出现 |
| `end_reason` | 每人都说过 / 用户叫停 / 到上限 | M7 | M29 和界面 |
| `idea_ids` | 这一轮整理出哪些候选 | M29 | 界面回看 |

**`utterances` 是数组，一轮里每个角色各一条**：角色的 id + 界面上展示的文本 + 指向结构化信息包的 id。前端按角色逐条展示——展示的是每个角色**想完之后的那段输出**，不是思考过程。

**不变量**

- **不保存内部思考过程**，只保存每个角色的最终输出。
- 一轮的默认结束条件是"每个角色各发言一次"。
- 这一轮的输出是 M29 整理候选的唯一原料；候选再带进主闭环当输入。

### C15 Citation（引用）

**每一句 AI 说的话都要能回答"依据什么"**（AC3）。`citations` 被 C4 主张、C7 提案与备选、C9 记忆四处使用，形状只在这里定义一次。

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `target_type` | 引用的是什么：`block` 文档块 / `memory` 记忆 / `material` 材料包 / `idea` 思路候选 / `user_input` 用户这轮说的话 / `claim` 同一批里的其他主张 | 产出方 | 界面（显示依据）；M28（写内容时带出处）；M17（提炼教训） |
| `target_id` | 目标的 id：`block_id` / `memory_id` / `material_id` / `idea_id` / `round_id` / `claim_id` | 产出方 | 同上；界面点开能跳到原文 |
| `target_version` | **只有 `block` 用**：引用时那个块的版本 | 产出方 | **M17 做失效判定**：现在版本比它大，说明引用内容被改过，这条记忆失效（I6） |
| `quote` | 引用片段的原文（可选） | 产出方 | 界面：用户不点开也能看到到底引了哪句 |

**不变量**

- **引用必须能定位**（I21）：`target_id` 必须指向真实存在的对象，指不到的引用不许出现。含糊地说一句"根据项目文档"不算依据。
- **`claim` 这一档只允许出现在编排层内部的对象及其留痕里**：C4 的主张内部、C11 的主张留痕可以引用 `claim`（审查角色指名反对哪一条）；**C7 的提案与备选、C9 的记忆不许**——跨层的永远是成品，不是原材料。
- 每条主张要么有 ≥1 条引用，要么**显式声明无来源**（`citations: []`），并在界面文本上标明"这是我的推断"。不允许"看起来有依据"但实际没有。
- 只有低可信材料的产出不能直接写入文档，见 C5 的不变量。

### C16 Project（项目）

项目的本体。它之前一直只以 `project_id` 的形式出现在别的契约里，自己没有契约——这是"建项目没有写入口"和"预算没有来源"两条缺口的共同根。

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `project_id` | 标识 | 建项目时 | 全局：记忆、检索、材料按项目隔离 |
| `name` | 项目名 | 建项目时 / 用户改 | 界面 |
| `template_id` | 用哪个模板（决定 9 个字段分区） | 建项目时 | M28 校验字段名合法；M2 渲染分区 |
| `config` | **项目级配置**：预算相关设置等 | 用户 / 系统 | L6 读它算预算；界面展示 |
| `created_at` | 建项目时间 | 建项目时 | 界面排序 |

**不变量**

- 建项目 = **一次事务**：建项目本体 + 按模板实例化 9 字段空 block 骨架，要么全成要么全不成。
- **建项目是应用函数，不是能力工具**：它不进注册中心、不需要 `description` / `tags` / `when_to_use`、不受 M23 管。没有人会让 AI 去挑"要不要创建项目"。
- 项目是记忆与检索的隔离边界：跨项目不可见。

### C17 Conversation（会话、消息与滚动摘要）

M15 的家。消息是"面向界面说过的话"，滚动摘要是"历史太长之后压出来的那段"。**不保存内部思考过程**（I12）。

**Message（消息）**

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `message_id` | 标识 | 产生消息的那一轮 | 被引用 |
| `project_id` | 属于哪个项目 | 同上 | 按项目隔离 |
| `round_id` | 哪一轮说的（主闭环与讨论区共用一套 id 空间） | 同上 | 和轮次对上 |
| `author` | `user` / 角色 id | 同上 | 界面区分谁说的 |
| `text` | 面向界面的文本 | 同上 | M13 组装上下文；界面 |
| `packet_id` | 如果这条消息来自某个角色，指向信息包（C4） | 同上 | 审计：这条是哪个包说的 |

**Summary（滚动摘要）**

| 字段 | 作用 | 谁写 | 谁读 |
|---|---|---|---|
| `summary_id` | 标识 | M15 | 被引用 |
| `project_id` | 属于哪个项目 | M15 | 按项目隔离 |
| `covers_round_ids` | 这段摘要盖住了哪些轮次 | M15 | 审计：摘要之后的原文还在，能对回去 |
| `text` | 摘要正文 | M15 | M13 组装上下文 |

**不变量**

- **M13 只管"这一轮"要带的东西**；历史消息继续保留，不因为进入新一轮就丢。
- **超过预算就开始摘要**，然后从这一轮开始重新计算对话历史上下文。
- 分工不许越界：**M15** 决定"带全量历史还是带摘要"；**M24** 只按 `priority` 裁、不做语义判断；**M13** 一个 token 都不裁。
- 摘要**不是删除**：`covers_round_ids` 盖住的原文仍然留在消息表里，摘要只是"带进上下文的那一份"换成它。

## 5. 层间接口（每层对外暴露什么）

这一节定的是**层与层之间怎么握手**。每个模块内部怎么实现——用什么框架、串行还是并行、prompt 怎么写——全部自由；但**跨层只有一个入口**：下面这些接口，加上 §3 里的契约对象。

### 5.1 三种跨层方式

| 方式 | 什么时候用 | 谁发起 | 携带什么 |
|---|---|---|---|
| **同步调用** | 上一层要下一层干一件事，等着拿结果 | 调用方 | 入参、返回值都是契约对象 |
| **黑板**（C12） | 跨层共享"这一轮的状态" | 只有拥有者写，其他人只读 | 已有契约的实例 |
| **事件**（C13） | 状态变了，通知关心它的层 | 状态的生产者 | 只有"什么变了" + 最小定位信息 |

配套规则：**跨层不直接读写对方的状态**（I20）。要给别的层东西，就调它的接口；要让别的层知道变了，就发事件，它自己回黑板读。

### 5.2 依赖方向（修订版）

| 层 | 可以调 | 黑板 |
|---|---|---|
| L0 注册中心 | L7 存储（注册条目要落库、要能改状态） | — |
| L1 交互层 | L2（所有 AI 动作）；L5 的**两件事**（M20 手动写入、M21 导出）；L7 存储**只读**（渲染文档、版本历史、卡片历史、trace） | **只读**；订阅事件，不发事件 |
| L2 编排层 | L0（读定义）/ L4 / L5 / L6；写黑板、发事件 | 唯一写者 |
| L3 通信层 | L7 存储（只写工作台与流水，不含业务语义）；不调其它层（它是通道，被所有层使用） | — |
| L4 记忆层 | L7 存储 | 只读 |
| L5 工具层 | L7 存储 | 只读 |
| L6 Harness | L7 存储（trace） | 只读 |
| L7 存储底座 | 不调任何层 | — |

**为什么 L1 可以直接调 L5 那两件事、可以直接读存储**：手动改文档、导出、渲染文档和回看历史都不属 AI 流程，不必绕经编排。手改照样走 M20（唯一写入口，`trigger = manual`），所以 I1 不受影响；反过来，如果这些都绕道 L2，编排层就平白多出一堆与 AI 无关的活。**读是只读的**，不碰任何状态，不违反 I20。

**为什么 L1 能读黑板、但不能发事件**：界面要渲染，就得多一份只读的状态源；但用户动作（点确认、打字纠正）不是"状态变化通知"，它是对 L2/L5 的调用。事件一律由状态的生产者发，事件的来源才唯一。

**为什么 L0 从"不调任何层"改成可以落 L7**：注册条目唯一写入口是 M27（§5.4），M30 还要经它改 skill 状态；如果 L0 一个层都不能调，这些写操作就没有落点。它照旧**不读黑板**，也不参与任何一轮的流转。

**为什么 L3 可以落 L7**：黑板持久化（C12）把工作台表（`rounds` / `board_regions`）放进了 L7，
而"写工作台与写账本能在同一个事务里"要求两者共享同一个事务边界。它照旧不参与业务判断。

### 5.3 每层暴露什么

| 状态 | 唯一写入口 | 谁读 |
|---|---|---|

| 本轮的上下文 / 主张 / 卡片组 / 已确认（C12 各区块） | 编排层 | 全部（只读） |
| 记忆（C9） | M17 写候选、M30 改状态 | M13 / M16 |
| 注册条目（C10） | M27 | M7 / M10 / M23 / M28 |
| 思路候选（C6） | M29 生成，用户改 `status`，**M13 组装上下文时标 `consumed`** | 勾选界面 / M13 |
| trace（C11） | M25 | 复盘 |

**这张表排掉了一整类问题**："这个状态到底谁说了算"。只要某个状态能找到两个写入口，就是设计有问题。

## 6. 全局不变量

不管实现怎么改，这些必须成立。模块可以拆可以合，这些不能破。

| # | 不变量 | 破了会怎样 |
|---|---|---|
| I1 | **唯一写入通道**：AI 不能直接改文档，只能产卡片，卡片确认后才写入 | "用户确认过"失去唯一入口，审计和回滚都失效 |
| I2 | **确认即冻结**：一组卡片点确认后整组不可变，要改只能开新一轮 | 无法回答"用户当时确认的到底是什么" |
| I3 | **可追溯**：AI 写的 block 带 `source_card_id`，卡片带 `citations` | 查不到来源，用户无法判断可信度 |
| I4 | **无来源不得进上下文**：材料包必须带 `ref` | 幻觉直接进文档 |
| I5 | **记忆两态**：只有 `active` 进常驻上下文 | 一次错误反馈污染以后所有生成 |
| I6 | **记忆会失效**：引用的 block 改动后，记忆标记失效 | 拿过期共识生成新内容 |
| I7 | **权限两档**：只判允许 / 禁止，没有审批态 | 权限逻辑分叉，行为不可预测 |
| I8 | **版本只增**：block 版本单调递增，文档版本只增不改，回退产生新版本 | 无法回溯，冲突检测失效 |
| I9 | **确认是原子的**：要么全部生效，要么全部不生效 | 文档出现半成品中间态 |
| I10 | **冲突不静默覆盖**：版本对不上时先问用户 | 用户手改的内容被无声抹掉 |
| I11 | **讨论区只产素材**：讨论区不产卡片，结论只能由主闭环生成 | 两条腿分叉，出现两套写入逻辑 |
| I12 | **不存思维链**：信息包和讨论留存只存结论与界面文本 | 上下文爆炸，而且没必要 |
| I13 | **只有工具和 skill 必须有描述**：这两个缺 `description` / `tags` / `when_to_use` 不许注册；角色、prompt 等只做统一管理，不要求 | AI 无法自行挑工具，注册中心沦为死目录 |
| I14 | **先组装上下文，再复述理解**：复述必须包含只有读了文档才知道的信息 | 不带上下文的复述等于抄一遍用户原话，没有价值；误读还会直接变成文档内容 |
| I15 | **一张卡只针对一个议题**；一批最多 5 张、没有例外，填充卡单独成批 | 一张卡拉七件事，用户没法答；卡片泛滥，用户窒息 |
| I16 | **填充卡是收尾**：只在整个任务没问题了才出现；不含填充卡的卡片组提交后不写文档 | 每轮都想写入，产生大量半成品版本 |
| I17 | **写范围由 M20 强制**：AI 只能写 `selected_fields` 里的字段，有选区时每条提案的 `target_label` 必须落在选区内 | 靠提示词自觉拦不住，AI 会顺手改别处 |
| I18 | **选区在轮内不变**：每轮用户输入重新选，轮内的循环沿用同一份 | 用户被反复打断，且无法回答"这轮改动的作用域是什么" |
| I19 | **黑板区块单写者**：`round` / `context` / `claims` / `card_group` / `confirmed` 只有编排层能写，其他层只读 | 一份状态有两个写者，就永远说不清"它现在是谁的意思" |
| I20 | **跨层不碰对方的状态**：要给别的层东西就调它的接口，要让别的层知道变了就发事件 | 层与层互相改对方的内部状态，任何一层都别想单独改 |
| I21 | **引用必须能定位**：每条引用都要指向真实存在的对象（`block` / `memory` / `material` / `idea` / `user_input` / `claim`） | 依据变成一句空话，AC3 的"可追溯"就无从验收 |

## 7. 端到端数据流（字段级）

**"跑通"的判据**：不是"界面能看到结果"，而是每一步**谁交给谁、传哪些字段、落在哪个契约上**都对得上。下面两张表就是验收 AC9 时逐行核对的依据。

### 7.1 主闭环（长任务）

| # | 谁 → 谁 | 传什么（字段级） | 契约 |
|---|---|---|---|
| 1 | 用户 → L1 | 写范围（在目录树上选的 schema 字段，可多选、可空）+ 本轮要求（原文） | C1 `selected_fields` |
| 2 | L1 → L2 `startRound` | `project_id` / `entry = main` / `user_input` / `scope`（C1 实例） | C1、C12 `round` |
| 3 | L2 → L3 | 写 `round` 区块：`round_id` / `project_id` / `entry` / `user_input` / `scope` / `phase = assembling`；发 `round.updated {round_id, project_id, entry, phase: assembling, from_phase: null}` | C12、C13 |
| 4 | L2 → L4 `assembleContext(round)` | 入参就是整个 `round` 区块 | — |
| 5 | L4 → L7 读 | ① C2 全文档块：`block_id` / `parent_id` / `schema_label` / `content` / `version`（**读全文**，同时生成 C1 的 `base_versions`）② M14 简报全文 ③ C9 里 `status = active` 的：`memory_id` / `type` / `content` / `citations` ④ 任务至今各轮的 `user_input` ⑤ C6 里 `status = selected` 的候选 | C1、C2、C9、C6 |
| 6 | L4 → L5 工具（按需） | `retrieve(project_id, query)` → C5（`source_type = retrieval`）；`searchWeb(query)` → C5（`source_type = web`）；两者都必须带 `ref` | C5 |
| 7 | L4 → L2 | **`{blocks, base_versions}`**：上下文块数组（每块 `source` / `ref` / `content` / `priority` / `credibility`）+ 这一轮的 C1 版本快照。**快照由编排层写进 C1**（round 区块只有编排层能写，I19） | C12 `context.blocks`、C1 |
| 8 | L2 → L6 `trim(blocks, project_id, model_ref)` | 返回 `{blocks, dropped}`。**预算由 L6 自己算**（叠 C16 的 `config`），调用方不传；**只按 `priority` 裁，不做语义判断** | C12 |
| 9 | L2 → L3 | 写 `context` 区块：`blocks` / `dropped` / `assembled_at` | C12 |
| 10 | L2 → L6 `complete`（复述理解） | 产出 C7：`card_id`（新）/ `kind = understanding` / `prompt`（**必须含至少一条只有读了文档才知道的信息**）/ `status = pending` | C7 |

### 7.3 基础设施：一轮里黑板、事件、存储各在什么时候动

| 时机 | 黑板（谁写哪个区块） | 事件 | 落到长期存储 |
|---|---|---|---|
| 0 建项目 | — | 无（界面自己发起的同步操作） | 项目 + 空 block 骨架（C2） |
| 1 开轮 | 编排层写 `round`（`phase = assembling`） | `round.updated`（开轮那一次：`from_phase = null`） | 消息记录 |
| 2 组装 | 编排层写 `context`（`blocks` / `dropped`） | `round.updated`（`assembling` → `restating`） | — |
| 3 复述理解 | 编排层写 `card_group` | `card_group.updated`；`round.updated`（`awaiting_user`） | 卡片历史 |
| 4 生成 | 编排层写 `claims`（含审查的 `challenge`）；工具产出 C5 | `tool.invoked`（调工具时）；`round.updated`（`working`） | — |
| 5 裁决 | 编排层写 `card_group`（含用户 `answer`）→ `state = confirmed` | `card_group.updated`（`state = confirmed`，`has_fill_card = false`） | 卡片组历史 |
| 6 成稿 | 编排层写 `card_group`（填充卡） | `card_group.updated`（新的一张卡） | — |
| 7 写入 | — | `card_group.updated`（`confirmed`，`has_fill_card = true`）→ `doc.changed` | C2 块 + C3 版本；回填 `result_version_id` |
| 8 收尾 | 编排层写 `confirmed` | `memory.updated`（候选）+ `round.updated`（`phase = done`） | C9 候选 + C11 trace |

**每一步要么有事件，要么上面那张覆盖表里写了"为什么不需要"。** 一轮里除 `registry.updated`（它跟着 M30 的验证动作走，不绑在轮次上）之外的 7 个事件，各自出现的位置就是这张表。

**黑板只放当前这一轮。** 一轮结束时，该长期留下的（文档、版本、卡片历史、消息、记忆候选、trace）落到 L7，这一轮的区块就可以清了——否则黑板会慢慢变成第二个数据库，谁都不知道该信哪一份。

### 7.4 一图看清两条链路

**入口一：主闭环（长任务）**

```
用户选 schema 字段（写范围，可什么都不选）+ 输入要求
   │
   ↓
M13 组装上下文（读全文，记 base_versions）←─┐（用户纠正理解时回到这里）
（文档 + 简报 + active 记忆 + 材料              │（讨论区勾选的候选也在这里进）
 + 任务至今的全部输入）                        │
   │                                          │
   ↓                                          │
复述理解 → understanding 卡 ───────────────────┘
   │  用户确认
   ↓
┌─→ M24 裁剪（只按 priority 裁）
│      │
│   产出角色（互不依赖，可并行）：C4 信息包，用工具就产 C5
│      │
│   审查角色（串行，读全部 claims）：challenge 主张
│      │
│   M8 汇总：合并 / 去重 / 判分歧
│      │
│   ┌──┴─── 卡住了吗？ ───┐
│ 缺信息 / 冲突           没问题了
│   │                       │
│ M9 组卡片组（≤5 张）   M28 成稿 → 一张填充卡（提案数组）
│   │                       │
│ M5 逐张回应            用户确认
│ （提交前可回头改）        │
│   │                  M20 校验版本 → 写入 → 产生文档版本
│ 提交 → 整组冻结           │
│   │                  M12 事件 / M17 提炼候选记忆 / M25 trace
└───┘ 回「M24 裁剪」继续完善（这一组没有填充卡，不动文档；
      用户的回应作为新的上下文块补进去，不重头读一遍文档）
```

**入口二：讨论区（只产素材，不产结论）**

```

                  │
                  ↓

                  │
                  ↓
           一轮结束，「整理成提案」
                  │
                  ↓
           M29 整理成思路候选（C6）
                  │
                  ↓

                  │
                  ↓

```

## 8. 开放问题

层间接口和字段级数据流已经定完（§5 / §7），下面剩下的都是**层内**或**产品口径**的问题。

| # | 问题 | 影响 |
|---|---|---|
| 1 | 角色的主张之间怎么判"说的是同一件事"（M8 合并去重的判定标准） | C4 / M8 |
| 2 | 编排层内部怎么组织：串行还是并行、DAG 怎么画（层间接口已定，只剩层内实现） | M7 |
| 3 | 主闭环这个循环什么时候停——什么算"没问题了"，谁来判定 | M8 / M9 |
| 4 | 主闭环按什么挑参与生成的角色：硬表（字段 → 角色），还是让 AI 判断 | M8 |
| 5 | 讨论区的角色是 M7 预选 + 用户增删换，还是完全由用户自己挑 | M7 / C14 |
| 6 | 项目简报的第一批内容从哪来（逐条添加需要个起点） | M14 |
| 7 | 简报加满 120 行之后按什么规则淘汰 | M14 |
| 8 | 填充卡 `op = append` 时 `content` 的确切形态（一整条还是一段） | C7 |
| 9 | 模板能否自定义、能否换 | C10 |

| 11 | M30 怎么算"该晋升"：用多少次、采纳率多少才算数 | M30 |
| 12 | `tags` 的受控词表——自由打标签，AI 就挑不中工具 | C10 |
