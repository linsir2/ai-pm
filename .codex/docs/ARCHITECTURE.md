## 2. 包结构与依赖规则

目录名跟 PRD 里的层名一一对应，谁看都知道哪层在哪儿：

```
src/pmstudio/
  kernel/            # 横切设施：Clock / IdGenerator / 错误基类（不含业务状态）
  contracts/         # 公共契约——层与层之间唯一共享的东西
    models/          #   C1–C17 契约对象
    interfaces/      #   CONTRACTS §5.3 的层间接口（Protocol）
  communication/     # L3 通信层：黑板 + 事件流
  registry/          # L0 注册中心
  interaction/       # L1 交互层
  orchestration/     # L2 编排层
  memory/            # L4 记忆层
  tools/             # L5 工具层
  harness/           # L6 Harness 层
  storage/           # L7 存储底座
  bootstrap/         # 装配根：唯一允许 import 具体实现的地方
devtools/            # 开发期工具（导入守卫等），不是产品代码
seeds/template.initial.json     # 附录 B 的 9 字段模板，是数据不是代码
tests/               # 与上面同名的目录，一一对得上
```

注意别混：仓库根的 `devtools/` 是开发期工具，产品代码里的 `src/pmstudio/tools/` 是 **L5 工具层**。

### 2.1 承重规则（只有一条）

**层与层之间只认公共契约，不认实现。**

1. 任何一层只允许 import：`kernel`、`contracts`、`communication`，加标准库和三方库。
2. **层与层之间永不互相 import**——不管 import 的是实现文件还是别的什么。要用别的层的东西，就用 `contracts/interfaces/` 里已经说好的接口；被调方去实现那个接口，两边在 `bootstrap/` 里接起来。
3. **唯一的例外是 `bootstrap/`**：它的职责就是接线，只有它 import 具体实现。
4. `storage`（L7）不读黑板，所以它只依赖 `kernel` + `contracts`。

跨层流转的只有三样东西，而且都装着契约对象：**黑板**（这一轮的状态）、**事件**（状态变了）、**接口调用**（入参返回值都是契约对象）。

### 2.2 为什么这么切

目标是"每个模块能被独立开发、独立替换"。判据不是文档写了"解耦"，而是：**给一个模块喂测试替身，它能单独跑测试，不需要其它模块存在**。

这条规则是"内聚"和"可读"一起换来的：谁依赖谁一眼能看出来（只看它 import 了哪些包），换一层实现不用动别的层的代码，加一层也不用回头改旧层。

## 3. 契约的表达约定

| 约定 | 做法 | 换来什么 |
|---|---|---|
| 冻结 | 所有契约模型 `frozen=True` | I2"确认即冻结"变成类型事实；改动靠产出新实例，不靠就地改 |
| 不许多余字段 | `extra="forbid"` | 字段名写错当场炸，而不是静默丢字段 |
| 判别联合 | C7 用 `UnderstandingCard \| QuestionCard \| ConflictCard \| FillCard` 按 `kind` 分派 | "分歧卡用 `options`、填充卡用 `proposals`"不用写注释，写错就挂 |
| 引用必填 | C4 主张的 `citations` **必填无默认值**：省略=报错，`[]`=显式声明无来源 | 精确实现"要么 ≥1 引用，要么显式声明无来源"，没有第三种含糊状态 |
| 兼容性 | 加字段兼容，改含义/删字段不兼容；持久化记录带 `schema_version` | 与 CONTRACTS §0 的约定一致 |

**契约里不许出现的东西**：自然语言字段（除非它就是给人看的）、思考过程（I12）、可空到没有语义的字段。

## 4. 端口与能力

### 4.1 读写能力分离

L7 对 L1 / L4 / L5 / L6 只暴露**只读视图**；写能力在装配时只发给对应层的唯一写入口：

| 写能力 | 只发给 |
|---|---|
| `DocumentWriter` | M20 文档写入 |
| `MemoryWriter` | M17 写候选 / M30 改状态 |
| `RegistryWriter` | M27 |
| `TraceWriter` | M25 |

这样 CONTRACTS §5.4 的"写入口一览"从文档里的一句声明，变成类型系统里的事实——**L1 手里根本没有能写文档的对象**（I1）。

### 4.2 黑板单写者

黑板（C12）提供一个只读视图和一个写句柄。**写句柄只注入编排层**（I19）；其他层拿到的是只读视图。黑板 API 里**没有 `subscribe`**——通知只归事件（C13），两套通知机制并存会让人不知道订哪个。

### 4.3 窄发布器

事件由**状态的生产者**发（C13）。为了让这条不靠自觉，装配根给每个生产者注入一个**只能发它那几种事件的发布器**：

| 生产者 | 能发的事件 |
|---|---|
| 编排层（L2） | `round.updated` / `card_group.updated` |
| M7 讨论编排器 | `discussion.utterance_added` |
| M20 文档写入 | `doc.changed` |
| 记忆层（L4，含 M17 / M30 / 失效判定） | `memory.updated` |
| M27 注册中心 | `registry.updated` |
| 工具层（L5） | `tool.invoked` |
| Harness（L6） | `generation.failed` |

注意 `memory.updated` 有**三个生产者**（C9 的 `status` 本来就有多个写者），所以守卫规则是 `event_type → 允许的生产者集合`，不是"一事件一生产者"。

## 5. 术语落地：能力工具 vs 应用函数

（术语来源见 `DECISIONS.md` §0.1。）

| | 能力工具 | 应用函数 |
|---|---|---|
| 是什么 | 给 AI 用的能力：联网搜索、检索，以及以后设计的同类工具 | 流程里固定的一步：创建项目、写入文档、导出、回退 |
| 进注册中心（C10） | 是 | 否 |
| 要 `description`/`tags`/`when_to_use` | 是（缺一不许注册，I13） | 否 |
| 能被 AI 自己挑 | 是（M10 按 tags 挑） | 否 |
| 受 M23 权限约束 | 是 | 否 |
| 代码位置 | `ports/tools/` 下的能力工具端口 | `ports/services/` 下的应用服务 |

**这条区分的实用价值**：防止以后所有函数都挂上 tags 往注册中心里塞，把 M10 的挑选空间稀释掉。

## 6. 通信层的实现口径

黑板与事件流在框架阶段就是**真实现**（分发方式——进程内还是消息总线——是运行时选择，不影响契约）。

### 6.1 黑板

五个区块，每个区块单写者；只放**当前这一轮**的状态，一轮结束把该长期留下的落 L7（否则黑板会变成第二个数据库）。

**介质：内存。** 代价说白：进程重启 = 当前轮丢失，用户得重开一轮。后续做持久化时，**"轮次状态持久化归哪层"要单独决策**——CONTRACTS §5.2 目前只允许 L6 落 trace 到 L7，别顺手把持久化塞进 Harness。

### 6.2 事件流

八种事件，一个状态对象只有一个事件类型；payload 只带最小定位信息，细节回黑板读。

**重入语义**（文档没定，这里定死）：`publish` 异步、按订阅顺序 await；处理器执行期间产生的**嵌套发布排队**，当前处理器返回后再排空；同一轮内 FIFO。`doc.changed` → 记忆失效 → `memory.updated` 这条链就靠它确定行为。

**事件是只读广播**：订阅者据此回黑板读，不能借它反向改别的层的状态。推送不是调用。

## 7. 存储

SQLite + SQLAlchemy 2.0。三个不变量在存储层落实：

| 不变量 | 怎么落实 |
|---|---|
| I8 版本只增 | 文档版本 append-only；`seq` 单调；回退**产生新版本**，不删不改历史 |
| I9 确认原子 | 一次卡片组确认 = 一个事务，要么全生效要么全不生效 |
| I10 冲突不静默覆盖 | 写入带 `expected_version`，对不上就拒绝，由上层产卡问用户 |

**改动与回退的原子单位 = 一个文档版本**：`submit` 一次卡片组确认 = 一版（带 `group_id`，所以"撤销某次 AI 写入"= 回退到该组之前那版）；`manual` **一次显式保存 = 一版**；`rollback` 本身也产生新版本。

**存储套件要对每个 adapter 跑**：不能只测内存实现，否则真 adapter 的错误永远测不出来。

## 8. 横切

| 件 | 口径 | 为什么 |
|---|---|---|
| `Clock` | 注入，测试里可控 | 断言里不允许出现真实时间 |
| `IdGenerator` | 注入 | 断言里不允许出现随机；轮次 id 全局唯一、主闭环与讨论区共用一套 id 空间 |
| 配置 | 项目级配置（C16 Project 的 `config`） | 预算这类设置是项目配置，不是散落的常量 |
| 预算 | **L6 内部算**：`模型窗口 − 输出预留 − 系统开销`，叠项目配置 | 调用方不传预算；`trim` 只按 `priority` 裁 |
| 错误 | `generation.failed` 必须带**失败在哪一步、人话的原因、能不能重试** | AC12：界面要展示原因，不能只转圈 |

## 9. 守卫

### 9.1 导入守卫（架构守卫）

用标准库 `ast` 解析每个 `.py`，得到它的 import 集合，按 §2 的声明表断言，违反就红并打印"哪个文件第几行 import 了谁"。

**必须配违规夹具**：拿一段故意写错的代码喂进去，断言检查器真的会红。没有这个夹具，检查器自己坏掉时你只会看到一路绿灯。

### 9.2 漂移守卫

把 `CONTRACTS.md` 的契约总表、各契约字段表首列、C13 的事件表，以及 I1–I21、AC1–AC15，与代码里的模型字段、事件枚举、守卫登记表逐一比对，不一致就红，失败信息直接说"改代码或改文档，二选一"。

**先做显式映射表 + 完整性断言，稳定后再转真解析。** 手抄一份清单等于制造第二个真相源，这条要盯着。

## 10. 未实现模块怎么表示

**不建桩、不建空壳、不写假实现。未实现就是不存在。**

装配处维护一张**显式的缺失清单**：哪个端口还没有实现、归哪个模块。测试断言这张清单与实际情况一致——实现接上去，清单里那行就删掉。

这样"没做"是可见的、可枚举的，而不是藏在某个返回常量假数据的桩里。框架阶段唯一允许的替身是**测试里的 test double**，生产代码里一个都没有。

## 11. 工作方式

- **TDD**：测试先写、先红，再写实现。每个契约、每个守卫、每个能力对象都先有用例。
- **质量门**：`pytest` 全绿；`ruff check` + `ruff format --check`；`contracts` / `ports` / `l3_comm` 行覆盖 100%。
- **最容易出的假绿灯**（写的时候盯死）：守卫没配违规夹具；只用 mock 断言"被调用过"而不回读状态；`pytest.raises` 断言太宽；漂移测试手抄清单；存储只测内存 adapter；断言里出现真实时间或随机数；AC9 走查只验函数名不验契约对象。
