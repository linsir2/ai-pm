## 0. 一页看懂

```
ai-pm/
├── backend/                     Python 后端（现在做）
│   ├── pmstudio/
│   │   ├── contracts/           ★ 唯一共享：16 个跨层契约 + 骨架形状 + 层间接口 + 不变量
│   │   ├── communication/       L3 骨架实现：黑板 + 事件流        ← 主干
│   │   ├── registry/            L0
│   │   ├── orchestration/       L2（含唯一一个层内契约 C4）
│   │   ├── memory/              L4
│   │   ├── tools/               L5 ── capabilities/ + services/
│   │   ├── harness/             L6
│   │   ├── storage/             L7
│   │   ├── api/                 前端契约的实现侧
│   │   ├── common/              标识 / 时间 / 错误（硬规则：只准这三样）
│   │   └── bootstrap/           装配根：唯一 import 具体实现的地方
│   ├── seeds/                   模板等初始数据
│   └── tests/                   与上面一一对应
├── frontend/                    React（推迟）
└── .codex/docs/                 设计文档
```

三句话：

1. **层与层之间只认公共契约，不认实现**——所以对外的东西全在 `contracts/`，层目录里只有内部实现。
2. **通信层是主干**，其余层是挂在主干上传递信息的节点；层内部怎么实现，这一阶段不管。
3. **L1 交互层不在后端**。它将来是 React 前端；后端只留 `api/` 承接前端契约。（D1/D2，已定）

| `storage/` | L7 | 三块：**账本**（项目 / block / 版本 / 卡片 / 消息 / 记忆 / 注册条目 / 材料 / 思路 / trace）、**工作台**（`rounds` ＋ 当前轮的 `board_regions`）、**流水**（`events`） | 不含业务语义；只增不改、事务与乐观锁在这里保证 |
| `api/` | 边界 | 前端契约的实现侧：动作入口、视图投影、事件推送口 | 不是新的一层；只做转发与投影 |

### 3.1 两处故意的物理隔离

**`tools/` 分成 `capabilities/` 和 `services/`。**
联网、检索这类是**能力工具**：进注册中心、必须有 `description`/`tags`/`when_to_use`、受 M23 权限管、AI 能自己挑。
建项目、写文档、导出这类是**应用函数**：流程里固定的一步，不进注册中心、不受权限管。
两类约束完全不同，混在一起，三个月后所有函数都会挂上 tags 往注册中心塞。**用目录隔开是最省事的防线。**

**C4 待在 `orchestration/` 里。**
它是唯一一个层内契约（角色产出的信息包，只在 L2 内部流转：角色 → M8 汇总 → M28 成稿）。放在自己层里，等于用位置声明"这东西不出门"。将来谁想让界面看主张，必须先讨论要不要动这个位置——这个摩擦是故意的。

### 3.2 `common/` 里的两样东西：标识与时间

**标识（id）——它解决的是"引用对得上"这件事。**

系统里有 19 类对象带 id：项目 / 文档 / 块 / 版本 / 轮次 / 卡片组 / 卡片 / 提案 / 备选 / 记忆 / 材料 / 思路候选 / 消息 / 摘要 / trace / 注册条目 / 信息包 / 主张 / 事件流水。

为什么必须**只有一个来源**：C15 的引用靠 `target_id` 定位真实对象（I21）。如果两层各自生成 id——一层用 uuid、一层用自增——引用立刻对不上；而且这种错不会当场炸，要等到"点开依据"才发现。所以生成器只有一处。

还有一条硬约束：**`round_id` 全局唯一**，主闭环轮次与讨论轮次**共用一套 id 空间**（C12 明确要求，靠 `entry` 区分）。

**时间——它解决的是"测试能复现"这件事。**

需要打时间戳的有六处：C16 的 `created_at`、C17 的消息时间与摘要时间、C13 事件的 `at`、C12 的 `ended_at` 和 `assembled_at`。

为什么不随手 `now()`：**断言里只要出现"现在"，测试就不可复现**。把时间收成一个可注入的东西，测试可以固定它；附带好处是全系统只有一处产生时间，将来要统一精度（秒 / 毫秒）只改一处。

**两者都极小**：一个 Protocol ＋ 一个真实现，不承载任何业务。

### 3.3 标识规格（已定）

**形式**：`<类型前缀>_<UTC 时间 YYYYMMDDTHHMMSS>_<8 位随机十六进制>`

例：`crd_20260914T103012_9f3a1c2d`

| 前缀 | 对象 | 前缀 | 对象 |
|---|---|---|---|
| `prj` | 项目 | `mat` | 材料包 |
| `doc` | 文档 | `ide` | 思路候选 |
| `blk` | 文档块 | `msg` | 消息 |
| `ver` | 文档版本 | `sum` | 摘要 |
| `rnd` | 轮次（主闭环与讨论区共用） | `trc` | trace |
| `grp` | 卡片组 | `reg` | 注册条目 |
| `crd` | 卡片 | `pkt` | 信息包（层内） |
| `prp` | 提案（填充卡的 proposals） | `clm` | 主张（层内） |
| `opt` | 备选（分歧卡的 options） | `mry` | 记忆 |
| `evt` | 事件流水 | | |

三条理由：**可读**（日志和 trace 里一眼看出这是什么、什么时候产生的）；**按 id 排序 ≈ 按时间排序**（调试时不用回头查时间戳）；**不依赖任何库**（Python 3.13 标准库还没有 uuid7，装库要联网）。

**不做强类型包装**：契约里 id 仍然就是字符串，避免每层都要转换；前缀词表集中在一处，保证一致。

## 4. `contracts/` 的内部构成

| 子项 | 内容 | 说明 |
|---|---|---|
| `models/` | **16 个跨层契约对象**：C1 C2 C3 C5 C6 C7 C8 C9 C10 C11 C12 C13 C14 C15 C16 C17 | 每个文件对应一个（或一族）契约；C4 **不在**这里 |
| `skeleton/` | C12 黑板五区块的形状（`round` 定形、`context` 定形、`claims` 占位）、C13 八个事件及 payload | 骨架是契约，只是形态是"骨架"；它的**实现**在 `communication/` |
| `interfaces/` | 每层对外暴露什么（CONTRACTS §5.3 的 Protocol）：L0 / L2 / L3 / L4 / L5 / L6（**L7 缺席**——文档没给签名，见 §11） | 接口放在契约里，是"层与层只认公共契约"的落地：调用方 import 接口、被调方实现接口、两边在 `bootstrap/` 接起来 |
| `invariants.py` | 跨对象、不属于单个模型的不变量 | 比如"一批最多 5 张""有选区时提案必须落在选区内"——这类写不进单个模型校验器 |

**C4 缺席的处理（两处灰色地带）**

1. `claims` 区块**只定"存在 + 单写者 + 只有编排层可读"，不装内容形状**；内容类型声明为 L2 自有，等 C4 定义了再回填。
2. 层间契约里有指回 C4 的引用（C14 的 `packet_id`、C15 的 `target_type = claim`）——这些位置**只保留不透明 id 引用（字符串），不解构 C4 内部**。引用关系是层间的，被引用物的形状是层内的，两者分开定。

| 6 | L2 → L4 | 要上下文 / 记忆 | C1 C2 C5 C6 C9 C12 C17 |

### 6.2 主闭环一轮的时序

> 记号：**写`区`** = 写黑板某个区块；**发** = 发事件；**调** = 跨层接口调用。

1. 前端 → `api.start_round(project_id, entry=main, user_input, scope)`，传 **C1**
2. 编排层取 `round_id` → **写`round`**（`phase=assembling`）→ **发 `round.updated`**（`from_phase=null`，开轮就是第一次 phase 变化）
3. 编排层 **调** `memory.assemble_context(round)`　【边 6】
   记忆层读 L7：C2 全文、M14 简报、C9(`active`)、C6(`selected`)、C17（历史或摘要）→ 产出 **`{blocks, base_versions}`**
4. 编排层把 `base_versions` 写进 C1，**写`context`**
5. 编排层 **调** `harness.trim(blocks, project_id, model_ref)`　【边 8】→ `{blocks, dropped}`，写回`context`
   —— 预算由 L6 自己算（模型窗口 − 输出预留 − 系统开销，叠 C16 的 `config`），调用方不传
6. `phase=restating`；**调** `harness.complete` 产出 **C7 `kind=understanding`**（复述里必须含至少一条只有读了文档才知道的信息）→ 组 **C8**（`state=answering`）→ **写`card_group`** → **发 `card_group.updated`**；`phase=awaiting_user`
7. 前端 → `api.submit_cards(group_id, answers)` → 编排层写回 `answer`
   - **若用户纠正**：`answer` 并入 `user_input` → **回第 3 步重新组装**（纠正可能改变该读什么）→ 直接生成，**不再出第二张理解卡**
8. `phase=working`；逐角色：**调** `harness.can_use` / `can_enter` → **调** `harness.complete` → 产出 **C4（层内）** → **写`claims`**
9. 需要工具时：**调** `tools.search_web` → **C5** → 由编排层追加进`context`；工具层 **发 `tool.invoked`**（`started` / `finished`）
10. **审查角色**读`claims`里全部主张 → 产出 `kind=challenge`，`citations` 用 `target_type=claim` 指名反对哪一条（**层内引用**）
11. M8 汇总：合并、去重、判分歧
    - **卡住了** → M9 组 **C8**（**≤5 张，一张卡一个议题**）→ **发 `card_group.updated`** → 用户逐张回应 → 提交 → `state=confirmed`（**整组冻结**）→ 用户回应作为新的上下文块（`source=user_input`、`ref=group_id`）补进`context` → **回第 5 步**继续完善。**这一组不写文档、不产生版本**
    - **没问题了** → 下一步
12. M28 成稿：内容候选 + 模板 + C1 + 相关 C2 → **C7 `kind=fill`**，`proposals[]` 每条含 `target_label` / `op` / `content` / `citations`；有选区时 `target_label` 必须落在选区内
13. **填充卡单独成批** → **写`card_group`** → **发 `card_group.updated`**；`phase=drafting`
14. 用户确认 → `state=confirmed` → **发 `card_group.updated`**（`has_fill_card=true`）；`phase=writing`
15. M20 收到确认 → 回黑板读这一组 → 取 `state=kept` 的提案 → 与 C1 的 `base_versions` 比版本
    - **对不上** → 产一张卡问用户，**不静默覆盖**
    - **对得上** → **一次事务**：写 C2 块（`version+1`、`source_card_id`）＋ 产生 **C3**（`trigger=submit`、`group_id`）＋ 本轮所有 `skipped` 的裁决卡落进"待确认问题"分区 ＋ 回填 `result_version_id`
16. M20 **发 `doc.changed`**（`trigger=submit`、`block_ids[]`）
17. 记忆层收到 → 按 `block_ids` ＋ `target_version` 做失效判定 → **发 `memory.updated`**（`status=invalid`）
18. 编排层收到 → 是这一轮自己写的 → `phase=done`、**发 `round.updated`**；**写`confirmed`**；调 M17 提炼候选记忆 → **发 `memory.updated`**（`candidate`）
19. 编排层 **调** `harness.record_trace` → 写 **C11**（含本轮主张留痕）→ L7
20. 轮末：黑板清空（长期状态已在第 15/19 步落 L7）

### 6.3 讨论区一轮的时序

1. 前端 → `api.run_discussion(project_id, user_input)`，新 `round_id`、`entry=discussion`
2. M7 从 **C10**（`kind=角色`）预选，**按 `allowed_entries` 过滤**，**上限 4 个**，每个给出选它的理由；用户可增删换，确认后开跑
3. 起 **C14**：`participants` / `state=running` / `utterances=[]`
4. 逐角色**串行**：M13 各自组装（C2 全文 + 简报 + `active` 记忆 + 材料 + 最近几轮 C14 的 `utterances`，超预算取 M15 的滚动摘要）→ `complete` → **C4** → `utterances.push` → **发 `discussion.utterance_added`**（界面逐条追加**想完之后的输出**）
5. 一轮结束：`state=finished`、`end_reason`（每人都说过 / 用户叫停 / 到上限）→ **发 `round.updated`**（`entry=discussion`、`phase=done`）→ 界面出现「整理成提案」
6. 用户点按钮 → `api.summarize_discussion` → M29 → **C6**（`status=pending`）
7. 用户勾选 → `api.select_ideas` → `status=selected` / `discarded`
8. **下一轮主闭环的第 3 步**：M13 把 `selected` 的候选转成 **C5**（`source_type=discussion`、`credibility=low`、`ref`=讨论轮 id + 候选 id）**并标 `consumed`**
   - 消费发生在**组装那一刻**、**整批一次**；这一轮若失败或没产出，用户要**重新勾选**

### 6.4 事件全景（8 个）

| 事件 | 生产者 | 订阅者 | 什么时候发 |
|---|---|---|---|
| `round.updated` | L2 编排层 | 前端（两个面） | 开轮、每次 phase 变化、收尾 |
| `card_group.updated` | L2 编排层 | 前端卡片面、M20 | 卡片组出现 / 更新 / 冻结 |
| `doc.changed` | L5 文档写入 | 编排层、记忆层、前端文档面 | 写入 / 手改 / 回退（三种来源共用一个事件） |
| `discussion.utterance_added` | L2 讨论编排器 | 前端讨论区面 | 每个角色说完一条 |
| `memory.updated` | L4 记忆层（含失效判定） | M16、M30、前端记忆面 | 候选产生 / 晋升 / 失效 / 退役 |
| `tool.invoked` | L5 工具层 | 前端 | 工具开始 / 结束 |
| `registry.updated` | L0 注册中心 | M7 / M10 / M23 / M28 | 注册条目状态变化 |
| `generation.failed` | L6 Harness | 前端、编排层 | 模型失败 / 超时 / 超预算；**必须带"哪一步、人话的原因、能不能重试"** |

**重入语义**：`publish` 异步、按订阅顺序 await；处理器执行期间产生的**嵌套发布排队**，当前处理器返回后再排空；同一轮内 FIFO。`doc.changed` → `memory.updated` 这条链靠它确定行为。

### 6.5 黑板生命周期

| 时机 | 发生什么 |
|---|---|
| 开轮 | 建当前轮的五个区块；只有编排层拿得到写句柄 |
| 轮内 | 只有编排层写（写即广播，见 §6.6）；其他层只读；`claims` 区块**只有编排层可读** |
| 轮末 | 该落账本的落账本、该留 trace 的留 trace，然后**删掉这一轮的区块**；`rounds` 那一条长期保留 |
| 崩溃 | 启动时扫到 `phase` 未结束的轮 → 标 `failed`、`end_reason = 进程重启`、**保留其五个区块**供查看"跑到哪了"；用户开新一轮时再删 |

**黑板持久化在 SQLite，但只装当前这一轮。** 不保留多轮的原因：历史轮次的东西各有各的家（文档与版本在 C2/C3、卡片在卡片历史、消息与摘要在 C17、结论在 C9、用了什么在 C11），再留几轮就是造第三个历史库，还会把 M13 组装上下文的工作重复落一遍。

### 6.6 通信层的位置与事件分发口径

**先把词说清："消息总线"有两个意思，别混。**

| 说法 | 指什么 | 做不做 |
|---|---|---|
| **逻辑总线** | 所有层挂上去、按约定发布／订阅、彼此不直接认识的那根通道 | **做**。这就是 **L3 通信层**（§5.2 原话：L3"本身就是通道"） |
| **外部消息中间件** | Kafka / Redis / NATS 这类独立进程的 broker | **不做**。单用户单机、一轮同步走，进程内分发够用；将来要换，契约不变（见下表最后一行） |

**黑板 ≠ 总线，但改黑板会经过总线。**
通信层承载两样东西：**状态**（黑板）和**通知**（事件）。黑板只是"状态"那一半的落点，它自己不派发——C12 明确写了"没有 `subscribe`：通知归事件管"，理由是"两套通知机制并存，用的人会不知道该订哪一个"。（这是实际做法：参照实现 `lite-interpreter` 的 `src/blackboard/` 里也一个 subscribe 都没有，订阅全在 `src/common/event_bus.py`。）

并且 8 个事件里**只有 2 个**的源在黑板（`round.updated` ↔ `round` 区块、`card_group.updated` ↔ `card_group` 区块）；另外 6 个讲的是长期存储（`doc.changed`、`memory.updated`、`registry.updated`）或瞬时动作（`discussion.utterance_added`、`tool.invoked`、`generation.failed`）。**总线是通信层，黑板是它的一半。**

| 项 | 定下来的 |
|---|---|
| 分发方式 | **进程内**（不引外部中间件） |
| 分发语义 | `publish` 异步、**按订阅顺序 await**；处理器执行期间产生的**嵌套发布排队**，当前处理器返回后再排空；同一轮内 FIFO |
| 异常隔离 | **一个订阅者抛异常，不阻断其它订阅者**。否则前端渲染出个小错，就会让"记忆失效"这种链条整段跑不掉 |
| **写入即广播** | 写某个区块时由黑板按映射表自动发事件：`round`→`round.updated`、`card_group`→`card_group.updated`、`context`/`claims`/`confirmed`→**不发**。消掉"写了状态忘了通知"这个失效模式 |
| **先提交后广播** | 事件必须在事务**提交之后**发；在事务里发，订阅者回读时读到的是旧状态 |
| **事件流水** | 每条 `publish` 落一张 append-only 表，回答"这件事到底发了没有" |
| 代价 | 单进程不能横向扩展（单用户，不需要） |
| 将来换中间件 | **契约不变**——C13 的 `type` / `payload`（最小定位信息）/ `at` 本来就够序列化；要改的只是接线与序列化，**重入语义要重新定义** |

### 7.2 三条引用规则（已拍板）

1. **跨层的引用不许指向层内对象。** C7 的 `proposals[].citations` 与 `options[].citations` 只允许 `block` / `material` / `memory` / `idea` / `user_input` 五档；`claim` 那一档只允许出现在 C4 主张数组内部。
2. **引用要透传到底，不许停在中间节点。** M28 从主张生成提案时，提案的 `citations` 透传**那条主张自己的依据**，而不是写"依据：某角色的第 N 条主张"。

> 一句话：**跨层的永远是成品，不是原材料。** 主张经 M8 / M28 加工成卡片文本后才跨层；引用一路透传到源头。

## 8. 目录级规则（写代码时的硬规矩）

1. **别人要用的东西必须进 `contracts/`。** 在层目录里发现一个"别人要用"的类型，就是放错了。
2. **层与层之间不互相 import。** 要用别的层，就依赖 `contracts/interfaces/` 里的接口；实现由 `bootstrap/` 接起来。
3. **接口的入参和返回值只能是契约对象或它们的集合。** "传一段自然语言给下一个模块"就是设计漏了。
4. **`common/` 只准放标识、时间、错误三样。**
5. **应用函数不许进注册中心。** 它写在 `tools/services/`，不是能力工具。
6. **层内契约不许出层。** 尤其 C4。
7. **不建桩、不建空壳。** 未实现的模块就是不存在；装配处留一张显式的缺失清单。

### 9.1 M0 拆步（每一步先写测试再写实现）

| 步 | 做什么 | 退出条件 |
|---|---|---|
| M0.1 | **存储底座**：建表、事务、乐观锁、`schema_version` | 能建项目、读文档、写块；版本冲突被拒；回退产生新版本；重启后数据还在 |

## 10. 做完之后有什么

1. **契约冻结**：17 个契约的形状与不变量有唯一出处，改它必须先改文档——不会再出现"两个说法"。
2. **层可以并行做**：给一个层喂契约里的接口替身，它能单独开发、单独测，不需要其它层存在。
3. **边界看得见**：谁依赖谁，看目录就知道，不用读 import。
4. **加一层不返工**：新层只需要实现 `contracts/interfaces/` 里的接口、挂到骨架上。
5. **前后端可拆**：前端是 React 时，契约可以直接导出成 TS 类型，`api/` 已经预留。
6. **每一步可验证**：里程碑的退出条件全部对得上 PRD 的 AC，不存在"感觉做完了"。
