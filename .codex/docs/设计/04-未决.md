- **模型接入：LiteLLM**（统一网关，假实现用于无密钥跑测试）

- **假实现只在测试里**（2026-09-22 定）：生产路径不提供"用假模型"的开关，不写无密钥降级分支；
  汇报"跑通"必须给真实模型证据。由 `tests/architecture/test_no_fakes_in_production.py` 强制。
- **写范围分两级**（2026-09-22 定）：硬约束只有"不得新增未授权 feature 子树"与"不得离开 13 章"；
  其余跑出本轮去处的内容不拒绝，改在草案卡上显式标注。详见 `02-编排与数据.md` §3①。
- **P0 拆成 P0a / P0b**（2026-09-22 定）：P0a 随 P1 计划（目录、工具链、四道守卫、端口声明），
  P0b（SQLite schema、仓储、UoW、LiteLLM 网关）随 P2 计划。
- **仓储端口声明在 `domain/ports.py`**（2026-09-22 定）：否则领域服务要反向 import `application/`。
- **跨上下文传参规则**（2026-09-22 定）：可以传 `shared/` 里的值对象，不能传对方的上下文实体；
  `Proposal → WriteInstruction` 的翻译发生在 `ProposalCommitter`。
- **block 类型由谁定**（2026-09-22 定）：功能字段查 `authoring/schema.py` 的固定表；章节级内容由
  提案显式给 kind。
- **小项**（2026-09-22 定）：事件名统一 `round.*`；Round 补 **R7**（只接受编制内的席位）；
  block id 用确定性 id；文档条目修订=原地替换+快照留旧值，出处修订=新增+`supersedes`；
  偏好区放 `Document` 内随版本化。

## C. 编排细节

**C1 内置哪些领域席位？**（需要你定）
建议通用组：数据规模与性能、权限与角色、业务规则、前端交互、技术方案；
触发组按输入匹配（导出导入 / 报表 / 通知 / 状态机 / 第三方集成 / 合规）。
范围守卫与陌生人读者在 v1 标"以后"。

**C2 席位一次推导多少条内容算合适？**（本轮新增）
影响：草案卡的长度与用户审阅负担。
建议：每个席位每轮**最多 5 条推导内容**，超出的进清单项或下一轮。

**C3 清单项的默认值由谁定？**（本轮新增）
影响：一键接受等于批量采纳，默认值错了会污染文档。
建议：默认值必须来自席位推导（带理由），不接受凭空默认；系统硬编码默认只允许用于结构类
（如"本节无要求"）。

**C4 "它提议的"默认不勾，如果用户从不勾怎么办？**（本轮新增）
建议：给"本批全接受"按钮，但**提议组单独计**；连续三轮全不勾时提示用户是否关闭席位提议。

**C5 Integrator 丢弃 finding 要不要留痕？** 建议要：可查"这条为什么没进问卷"。

**C6 答案轮的终止条件**：默认最多两轮问卷（已定），用户可主动"继续深挖"。

**C7 一轮最多几次席位轮？**（本轮新增）
影响：缺口多的输入可能要来回几轮，但轮数多了用户等得久、成本也高。
建议：**上限 3 次**；到上限仍有缺口就全部显式化（转开放问题 + 草案卡提示缺口），不再追问。

**C8 答案回来后"缩编席位"按什么规则选？**（本轮新增）
影响：重跑全部席位太贵，重跑太少又可能漏掉受影响的判断。
建议：按答案的 `target` 反查——**哪个席位的判断落在这些 target 上，或与这些 target 相邻，
就请它**；同时范围守卫这类要盯全局的角色每次都在（v1 暂无守卫，则每次带上 Analyzer）。

## D. 数据与一致性

**D1 用户手改 content 的排期？** **已定（2026-09-24）**：手改做进 v1。
落地方式：`POST /projects/{id}/edits`（`op = add / replace / remove`）→ `EditEntry` 用例
→ `ProposalCommitter.apply_manual`（与 AI 写入共用同一个 `DocumentWriter`，仍是唯一写路径）。
手改内容自动生成一条 `manual` 来源的编号（第七类 kind，且算可追溯链的终点）；
指令带 `manual=True`，落到的块打上 `manually_edited`。
**D5 的边界也一并澄清了**：`manually_edited` 拦的是"AI 静默覆盖"，人自己可以继续改、继续删。

**D2 偏好区存在哪？** 建议：独立区块，随文档版本化，但不进给工程师的正文。

**D3 block id 生成规则？** 建议：短随机 id + 语义前缀（`feat-a1b2`）。

**D4 版本快照存整棵树还是增量？** 建议：v1 存整棵树，diff 在展示时算。

**D5 出处账本会被导出吗？**（本轮新增）
影响：出处里含用户原话，可能带客户名或金额。
建议：导出文档时默认**只带编号与一句话摘要**，原文留在系统内。

另有两条**界面侧的实现选择**，记在这里免得下次当成 bug：

1. **复述卡锁定两类标签**：后端 `Claim` 规定"标签决定分区"，且猜测必须带假设、决策必须带拍板人。

   因此晚到，顶栏在这段时间显示"推送连接中"。要更快，就在建流时先发一行注释心跳（后端改动）。
3. **两处有意保留的小重复**：`labels.ts` 的 12 个功能字段中文名（真相源在后端
   `authoring/schema.py`）与进度条的 `MAX_SEAT_ROUNDS = 3`（真相源在 `round/step.py`）。
   要消掉它们，就给后端加一个读 schema / 常量的端点（与 F2 一起做）。
