# 03 · 案例与验收

> 两个案例按**当前模型**走完整轮（席位做三件事：发现 / 推导内容 / 判定要问什么）。
> 最后是 v1 主闭环的验收清单。

> **2026-09-22 第二次修订**：席位职责收成一件事——**只出专业意见**（疑问 或 判断），
> 把意见组装成 schema 形状的内容候选是 **Integrator** 的活。下面案例里的
> "发现 / 推导" 请按"疑问 / 判断"理解；标号 `A*` 的是席位意见，经整合者组装后才成为内容候选。
> 另外：**问卷不是必然环节**——没有必须问用户的东西时整段跳过，直接出草案。

## 案例 A · 从零开始，一轮里三件事

### A1 用户输入（第一轮）

> 想做个订单导出的功能，运营每天都要用，最好能按时间筛选，数据量大概几万吧。
> 另外登录页太丑了，顺便改一下，支持微信登录。月底必须上线。

### A2 主张（Analyzer 一次调用）

| 编号 | 主张 | 标签 | 去处 |
|------|------|------|------|
| E1 | 要做一个订单导出功能 | 需求 | s5 |
| E2 | 运营每天都要用 | 事实 | s3 |
| E3 | 最好能按时间筛选 | 需求 | s5 |
| E4 | 数据量大概几万 | **猜测** → 升格为假设 | s10 |
| E5 | 登录页太丑 | **偏好** | 偏好区（不进正文） |
| E6 | 登录页要改一下 | 需求 | s5 |
| E7 | 支持微信登录 | 需求 | s5 |
| E8 | 月底必须上线 | 约束 | s10 |

### A3 开场卡（两张）

复述卡列出 E1–E8，其中 E4、E5 带警示；底部只读一行"本轮将改动 s3 / s5 / s10"。
席位卡预选四位：数据规模与性能、权限与角色、前端交互、业务规则。用户全留。

### A4 席位轮（并行；每个席位只出一件事：专业意见）

**数据规模与性能**

- 疑问 `O1`：量级是估的，它是同步与异步的分界，必须问用户（依据 E4）。
- 判断 `O2`：单次导出应在 60 秒内完成；超过 5 万条时提示分批并拒绝本次导出
  （依据 E4；理由：量级在 1 万级，同步实现可满足，60 秒是同类导出的常见上限）。

**权限与角色**

- 发现：F2 谁能导出？导出文件和页面可见范围未必相同。
- 推导：`A3` → s5 异常与边界"无导出权限的用户不显示导出入口"（依据 E1；理由：
  订单数据含客户信息，导出即数据外流，默认按最小可见处理）；
  `A4` → s7 数据"导出文件对客户手机号做脱敏"（依据 E1 与 A3 的理由）。
- 判定要问：F2。

**前端交互**

- 发现：F3 微信登录要覆盖哪些端？
- 推导：`A5` → s5 主流程"登录页提供微信扫码入口，未绑定手机号时引导绑定"（依据 E7）。
- 判定要问：F3。

**业务规则**

- 发现：F4 时间筛选按创建时间还是支付时间？
- 推导：`A6` → s5 状态与规则"筛选条件为空时导出全部（受权限限制）"（依据 E3）。
- 提议（无锚点）：`A7` → s5 状态与规则"导出记录保留 30 天"（纯专业判断，
  依据为空，标 `proposed`）。
- 判定要问：F4。

### A5 整合

- **并上下文**：本轮主张 + 文档现状 + 四个席位交回的意见。
- **合并**：数据规模席与前端席关于"数据量"的疑问指同一字段，合并成一题，
  `asked_by` 保留两个席位。
- **组装**：疑问 → 题目；判断 → 内容候选（补 target、理由变 `rationale`、依据变 `refs`）。
- **编号**：席位交回的判断 → E9–E14（`agent_derived`）；无依据的那条 → E15（`agent_proposed`）。
- **出路**：5 道题（正好一批，无需降级）→ 出问卷；草案等答案回来再定。

### A6 问卷（5 题）

```
▾ s8 非功能需求
  Q1 单次导出的最大行数是多少？     [数据规模席 + 前端交互席]
     ○ 少于 1 万  ○ 1 万–10 万  ○ 超过 10 万  ○ 不确定
     选项含义：少于 1 万 → 同步导出即可；超过 10 万 → 必须走异步任务
  Q2 一次导出最多能等多久？         [数据规模席]
     ○ 10 秒内  ○ 1 分钟内  ○ 可以等几分钟（后台跑）
▾ s3 用户与受众
  Q3 谁能执行导出？                 [权限与角色席]
     ○ 运营专员  ○ 运营专员 + 主管  ○ 所有登录用户
▾ s5 功能需求
  Q4 时间筛选按哪个时间？           [业务规则席]
     ○ 创建时间  ○ 支付时间  ○ 两个都要
  Q5 微信登录要覆盖哪些端？          [前端交互席]
     ○ 只 PC  ○ PC + 移动  ○ 还没想好
```

### A7 作答与回灌

Q1 选"1 万 – 10 万"→ E16；Q2 选"1 分钟内"→ E17；Q3 选"运营专员 + 主管"→ E18；
Q4 选"创建时间"→ E19；**Q5 跳过** → 按题面后果落成 s11 开放问题（记录型）：
"微信登录的覆盖端未决定（待决人：PM）"。

答案带 `question_id` 进账本，然后**重新组装上下文、回到席位轮**：
数据规模席此时可以确认"同步导出够用、60 秒上限成立"，权限席可以确认脱敏口径。
这是"继续任务"，不是把选项消费掉就完。

### A8 草案卡（一张，三组）

```
【你说过的】5 条
   · feature#order-export 一句话描述 / 用户故事 / 主流程（E1 E2 E3）
   · feature#login-wechat 一句话描述（E6 E7）
   · s10 约束：月底上线（E8）

【它替你推的】9 条        ← 每条可展开看推导理由
   · 性能上限 60 秒（E9）         · 超限分批（E10）
   · 无权限不显示入口（E11）      · 手机号脱敏（E12）
   · 微信扫码 + 绑定引导（E13）   · 空筛选导出全部（E14）
   · AC-1 5 万条内 60 秒可下载（依据 E4 E9）
   · AC-2 无权限账号不出现导出按钮（依据 E1 E11）
   · AC-3 未注册微信用户扫码后进入绑定流程（依据 E7 E13）

【它提议的】1 条          ← 默认不勾
   · 导出记录保留 30 天（E15，无依据，纯专业判断）
```

用户全要（提议那条也勾了），并删掉 E12 里"脱敏"一句，改成"导出文件仅含订单号与金额"。

### A9 结果

文档 v0.1：新增两棵功能子树（**都由用户在输入里点名过**），s3 / s7 / s8 / s10 各补若干条目，
s11 一条开放问题。版本快照记录 17 个新 block。

**这一轮的看点**：席位不再只是提问——它把验收标准、异常边界、主流程细节直接推出来
（9 条），用户的工作从"从零填写"变成"审查与修改"；问卷只剩 5 题，都是**只有用户知道**的事；
唯一一条没有依据的提议被单独分组、默认不勾。

## 案例 B · 增量 + 技术方案 + 撞旧边界

前提：文档已在 v0.1，s4 的"本期不做"里有 **E30：本版不做定时导出**。

### B1 用户输入（第二轮）

> 运营说还是每天固定时间自动导出比较好，我想用 Redis 做个队列来做这件事。

### B2 主张

| 编号 | 主张 | 标签 | 去处 |
|------|------|------|------|
| E31 | 运营要每天固定时间自动导出 | 需求 | s5（与 s4 的 E30 冲突） |
| E32 | 用 Redis 做个队列 | **技术方案** | s9 待定 |
| E33 | 这是运营提出的 | 事实 | s3 |

### B3 席位

**技术方案席**

- 发现：F5 E32 是方案不是需求，先问它解决什么（不阻塞页面 / 支撑更大量 / 失败可重试）。
- 发现：F6 Redis 是新增的运维组件（进程、持久化、重启恢复），成本要你点头。
- 推导：`A8` → s9 技术决策"用 Redis 作为导出任务队列"（依据 E32）。

**数据规模与性能**

- 发现：F7 定时导出与手动导出是否共用筛选与权限？
- 推导：`A9` → s5 状态与规则"定时任务每日 06:00 执行"（依据 E31；理由：运营上班前要拿到数据）。

**权限与角色**

- 发现：F8 定时导出的文件发给谁，还是放在系统里等人来下？

**整合**

- 判定矛盾：E31 与 s4 的 E30 冲突 → 出矛盾题。
- **判定新增功能**：用户点名了"定时导出"这个能力，但没说它是不是独立功能。
  按 v1 规则，席位不能自己新建子树 → **出一题问用户**。
- 编号：A8、A9 → E34、E35（`agent_derived`）。

### B4 问卷（5 题）

```
▾ s4 范围与边界
  Q6 ⚠ 你上轮定过"不做定时导出"，这轮要"每天定时导出"，改哪个？
     A 方的依据：本轮输入（E31）
     B 方的依据：s4 本版不做（E30）
     ○ 改非目标，本版做   ○ 维持不做，记入后续   ○ 暂不决定
▾ s5 功能需求
  Q7 "每天定时导出"是订单导出功能的一部分，还是一个独立功能？
     ○ 订单导出的一部分   ○ 独立功能（会新建一棵功能子树）
  Q8 定时导出与手动导出共用一套筛选和权限吗？
     ○ 共用   ○ 各自独立   ○ 还没想好
▾ s9 技术方案
  Q9 你要队列是为了解决什么？     [技术方案席]
     ○ 不阻塞页面   ○ 支撑更大的数据量   ○ 失败可重试、不丢任务   ○ 其他
  Q10 接受新增一个需要运维的组件（Redis）吗？
     ○ 接受，本机跑就行   ○ 接受，但要能扛住重启   ○ 不接受，换方案
```

### B5 作答与回灌

Q6 选"改非目标"→ **E36（改判型）**；Q7 选"独立功能"→ **E37**（用户命名了新功能，
此时才允许新建子树）；Q8 选"共用"→ E38；Q9 选"失败可重试"→ E39；Q10 选"本机能扛住重启"→ E40。

E36 是改判型，系统做三件事：从 s4 的非目标里移除 E30；给 s4 的"本期范围"补一条；
在版本记录里写明"v0.2 撤销了 v0.1 的非目标 E30，依据 E36"。

### B6 草案卡

```
【你说过的】3 条：定时导出需求（E31）、运营提出（E33）、独立功能（E37）
【它替你推的】4 条：Redis 作为队列（E34）、每日 06:00 执行（E35）、
                    共用筛选与权限（E38）、失败可重试（E39）
【它提议的】0 条
另附一条修订：s4 撤销"不做定时导出"，依据 E36
```

### B7 结果

文档 v0.2：新增 `feature#scheduled-export` 子树（用户确认是独立功能后才建）、
s4 撤销一条非目标并补一条本期范围、s9 新增一条技术决策（含备选）、s7 新增 Redis 依赖。

**这一轮的看点**：技术方案先被降级为建议、先问目标；撞旧边界时出矛盾题而不是静默放开；
**"不新增 feature"这条规则逼出了一道关键问题**（这是不是独立功能），
用户点头之后才建子树——功能边界始终在用户手里。

## v1 主闭环的验收清单

在一次真实操作里能连续做到：

1. 输入一段零散想法 → 看到开场卡（两张），且复述里包含只有读了文档才知道的信息
2. 确认后 → 收到一张问卷；**同一件事不重复问**（同一去处的两件不同事可以各出一题，见
   `02` §11.0.6）、每题落到具体字段、每题带选项含义
3. 作答 → 答案变成带编号的出处（带 `question_id`）；跳过的问题落成 s11 开放问题
4. 草案卡按三组显示：**你说过的 / 它替你推的 / 它提议的**；每条带出处；
   推导类可展开看理由；提议类默认不勾选
5. 确认 → 文档新增内容，版本 +1；若撤销了旧结论，版本记录写明依据
6. 席位提出的是新功能时，系统必须先问用户，用户确认后才允许新建子树
7. 席位返回不可解析 → 整轮失败可重试，文档不发生任何写入
8. 全程没有任何一步让 AI 直接改动文档
9. **如果没有任何必须问用户的东西，整段跳过问卷，直接出草案**
10. 闭环区能看到每个席位交回的信息包（几条判断、几条疑问、依据是哪些编号），
    以及整合者做了什么（合并了几条、组装成几题）
11. 答案回来后**席位轮重新跑过一次**（缩编），受影响的判断被更新，而不是把选项直接写进文档
