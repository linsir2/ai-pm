# 01 · 规格（要做什么）

> 这份回答"要做什么、长什么样"。系统怎么跑在 `02-编排与数据.md`，
> 怎么算做对了在 `03-案例与验收.md`，还没定的在 `04-未决.md`。

---

## 1. 这是什么

单用户本地 Web 应用。产品经理把零散想法倒进来，系统用**领域专家席位**把它整理成
结构化产品文档；AI 只出草案，用户确认后才写入，每次改动产生一个版本。
第一个用户就是作者本人。

**非目标**：多用户与登录、AI 自动改文档、面向工程的排期管理。

## 2. 范围

**v1 做**：建项目 → 输入 → 复述 → 席位 → 问卷 → 草案 → 确认 → 写入 → 版本。
角色只有五个：Analyzer、领域席位、Integrator、Validator（纯代码）、人。

**v1 不做的整块**：讨论区、工具层（联网 / 上传 / 检索）、记忆维护、完整门禁、导出、
多项目界面。

**两条硬约束**：

1. 席位**不能新增 feature 子树**，只能在已有功能的字段内补内容。
   （例外：用户自己在输入里点名了一个新功能，那时允许新建。）
2. 席位的每条内容必须标出来源：**用户说的 / 它推导的 / 它提议的**。

## 4. 文档骨架

**结构固定、内容生长**：十三章焊死，只有功能子树可增长。

| # | 章节 | 合格标准（编排层据此判断能否收工） |
|---|------|----------------------------------|
| 1 | 背景与问题 | 有现状、问题、不做的代价；事实与推测分开 |
| 2 | 目标与非目标 | 至少一条目标带可验证判据；非目标至少一条且是真非目标 |
| 3 | 用户与受众 | 每个角色有场景与痛点；角色之间能区分 |
| 4 | 范围与边界 | 本期范围与本期不做无交集；边界写清谁处理 |
| 5 | 功能需求 | 每个功能有验收标准、异常与边界非空、能关联目标与角色 |
| 6 | 业务流程与交互 | 主流程与异常路径都能走通，无断头分叉 |
| 7 | 数据与接口 | 功能里出现的实体都有归宿；外部依赖都有对接方式 |
| 8 | 非功能需求 | 性能 / 可用性 / 安全 / 兼容 / 可观测 / 成本六项都有表态 |
| 9 | 技术方案与约束 | 关键决策有理由；至少一个被考虑过的备选 |
| 10 | 假设、约束与依赖 | 假设写明失败后果；依赖写明失联怎么办 |
| 11 | 风险与开放问题 | 所有未决的矛盾都有条目，并标注待决人 |
| 12 | 上线、验收与迭代 | 验收清单每条都能独立判定真假 |
| 13 | 版本历史 | 系统维护，不允许人工编辑 |

**功能子树字段**（每个功能一棵，缺字段就出题）：
名称 / 一句话描述 / 优先级 / 服务的目标 / 面向角色 / 用户故事 / 主流程 /
异常与边界（非空）/ 输入与输出 / 状态与规则 / 验收标准（至少一条）/ 依赖。

**block 树**：

```
document
├── meta：标题、版本、状态、更新时间、变更摘要
└── blocks[]
    ├── section(s1..s13)   固定，不可增删重排
    │   └── text / bullet_list / table / steps / acceptance / entity /
    │       interface / nfr / decision / assumption / constraint /
    │       dependency / risk / question / metric
    └── feature#<slug>     仅允许出现在 s5，功能子树根
```

规则：section 的 id 固定为 `s1`–`s13`；block 创建时分配**永久稳定 id**，内容或位置变化
都不改 id；删除留墓碑记录；**一次改动 = 一版**，版本只增不改，回退产生新版本。

## 5. 界面

**文档区占一大半（约 70%）**，右边是**闭环区**（约 30%）：那里是发言与相关思考的地方。
**问卷与草案是"到了需要的时候弹出来"的**，不常驻。

```
┌──────────────────────────────────────────────────────────────┬──────────────┐
│ 文档区（约 70%，主导）                                        │ 闭环区（30%）│
│                                                              │  本轮讨论流  │
│  s1 背景与问题                                               │ ─────────── │
│  s2 目标与非目标 ●                                           │ ① 数据规模   │
│  s5 功能需求 ◐                                               │   判断 2 条  │
│    ▾ feature#订单批量导出                                     │   疑问 1 个  │
│      一句话描述 …                                             │   依据 E4    │
│      性能上限 60 秒〔E9〕                                     │ ② 权限与角色 │
│      验收标准 AC-1 …〔E11〕                                   │   判断 1 条  │
│    （点编号跳回原文）                                          │ ③ 整合       │
│                                                              │   合并 2 条  │
├──────────────────────────────────────────────────────────────┴──────────────┤
│ 【输入区：把这一轮的想法丢进来】                   状态：等你回答 ●           │
├─────────────────────────────────────────────────────────────────────────────┤
│ 版本历史 ▸ v0.4 草案确认 · 3 个 block | 查看差异                             │
└─────────────────────────────────────────────────────────────────────────────┘

        问卷 / 草案卡 ── 需要时从右侧滑出抽屉（覆盖闭环区，不遮挡文档）
   ┌──────────────────────────┐
   │ 问卷 · 3 题              │
   │ Q1 …                     │
   │ ───────────────          │
   │ [交卷]  [先提交已答的]    │
   └──────────────────────────┘
```

- **文档区（约 70%）**：block 树渲染，章节带状态标记（空 / 有内容 / 有缺口 ◐ /
  有开放问题 ●）；每条内容后面挂出处编号，点编号跳回原文。v1 只读。
- **闭环区（约 30%，常驻）**：**本轮讨论流**。按时间展示这一轮走了什么——每个席位交回的
  信息包（几条判断、几条疑问、依据哪些编号）、整合者做了什么（合并了几条重复、组装成几题）。
  这里是"看发言、看相关思考"的地方。**只展示结构化的产出与依据，不展示模型的思维链。**
- **弹出层（问卷 / 草案卡）**：到了需要你决定的时候，从右侧滑出抽屉。
  选抽屉不选居中的模态，是因为答题时经常要**对照文档**——抽屉只覆盖闭环区，文档始终可见。
  一次一批，**交卷语义**：提交前可改，提交后冻结。提交后抽屉收起，讨论流接着往下走。
- **依据可见**：席位的每条判断/疑问都带依据编号；文档每条内容也带编号。
- **进度**：席位并行时显示已完成 / 进行中 / 待启动，而不是一个转圈图标。
- **失败**：显示失败在哪一步、人话原因、能不能重试。

界面**不做**：卡片里编辑内容（编辑归文档）、展示模型的思维链或推理草稿、审批流。

## 6. 与既有设计的关系

仓库的 `main` / `redesign` 分支上有另一套更完整的设计与后端实现（到 R1.5.1）。

- **关系**：参考思路，不搬契约、不复用代码。
- **借来的规矩**：卡片是问卷（交卷语义）、一批最多 5 张、一卡一议题、草案卡单独成批、
  卡片只有要 / 不要、复述必须带只有读了文档才知道的信息、分歧要暴露不抹平、
  一次改动 = 一版、未实现模块不建桩而用显式缺失清单、写范围由写入端强制。
- **本套设计自己的东西**：领域专家席位、七种标签定性、内容按来源三分组、
  可追溯不变式（refs → derived_from 必须落到用户输入或答案）。
