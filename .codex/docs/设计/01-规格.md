# 01 · 规格（要做什么）

> 这份回答"要做什么、长什么样"。系统怎么跑在 `02-编排与数据.md`，
> 怎么算做对了在 `03-案例与验收.md`，还没定的在 `04-未决.md`。

## 1. 这是什么

单用户本地 Web 应用。产品经理把零散想法倒进来，系统用**领域专家席位**把它整理成
结构化产品文档；AI 只出草案，用户确认后才写入，每次改动产生一个版本。
第一个用户就是作者本人。

**非目标**：多用户与登录、AI 自动改文档、面向工程的排期管理。

## 2. 范围

**v1 做**：建项目 → 输入 → 复述 → 席位 → 问卷 → 草案 → 确认 → 写入 → 版本。
角色只有五个：Analyzer、领域席位、Integrator、Validator（纯代码）、人。

**v1 不做的整块**：多项目界面。（其余几块都已按各自口径交付：工具层与导出 P5a–P27、
门禁只提示不挡写入 P5a、记忆本体 M6、讨论区 M9——见 `04-未决.md` E1/E4/F10。）

**两条硬约束**：

1. 席位**不能新增 feature 子树**，只能在已有功能的字段内补内容。
   （例外：用户自己在输入里点名了一个新功能，那时允许新建。）
2. 席位的每条内容必须标出来源：**用户说的 / 它推导的 / 它提议的**。

## 4. 文档骨架

**结构固定、内容生长**：十三章焊死，只有功能子树可增长。

> **2026-10-15 修订（两处）**：① 上面这句只对 `standard` 模板成立。章节集由模板决定
> （`02` §11.0.68，三锚点必存）。② **判据本身也由模板决定**（`02` §11.0.69）：下面这张表是
> `standard` 模板的取值——`min_entries`（最少条目数）与 `coverage`（该有却没有型 warn 谓词）
> 在 `infrastructure/templates/standard.toml` 里逐条声明，后端不再硬编码。
> 换模板就是换这张表；表里没有的章节，对那个模板不判。
**合格标准必须是可判据的**（2026-09-24 定，见 §7）：下面第三列写"算得出来的是什么"，
第四列写"算不出来、只能人看的是什么"——不假装都判了。

| # | 章节 | 判据（纯代码算，`ReadinessChecker`） | 只能人看（一律 `warn`，不参与"就绪"判定） |
|---|------|----------------------------------|----------------------------------------|
| 1 | 背景与问题 | ≥1 条非空 | 是否写了"不做的代价"；事实与推测是否分开 |
| 2 | 目标与非目标 | ≥2 条非空 | 目标是否真带可验证判据；非目标是不是真非目标 |
| 3 | 用户与受众 | ≥1 条非空 | 每个角色是否都有场景与痛点；角色是否分得开 |
| 4 | 范围与边界 | ≥2 条非空 | 本期范围与本期不做是否真的无交集；边界谁处理 |
| 5 | 功能需求 | 至少一棵功能子树；每个功能的必填字段非空（=`Document.gaps()`） | "能关联目标与角色"的语义质量 |
| 6 | 业务流程与交互 | 有功能却没有任何 `steps` 条目 → warn（**跨功能/端到端的流程与异常路径**归这一章，章节级 `kind=steps`；功能内部路径归 s5 的 `main_flow`，见 `02` §11.0.41） | 主流程与异常路径是否真的走得通 |
| 7 | 数据与接口 | 有功能带 `dependencies` 却无 `interface`/`entity` 条目 → warn | 实体是否都有归宿、对接方式是否写全 |
| 8 | 非功能需求 | 六个章节槽（性能/可用性/安全/兼容/可观测/成本）**各有非空条目** | 每一块的表态是否真的有实质内容 |
| 9 | 技术方案与约束 | 有技术约束却无 `decision` 条目 → warn | 关键决策的理由；是否真考虑过备选 |
| 10 | 假设、约束与依赖 | ≥1 条非空 | 假设是否写了失败后果；依赖失联怎么办 |
| 11 | 风险与开放问题 | 无阻塞型未决条目（阻塞型由 `Question.blocking` 标进条目文本） | 未决是否都标了待决人（生成时已带，仍需人核） |
| 12 | 上线、验收与迭代 | ≥1 条 `acceptance` | 每条验收是否真能独立判定真假 |
| 13 | 版本历史 | **不判**——导出时由 `Version[]` 生成 | — |

**s8 的六项（2026-09-24 拍板）**：给 s8 加六个固定子块（性能 / 可用性 / 安全 / 兼容 /
可观测 / 成本），"六项表态"于是从形容词变成"六个子块各有非空条目"。这是"结构固定、
内容生长"的正当用法：子块是骨架，不是内容。**判"有内容"一律按非空条目算，不按"有没有块"算**
（空子块不算内容——前端 `status.ts` 与后端 `ReadinessChecker` 用同一条规则）。

**随之必须解决的一件事（否则子块是死的）**：现在的 `Target` 只能落到"章节 / 功能 / 功能字段"，
落不到"章节下的某个槽"，所以没人能往这六个子块里写东西。因此把子块定义为**章节槽
（section slot）**，用 `Target.body("s8", field="performance")` 寻址——`field` 的合法值
分两个命名空间：有 `feature_slug` 时取**功能字段表**，没有时取**该章的槽表**
（`domain/shared/sections.py::SECTION_SLOTS`，与 13 章骨架同处，避免跨上下文 import）。
这条同时解掉 `04-未决.md` F8 里"章节级追加每次都新开一段"的一半。

**老文档不用迁移**：判据把"槽不存在"按"空"算，老项目照样能算就绪度，只是 s8 会显示"六项都缺"。

**功能子树字段**（每个功能一棵，缺字段就出题）：
名称 / 一句话描述 / 优先级 / 服务的目标 / 面向角色 / 用户故事 / 主流程 /
异常与边界（非空）/ 输入与输出 / 状态与规则 / 验收标准（至少一条）/ 依赖。

**block 树**：

```
document
├── meta：标题、版本、状态、更新时间、变更摘要
└── blocks[]
    ├── section(s1..s13)   固定，不可增删重排
    │   └── text / bullet_list / table / steps / acceptance / entity /
    │       interface / nfr / decision / assumption / constraint /
    │       dependency / risk / question / metric
    └── feature#<slug>     仅允许出现在 s5，功能子树根
```

规则：section 的 id 固定为 `s1`–`s13`；block 创建时分配**永久稳定 id**，内容或位置变化
都不改 id；删除留墓碑记录；**一次改动 = 一版**，版本只增不改，回退产生新版本。

## 5. 界面

**文档区占一大半（约 70%）**，右边是**闭环区**（约 30%）：那里是发言与相关思考的地方。
**问卷与草案是"到了需要的时候弹出来"的**，不常驻。

```
┌──────────────────────────────────────────────────────────────┬──────────────┐
│ 文档区（约 70%，主导）                                        │ 闭环区（30%）│
│                                                              │  本轮讨论流  │
│  s1 背景与问题                                               │ ─────────── │
│  s2 目标与非目标 ●                                           │ ① 数据规模   │
│  s5 功能需求 ◐                                               │   判断 2 条  │
│    ▾ feature#订单批量导出                                     │   疑问 1 个  │
│      一句话描述 …                                             │   依据 E4    │
│      性能上限 60 秒〔E9〕                                     │ ② 权限与角色 │
│      验收标准 AC-1 …〔E11〕                                   │   判断 1 条  │
│    （点编号跳回原文）                                          │ ③ 整合       │
│                                                              │   合并 2 条  │
├──────────────────────────────────────────────────────────────┴──────────────┤
│ 【输入区：把这一轮的想法丢进来】                   状态：等你回答 ●           │
├─────────────────────────────────────────────────────────────────────────────┤
│ 版本历史 ▸ v0.4 草案确认 · 3 个 block | 查看差异                             │
└─────────────────────────────────────────────────────────────────────────────┘

        问卷 / 草案卡 ── 需要时从右侧滑出抽屉（覆盖闭环区，不遮挡文档）
   ┌──────────────────────────┐
   │ 问卷 · 3 题              │
   │ Q1 …                     │
   │ ───────────────          │
   │ [交卷]  [先提交已答的]    │
   └──────────────────────────┘
```

- **文档区（约 70%）**：block 树渲染，章节带状态标记（空 / 有内容 / 有缺口 ◐ /
  有开放问题 ●）；每条内容后面挂出处编号，点编号跳回原文。v1 只读。
- **闭环区（约 30%，常驻）**：**本轮讨论流**。按时间展示这一轮走了什么——每个席位交回的
  信息包（几条判断、几条疑问、依据哪些编号）、整合者做了什么（合并了几条重复、组装成几题）。
  这里是"看发言、看相关思考"的地方。**只展示结构化的产出与依据，不展示模型的思维链。**
- **弹出层（问卷 / 草案卡）**：到了需要你决定的时候，从右侧滑出抽屉。
  选抽屉不选居中的模态，是因为答题时经常要**对照文档**——抽屉只覆盖闭环区，文档始终可见。
  一次一批，**交卷语义**：提交前可改，提交后冻结。提交后抽屉收起，讨论流接着往下走。
- **依据可见**：席位的每条判断/疑问都带依据编号；文档每条内容也带编号。
- **进度**：席位并行时显示已完成 / 进行中 / 待启动，而不是一个转圈图标。
- **失败**：显示失败在哪一步、人话原因、能不能重试。

界面**不做**：卡片里编辑内容（编辑归文档）、展示模型的思维链或推理草稿、审批流。

## 6. 与既有设计的关系

仓库的 `main` / `redesign` 分支上有另一套更完整的设计与后端实现（到 R1.5.1）。

- **关系**：参考思路，不搬契约、不复用代码。
- **借来的规矩**：卡片是问卷（交卷语义）、一批最多 5 张、一卡一议题、草案卡单独成批、
  卡片只有要 / 不要、复述必须带只有读了文档才知道的信息、分歧要暴露不抹平、
  一次改动 = 一版、未实现模块不建桩而用显式缺失清单、写范围由写入端强制。
- **本套设计自己的东西**：领域专家席位、七种标签定性、内容按来源三分组、
  可追溯不变式（refs → derived_from 必须落到用户输入或答案）。

## 7. 就绪度与交付（2026-09-24 定）

作者提问："我现在还差啥功能，感觉设计都还不够扎实。" 三条结论落在这里：
**能不能交付、凭什么信它、卡住了怎么办**。本节只写"要做什么"，怎么实现见
`02-编排与数据.md` §10 与 `06-前端.md` §2.2。

### 7.1 三级就绪度

| 级 | 判据 | 谁在算 |
|---|---|---|
| L1 结构级 | 13 章齐（D1）、功能字段齐（`Document.gaps()`） | 已有 |
| L2 章节级 | §4 第三列那些判据 | **新增** `ReadinessChecker`（纯代码，无模型） |
| L3 交付级 | 汇总判定：**blocker 项为 0** 就叫"就绪"（`ready = blockers == 0`） | **新增**，由 L2 结果汇总 |

输出一份清单，每条含：`section_id / code / title / detail / severity`，
`severity ∈ {blocker, warn}`。**只有结构缺失算 blocker，语义条款一律 warn。**
**同一 (章节, code) 只出一条**，明细写进 `detail`（如"login-wechat：名称、服务的目标…
还缺 5 项"），避免一次弹出二十条把人吓跑。

### 7.2 就绪度有两个消费者，缺一不可

1. **界面**：底栏与章节头显示"差 N 项"，点开看清单（见 `06-前端.md`）。
2. **智能体的上下文**：把清单追加在文档正文之后，让席位/整合者知道"本章按标准还缺什么"。
   否则它只是个仪表盘，不改变 AI 行为。

同时立一条硬规矩：**补缺口不等于填满**——拿不准就出题，不许为凑判据编内容
（写进提示词，并由 eval 盯住）。

### 7.3 交付物：一份 Markdown

- 形态：`GET /projects/{id}/export/markdown` → `text/markdown` 下载；标题 `产品文档 · <项目名>（vN）`。
- 头部盖章：`就绪度：通过 / 未通过（阻塞 N 项 / 提示 M 项）`。
- 空章显式写出"（本章为空：至少需要 N 条）"——**不许静默省略**。
- 功能子树按字段列出；非必填但为空的字段列在下面一行，方便继续补。
- **s13 版本历史由 `Version[]` 生成**（不读 block 树、不参与判据）。
- 附录 A：**本文引用过的**出处清单，**只给 `编号 + kind + 一句话摘要`**；原话（`raw_span`）
  留在系统内（`04` D5）。界面上可以看原话，导出里没有。
  **2026-10-02 收窄（P31）**：账本是**项目级、跨轮、只增**的，里面还有未被采纳的提案、
  被跳过的题与更早的轮次——那些编号在正文里**没有落点**，读者查不回去，列出来只会稀释
  真正的出处（真跑 59 份导出实测：附录 A 占全文 51%（中位），其中 **63% 从未被引用**）。
  所以准入判据 = **编号出现在本文任一条目的 `refs` 里**（13 章正文 + 偏好区都算）；
  没进本文的不静默消失，只在末尾写一行 `（另有 N 条出处没有被本文引用…）`。
  连带的一条：**名称也是正文内容**——功能名旁边的编号要挂出来（与界面 `FeatureBlock` 的
  出处胶囊一致），否则附录里会出现一个正文根本看不见的编号。
  **2026-10-04 再收一刀（M7 B）**：**只被第 11 章未决清单引用**的编号也不进附录——
  未决条目是"还没定的事"的记账，它引用的 `system_default` 就是正文那句话的回声，
  读者看不到第二个信息（真跑实测：附录 A 里 **47–95% 的行**是这种回声）。
  正文里的 s11 条目照旧挂编号（系统里按编号能查到），附录末尾用**两行**分别说清
  "只被未决清单引用的 N 条"与"完全没被本文引用的 M 条"。
- 偏好区**不进正文**；作为"附录 B · 不进交付物"保留（拍板 2026-09-24）。
- 渲染是**纯函数**：同一份文档 + 同一份账本，永远导出同一份字节。

### 7.4 门禁：提示，不挡

- 写入不受就绪度影响；导出允许"未就绪也能导"，但头部盖章。
- 理由：挡写入会让用户被自己没答的问题卡死（与 C6/C7"用户永远能走到草案卡"同一条原则）；
  "能不能交出去"本来就该由人拍板，系统只负责把缺的摆到台面上。

### 7.5 信任三件套（2026-09-28 落地，P5b）

1. **留痕一条通道**：`Round.dropped[]`，三个来源——`integrator`（模型申报 `dropped_opinions`）、
   `assembly`（归因对不上号）、`unaccounted`（装配层核出"既没说丢、也没交代落到哪儿"）。
   界面：每个席位包底部一行"它说的 N 条里，M 条没进卡片"。
2. **版本三件**：列表 / 差异（按 `entry_id` 的纯函数 diff）/ 回退（回到某一版时**产生新的一版**，
   历史版本一个都不删）。
3. **出处查询**：按编号给出原话（`raw_span` 只在界面给，不进导出，见 `04` D5）、来路、
   追溯链条、以及"现在被哪条内容引用着"。跨轮编号因此能跳回原文。
