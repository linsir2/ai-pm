## 0. 本文档的边界

只回答四件事：**做什么、分几层、有哪些模块、模块之间怎么串成一条数据流**。

> **两份文档的分工**：本文档回答"**做什么、为什么这么做**"——背景、目标、场景、产品决策和它们的理由、验收条件。
>
> 契约的字段级定义（每个对象有哪些字段、字段干什么、谁写谁读、有什么不变量）**只在 `.codex/docs/CONTRACTS.md` 里写一次**，本文档不重复。需要看"传什么"就翻契约文档；两份冲突时以契约文档为准。
>
> **工程与实现决策**（技术栈、代码怎么组织、边界靠什么保证）在 `directory.md`（§8 目录级硬规矩）与 `DECISIONS.md` §10（P1–P9）；某条决定是什么时候、为什么这么拍的，看 `DECISIONS.md`。
>
> 这条分工是硬要求：同一件事在两处各写一遍，迟早会不一致，然后没人知道该信哪份。

不回答：模块内部的代码结构、prompt 内容、数据库表结构。

## 1. 背景与问题

产品经理脑子里已经有大致的构思，但表达出来仍是自然语言——可能完整，也可能只有一个目标和几条零散描述。工程师需要的是可执行的东西：功能到底是什么、依赖什么、边界在哪里、做到什么算完成。

这中间缺一个可信的翻译与收口环节，它是产品到工程之间最容易失真的一段。失真在早期不被暴露，会在实现阶段以返工的形式集中爆发。

PM Studio 要占的就是这个位置：把一份构思**逐步**整理成双方都能确认、并且能继续使用的产品共识。同时给产品经理一个 AI 讨论区，用于创意指导——帮他想得更多更全，而不是替他做决定。

## 2. 目标与非目标

### 2.1 目标

- **G1 共识生成**：用户输入一段想法，系统**先复述理解**，再整理成结构化的产品文档，逐步收口成可确认的共识。
- **G2 创意讨论区**：角色群讨论产出思路，供用户挑选后带入主闭环。
- **G3 可溯源**：所有 AI 产出都带依据——引用了哪段文档、哪条结论、哪份材料。
- **G4 人在环上**：AI 永远不直接改文档，只能产出卡片，用户确认后才写入。
- **G5 沉淀复利**：用户的每次回应都成为下一轮生成的输入，不是一次性消耗品。

### 2.2 非目标

- 多人协作、登录鉴权、管理员后台。**系统只有一个用户角色。**
- 面向工程侧的排期、任务拆解、工时管理。
- AI 自动修改文档。
- 面向外部的开放 API、多租户。

## 3. 用户与场景

**用户**：产品经理，单人使用。无登录、无账号体系、无管理员。

| 场景 | 描述 | 入口 |
|---|---|---|
| S1 从零开始 | 只有一个目标加几条零散描述，需要把文档骨架搭起来 | 主闭环 |
| S2 补充规整 | 已有文档，让 AI 按上下文补充、规整、细化某一块 | 主闭环 |
| S3 研讨取思路 | 想法没想清楚，开讨论区跟角色群聊，拿到一批思路 | 讨论区 → 主闭环 |
| S4 反馈复利 | 对某次输出不满意，直接说出问题，下次生成要变好 | 卡片下方的输入框 |

## 4. 核心概念

> 每个对象的字段定义以 CONTRACTS.md 为准，这里只是导览。

| 对象 | 说明 | 关键性质 |
|---|---|---|
| 项目 Project | 顶层容器，可建多个 | 记忆、角色、文档、材料都以项目为边界；带**项目级配置**（预算这类设置）。建项目是**应用函数**，不是能力工具 |
| 文档 Document | 按模板字段分区的 block 树 | 一个项目一个文档；每个 block 有 id 与版本 |
| 模板 Template | 字段分区定义 | 是 **schema**，定义"填哪里"，不是内容本身。初版 9 个字段，见附录 B |
| 范围 Scope | 只管"改哪儿" | 写范围 = 用户在目录树上选的 schema 字段；读范围固定是全文；每轮重选、轮内不变 |
| 信息包 Agent Packet | 每个角色的一次输出 | 统一形态，必须带依据；**不保存思考过程** |
| 卡片 Card | 系统**卡住时向你求助**的方式 | 四种情形：确认理解 / 补信息 / 选一个 / 确认内容。卡片下面都有输入框。**一张卡只针对一个议题** |
| 卡片组 Card Group | 一次裁决的一批卡片，**每批最多 5 张** | 是中途的关卡，不是终点：提交前可回头改，提交后整组冻结，提交完继续干活。**填充卡单独成批** |
| 思路候选 Idea Candidate | 讨论区整理出的、可供勾选的思路 | 用户挑的是它，不是一屏聊天记录 |
| 材料包 Material Packet | 进入生成链路的外部信息 | 三个来源：检索 / 联网 / 讨论区。必须带出处 |
| 引用 Citation | 每条 AI 产出挂的依据 | 必须指向真实存在的对象（块 / 记忆 / 材料 / 思路候选 / 用户输入 / 主张），指不到的不算依据 |
| 记忆 Memory | 沉淀下来的事实、决定、教训、偏好 | 分候选与生效两态；只有生效的进常驻上下文；引用的内容改了会失效 |
| 项目简报 Project Brief | 项目级的 AGENTS.md | 一条一条加，逐条确认，控制在 120 行左右。见 §11 |
| 会话与消息 Conversation | 面向界面说过的话 + 历史压出来的滚动摘要 | **不保存思考过程**；M13 只管这一轮要带的，历史继续留着，超预算才开始摘要 |
| 注册资产 Registry Entry | 角色 / prompt / 工具 / skill / 模板 / 模型 / 编排策略 | 只存**定义**。工具和 skill 必须有描述和标签（AI 要靠它自己挑）；角色、prompt 等只做统一管理。用户可自行删除 skill |
| Skill | 从复利里收割出的可复用做法 | 领域级通用，不是具体问题的补丁 |
| Trace | 一轮用了哪些上下文、哪些工具 | 观测与复盘的入口 |

## 5. 分层

**8 层（含底座）+ 3 横切契约。**

| # | 层 | 一句话职责 |
|---|---|---|
| L0 | 注册中心 | 所有**定义**的家：角色、prompt、工具、skill、模板、模型、编排策略 |
| L1 | 交互层 | 用户看到的三个面：文档、讨论区、卡片 |
| L2 | 编排层 | 复述理解 + 角色调度 + 汇总生成 + 成稿 + 卡片组装 |
| L3 | 通信层 | 层间不直接读写对方的状态：要东西调接口，传状态走黑板，报变化走事件 |
| L4 | 记忆层 | 组装"这一轮该带什么上下文" |
| L5 | 工具层 | 联网、材料上传解析、检索、文档读写、导出 |
| L6 | Harness 层 | 模型接入、角色权限、预算与裁剪、观测、重试降级 |
| L7 | 存储底座 | 项目 / block 树 / 消息 / 角色 / 记忆 / 卡片历史 |

**横切契约**：结构化信息包、材料包、模板 schema。

**为什么 L0 和 L6 必须分开**：注册中心是**定义**（加一个角色、改一版 prompt 时它变），Harness 是**运行时行为**（换模型、调预算时它变）。一个存目录，一个做执行。推论：**权限的声明在 L0，权限的执行在 L6。**

**通信层为什么必须存在**——这里有个容易搞混的边界：

- **智能体之间**怎么调度、谁在什么时候读写共享状态 = **编排层内部的事**，换一种编排方式不该影响别的层，所以不对外暴露。
- **层与层之间**的流转 = 必须有通道。工具层跑完要告诉编排层、记忆晋升要通知检索、文档变了要告诉界面——层多了，没通道就没法协同运转。

所以通信层提供两个机制：**黑板**（共享状态放在哪）和**事件流**（状态变了怎么通知）。编排层怎么用黑板，是它自己的设计。

### 5.1 设计参照：文档即代码

这套系统和现有编程智能体工具高度同构——**它们生成代码，我们生成产品共识文档**。编程工具已经把"AI 改文件"的工程问题解完了，我们直接搬结构，不重新发明。

| 编程工具 | PM Studio | 位置 |
|---|---|---|
| 代码仓库 | 项目 | L7 |
| 源文件 / 文件树 | 文档 block 树 | M2 |
| commit / 回退 | 文档版本 | C3 |
| diff / PR / merge | 卡片 + 确认 | M9 / M20 |
| AGENTS.md / CLAUDE.md | 项目简报 | M14 |
| skills | Skill | L0 |
| subagent | 角色 | M6 |
| 工具调用 | 材料包 | L5 |
| lint | 模板字段校验 | M28 |
| tests / CI | 验收条件 | §13 |
| trace | 观测 | M25 |

从这套参照里搬过来的四条：

1. **patch + review + merge，绝不直接改文件。** 这就是卡片机制。
2. **上下文两层注入**：几乎每次都要的常驻；按场景才要的按需。对应 M14 与 M16。
3. **权限分档**：工程界用三档（自动 / 需确认 / 禁止），我们**只取两档：允许 / 禁止**——不是生产级管控，不需要审批态。代价是少一层安全网，收益是权限模型一眼看懂。
4. **多代理只踩三个坑**：死锁（依赖必须是 DAG）、无限循环（必须设最大轮次）、输出格式错误（必须校验 + 重试）。

### 5.2 Scope（范围）

**范围只管一件事：改哪儿。** 特调（谁来改）已去掉——角色选择归讨论区，用户在讨论区里自己挑智能体。

产品上的三条决策（字段定义见契约 C1）：

1. **用户圈的是"写范围"，读范围固定是全文。** 让用户同时决定读和写是上一版把范围搞复杂的根源。用户只需要说"我要改这里"，"要读什么才能改对"是系统的责任。
2. **每轮重新选，轮内不变。** 选区不跨轮保留——免得用户忘了自己还选着东西，导致改动落到意想不到的地方。
3. **什么都没选也可以。** 正常走主闭环，不限制写范围，由 M28 推导落位；保护只剩最后那张填充卡的确认。

**一个副作用（好的）**：有了选区，确认理解卡的复述天然就具体了——系统知道你圈的是"功能清单"，复述里就能说出位置，不会退化成复读用户原话。

## 6. 模块清单

编号用于后续模块 spec 引用。每个模块的输入输出契约见 CONTRACTS.md §4。

### L0 注册中心

**M27 资产注册中心** — 统一登记所有**定义**：角色、prompt、工具、skill、模板、模型、编排策略。
**工具和 skill** 必须带 `description`（它是什么）、`tags`（能力标签）、`when_to_use`（什么情况下用它），**缺一不许注册**——这是 AI 能自行挑选工具的前提；角色、prompt、模板这些只是解耦出来统一管理，有名字和本体就够了。只存定义，不存运行状态。

### L1 交互层

**M1 项目容器** — 创建 / 切换项目。新建项目 = 选模板 + 实例化空 block 骨架，走**应用函数**（不是能力工具），一次事务完成。另提供历史轮次与 trace 的回看入口。

**M2 文档编辑器** — block 树渲染与编辑，按模板字段分区展示；用户可手动编辑；版本历史与回退。不做任何 AI 相关决策。

**M3 范围选择器** — 用户在**目录树上选 schema 字段**，产出写范围。粒度是字段，不能选到细 block；允许多选；每轮重新选，轮内不变。

**M4 讨论区** — 悬浮球入口、角色群、消息流、用户发言；一轮结束后出现「整理成提案」按钮；展示思路候选供勾选。

**M5 卡片界面** — 卡片组展示，逐张回应、前进后退、返回修改、统一确认。每张卡片下有输入框，点按钮和打字地位相同。**不写文档**。

### L2 编排层

**M6 角色注册表** — 预设角色 + 用户自定义角色。每个角色是一等公民：独立人设、独立上下文、独立工具权限。**独立上下文的具体含义**：每个角色各自走一次 M13，同一个作用域、不同角色视角。

**M7 讨论编排器** — 决定谁发言、按什么顺序、什么时候停；按 skill 选择编排策略。默认一轮 = 每个角色各说一次。参与角色**上限 4 个**：先预选并给出选它的理由，用户可增删换，确认后才开跑。不判断内容对错，只调度。

**M8 共识生成器** — **每轮用户输入之后先复述理解**；然后汇总各角色的信息包（信封 + 主张数组，含审查角色提出的 `challenge`）、**逐条主张**合并去重、判断有没有分歧、产出内容候选。
四种判定：需要对理解 → 确认理解卡；信息不足 → 提问卡；角色矛盾 → 分歧卡；信息足够 → 内容候选。
分歧判断放在本模块，不单设模块。

**M9 卡片组装** — 把 M8 与 M28 的产出组装成卡片组（顺序：补信息的在前，确认内容的在最后），管理卡片状态。**确认前整组可改，确认后整组冻结。** 不做内容判断。

**M10 工具调用决策** — 哪个角色、在什么条件下、用哪个工具。工具从 M27 注册中心里按标签挑。

**M28 成稿器** — 内容候选 + 模板字段 + 作用域 → 按字段落位 → 边界校验 → 产出填充卡（写到哪 / 怎么写 / 写什么）。
与 M8 的分工：**M8 决定"说什么"，M28 决定"怎么说成符合文档结构的话"**。只处理本次涉及的字段子集，不走完整模板。

**M29 思路整理器** — 把一轮讨论的发言整理成结构化思路候选（一句话主张 + 出处 + 建议落位）。**不产结论、不产卡片**。它只把"聊出来的东西"变成"可以挑的东西"。

**M30 复利验证器** — 管理教训与 skill 的候选 → 验证 → 晋升 / 退役。**不允许人工直接把 skill 置为生效。**

### L3 通信层

层与层之间**不直接读写对方的状态**：要东西调接口，传状态走黑板，报变化走事件。这样任何一层的内部改造都不会牵动别人。

**M11 黑板** — 这一轮任务的共享状态。分五个区块：这一轮在干什么（round）、组装出来的上下文（context）、各角色产出的主张（claims）、当前卡片组（card_group）、已确认的结论（confirmed）。每个区块有明确的拥有者，别人只能读。区块定义见契约 C12。

**M12 事件流** — 状态变更通知。**事件只说"什么变了"，细节回黑板读**——这是黑板和事件的分工，缺一个都会退化：只发事件不带状态，订阅者拿到通知还得再问一圈；只共享状态不发通知，别人不知道什么时候该来看。事件表见契约 C13。

### L4 记忆层

**M13 上下文组装器** — 按优先级输出"这一轮该带什么"。输出带优先级标注的上下文块，**一个 token 都不裁**。

**M14 项目简报** — 常驻注入的那一小块。用户可直接编辑。详见 §11。

**M15 长对话管理** — 保存面向界面的消息与滚动摘要（C17）。**不保存内部思考过程。** 边界：**M13 只管这一轮要带的东西**，历史消息继续保留；**超过预算才开始摘要**，然后从这一轮重新计算历史上下文；带全量还是带摘要由 M15 决定。与 M16 的分界：M15 管"最近的全量"，M16 管"历史的按需"。

**M16 检索** — 从已确认结论、文档内容、上传材料里按需取用。

**M17 反馈与画像** — 从用户的回应里提炼两类产物：教训写入 M14，可复用的做法收割为 Skill 写入 L0。必须能回答"它改变了下一次生成的什么"。

### L5 工具层

**M18 联网搜索** — 输出统一成材料包。

**M19 材料上传与解析** — 上传 → 解析 → 进资料库（变成可检索的语料）。**它不是材料包来源，是准备动作**；之后被检索命中时才以材料包形式出现。

**M20 文档写入** — 卡片确认后的事务性写入；定位目标 block；校验版本防覆盖手改；每次写入产生一个文档版本。**AI 改文档的唯一通道。**

**M21 导出** — 把文档导出为可交付形态。

### L6 Harness 层

**M22 模型接入** — provider 抽象与调用。

**M23 角色权限** — **两组白名单**：`allowed_tools`（这个角色能调哪些工具）+ `allowed_entries`（这个角色能在哪些入口出现，比如只在讨论区发言的角色）。权限**只有允许 / 禁止两档**，两个判定 `canUse` / `canEnter`。预设角色可定制工具集（可有专属工具）；用户自定义角色只能从有限统一工具池里选，这是**注册时**的校验（M27）。只做执行，不做语义判断。

**M24 预算与裁剪** — 只管"能带多少"，按 M13 给的优先级裁。**不做语义判断。预算由 Harness 自己算**（模型上下文窗口 − 输出预留 − 系统开销，叠项目配置），不由调用方传进来。

**M25 观测** — 记录每一轮用了哪些上下文、哪些工具、最终写进了哪一版。

**M26 重试与降级** — 模型失败、超时、超预算时的重试与降级。必须向上抛 `generation.failed`，带**失败在哪一步、人话的原因、能不能重试**——界面要展示原因，不能只转圈。

### L7 存储底座

项目、block 树、文档版本、消息、角色、记忆、卡片与卡片组历史、材料。

## 7. 模块如何搭配

### 7.1 八条边界约定（分层的承重墙）

1. **AI 不直接改文档**：只能产卡片，卡片确认后才由 M20 写入。这是"用户确认过"的唯一入口。
2. **M13 说带什么，M24 说带多少**：M13 输出带优先级的上下文块，M24 只按预算裁剪。否则换模型时不知道改哪层。
3. **权限只有允许 / 禁止两档**，由 M23 执行，声明在 L0。**写范围由 M20 强制**：AI 只能写选区内的字段，不靠提示词自觉。
4. **M5 不写文档，M20 不改内容**：卡片界面只收集用户回应，写入只做机械落库。
5. **跨层传结构化契约，不传自然语言**：自然语言只出现在给人看的地方。
6. **L0 只存定义，L6 只做执行**。
7. **工具只吐材料包**。
8. **讨论区只产素材，不产结论**：结论只能由主闭环生成。

### 7.2 依赖方向

| 层 | 可以调 | 黑板 |
|---|---|---|
| L1 交互层 | L2（所有 AI 动作）；L5 的**两件事**（手动写入、导出）；L7 存储只读（渲染文档、版本历史、卡片历史、trace） | 只读；订阅事件 |
| L2 编排层 | L0 注册（读定义）/ L4 记忆 / L5 工具 / L6 Harness | **唯一写者** |
| L4 记忆层 / L5 工具层 / L6 Harness | 落 L7 存储 | 只读 |
| L0 注册中心 | L7 存储（注册条目要落库、要能改状态；它不读黑板、也不参与任何一轮流转） | — |
| L3 通信层 | 不调任何层（它本身就是通道） | — |
| L7 存储底座 | 不调任何层 | — |

**为什么 L1 能直接碰 L5 的那两件事**：手动改文档和导出不是 AI 流程，没必要绕经编排；它们照样走 M20（唯一写入口，`trigger = manual`），所以"AI 不能直接改文档"这条不受影响。

**为什么 L1 能读黑板、却不能发事件**：界面要渲染，就得多一份只读的状态源；但用户点确认、打字纠正不是"状态变化通知"，那是对编排层的调用。事件一律由状态的生产者发。

每层具体暴露哪些接口见契约文档 §5.3。

### 7.3 功能组合

| 组合 | 包含模块 | 用途 |
|---|---|---|
| A 最小生成闭环 | M2 M13 M24 M22 M8 M28 M9 M5 M20 | 用户输入 → 复述理解 → 生成 → 出卡 → 确认 → 写入 |
| B 讨论区取思路 | A + M4 M6 M7 M11 M12 M27 M29 | 角色群讨论 → 整理成候选 → 用户勾选 → 作为输入进 A |
| C 带工具 | B + M10 M16 M18 M19 M23 | AI 能搜索、能读材料、受权限约束 |
| D 带复利 | C + M14 M15 M17 M30 | 反馈进简报与 skill，**验证通过才生效** |
| E 带观测 | 全部 + M25 M26 | 每轮可复盘 |

## 8. 端到端数据流

**系统只有两个入口：主闭环和讨论区。** 两者是上下游，不是并列——讨论区产出思路素材，用户挑中的素材作为输入进入主闭环。讨论区自己不产出卡片。

### 8.1 主闭环是一场长任务

**它不是"一问一答就出结果"，而是可以持续很久的过程。** 卡片组是中途卡住时的裁决机制，**不是输出的终点**；填充卡是收尾，最后才来。

1. 用户**在目录树上选 schema 字段**（写范围，可多选、可什么都不选），然后输入要求
2. **M13 组装上下文**：文档内容 + 项目简报（常驻）+ 生效记忆 + 材料包 + 任务至今的全部输入 + 本轮输入
3. **M8 带着上下文复述理解** → 确认理解卡
   - 复述必须**具体**：说清楚"你要我改文档里的哪一块、按什么约束、改成什么样"
   - **合格标准：复述里必须包含至少一个只有读了文档才知道的信息。** 否则就是在复读用户原话，等于抄一遍，没有价值
4. 用户确认，或直接在输入框里打字纠正
   - **纠正 → 直接按纠正后的理解走**：重新组装上下文（纠正可能改变该读什么），然后直接进入生成。**不再出第二张确认理解卡**，不让用户为同一件事确认两次
5. **进入循环**（复用已经组装好的上下文；这一轮里用户的卡片回应作为新的上下文块补进去，不重头读一遍文档）：
   - **M24 按预算裁剪**
   - **M8 逐角色调用**：M22 模型 + M23 权限 + M10 决定工具 → 每个角色产出信息包（带依据）
   - **审查**：内容都产出之后，审查角色读**全部**主张，专门提反对意见（`challenge`）。分歧卡就是从这儿来的。它必须排在内容角色**之后**——内容还没齐，没什么可审的
   - **M8 汇总**：合并、去重、判断有没有分歧
   - **判断卡住了吗**
     - **缺信息 / 有冲突** → M9 组装一组卡片（最多 5 张，一张卡一个议题）→ 用户逐张回应 → 提交 → **回到循环开头继续完善**（这一组里没有填充卡，不动文档）
     - **没问题了** → 跳出循环
6. M28 成稿 → **一张填充卡**，里面是提案数组（每条标明落到哪个字段、追加还是改写），按字段分区渲染
7. 用户确认
8. **M20 事务写入**：校验版本 → 写入 → 更新 block → 产生一个文档版本
9. M12 广播事件 → 文档刷新；M17 提炼候选记忆；M25 记 trace

确认之后如果又发现问题，就再来一组卡片。

### 8.2 讨论区

1. 用户输入 → M7 从角色池预选参与讨论的角色（**最多 4 个**，每个说明为什么选它）→ 用户可增删换 → 确认后开跑
2. **一轮 = 每个角色各说一次**，说完默认停下
3. 停下后出现「整理成提案」按钮
4. M29 把发言整理成思路候选：一句话主张 + 出处 + 建议落到哪个字段
5. 用户勾选想要的（挑的是结构化候选，不是聊天记录）
6. 勾选结果在下一轮主闭环**组装上下文（第 2 步）**时以材料包身份进场，用掉一次就标成已消费，不会每一轮重复带进来

其它结束条件：用户随时叫停；到轮次上限。

### 8.3 全景图

主闭环和讨论区这两张全景图，连同每一步"谁交给谁、传哪些字段"，都放在**契约文档 §7**。同一个流程在两个文档里各画一张，迟早会有一张是过期的，所以这里只留产品语义（8.1 / 8.2），图只留一份。

**"跑通"的定义**：不是界面能看到结果，而是**每一跳的数据结构都对得上**——按契约文档 §7 的字段级走查逐行核对，这就是 AC9。

**每一步怎么通知别人**在契约 C13：谁在什么时候发事件、谁订、payload 带什么，以及一张"数据流每一步有没有事件覆盖"的核验表。没有那张表，"事件够不够"就只能靠感觉。

## 9. 卡片机制

**卡片是系统在长任务过程中卡住时向你求助的方式。** 它不是审批流程，也不是输出的终点。

**它什么时候出现**：系统干活的过程中发现缺信息、或者角色之间有冲突，就把问题整理成卡片抛出来等裁决。裁决完继续干。**填充卡是例外——它是收尾，要等内容都没问题了才出现。**

**一组最多 5 张。** 每张卡只针对**一个议题**：一个冲突，或者一个独立类别的问题。每张卡的信息量可以大一点，但必须聚焦——不能一张卡拉七件事。超过 5 张说明问题没拆干净，应该分批问。

**填充卡单独成批**（它那一批里只有 1 张），所以"5 张"这个上限没有例外，也不需要为它开一个口子。

### 9.1 四种情形

同一张卡，内容不同：

| 情形 | 什么时候出现 | 卡片上是什么 |
|---|---|---|
| **确认理解** | **每一轮用户输入之后** | 系统**读过文档之后**复述"你要我改哪一块、按什么约束、改成什么样" |
| **补信息** | 系统缺信息，做不下去 | 要问的问题 |
| **选一个** | 角色之间意见矛盾 | 分歧在哪 + 几个备选方案，每个带自己的依据 |
| **确认内容** | **只在最后，内容都没问题了才出现；永远只有一张** | 按字段分区的提案列表，每条只有"要 / 不要" |

**为什么理解确认每轮都有**：它确认的是**这一轮用户输入的意思**，不是项目级的目标。用户这轮可能是在说目标，也可能是在说"帮我看看功能清单缺什么"——先对齐这一轮的意思，后面才不会跑偏。

**它必须带着上下文复述，否则没有价值。** 如果用户说"细化一下功能清单"，系统回一句"我理解你要细化功能清单"，那是抄一遍。有价值的复述是：

> 我读了文档。现在功能清单第 3 条只写了"消息推送"；结合目标里的留存率要求、和依赖与边界里写的推送通道限制，我理解你要的是把它拆成可验收的行为规则，而不是加新功能。是这个意思吗？

**合格标准（可验收）**：复述里必须包含至少一个**只有读了文档才知道的信息**。做不到，说明 M13 的上下文没组装对，或者系统在复读。

用户纠正之后**直接按纠正后的理解走**：重新组装上下文（纠正可能改变该读什么），然后直接生成。**不再出第二张确认理解卡**。

### 9.2 用户怎么回应

**每张卡片下面都有输入框。** 用户可以点按钮选，也可以直接打字说要改什么。**两种方式地位相同。**

没有"驳回"这个专门动作——用户说什么就是什么，系统按用户说的继续。

### 9.3 为什么卡片是"问卷"而不是"审批"

四个产品决策，对应的字段规则见契约 C7 / C8：

- **提交之前可以回到任意一张改，提交之后整组冻结。** 交卷语义。不做边答边写——否则用户答到第三张想回头改第一张就废了。
- **提交完不是结束。** 只有填充卡确认完才算写入文档；中间那些裁决卡提交完，系统接着往下完善。
- **跳过的卡片不丢**，落到文档的"待确认问题"分区。PM 工具的价值不是逼用户当场决定所有事，而是让没决定的事有地方待着，下次还找得到。
- **每批最多 5 张、没有例外，一张卡一个议题。** 填充卡单独成批。超过 5 张说明问题没拆干净；一张卡拉七件事用户没法答。

### 9.4 依据可见

每张卡片都能回答"这条内容依据什么"——引用了哪段文档、哪条结论、哪份材料。既防幻觉，也给用户判断的抓手，同时是 M25 观测的入口。

冲突要**暴露而不是抹平**：分歧卡必须把分歧点摆出来，不能只给一个被综合过的结论。对 PM 来说"争议在哪"本身就是产品价值。

### 9.5 填充卡

填充卡是收尾的那一张，里面装的是**提案数组**——一次生成可能改动好几处，全装在这一张卡里，渲染时按字段分区：

```
提案 3 条

【目标】替换
  现在是：给产品经理用
  改成：给产品经理和工程师之间做需求对齐用的工具
  [要] [不要]

【功能清单】追加
  第 6 条：支持把讨论候选带进主闭环
  [要] [不要]

【验收条件】替换
  ...
  [要] [不要]
```

三条产品决策（字段定义见契约 C7）：

1. **填充卡永远只有一张**，多条改动装在一个提案数组里。它**单独成批**，所以不会挤占裁决卡的名额，也不会把一批撑过 5 张。
2. **卡片上只有"要"和"不要"，没有编辑器。** 想改文案就写进文档后再改，或者删掉这条重新说一次。**编辑归文档**——文档本来就能手动编辑，卡片只负责收敛决定。多放一个编辑器就得回答"卡片里改的和文档里改的谁优先"，还得再定一套合并规则。
3. **"删除"和"跳过"是两件事**：删除是提案级的（这条不要），跳过是卡片级的（这张卡我暂时不想决定）。前者本身就是一条反馈信号——AI 提了一条你不想要的，这件事要记下来喂给复利，否则系统永远不知道它提错了。

## 10. 反馈与复利

反馈只有构成闭环才有意义。复利产出**两类**东西：

```
用户的每次回应 ─┬→ 教训 → 项目简报 → 下一轮由 M13 常驻注入 → 生成变好
                └→ Skill → L0 注册中心 → M7 按 skill 决定怎么编排
```

### 10.1 五条必须成立的约束

1. 项目简报与按需检索的上下文**分开**。简报是常驻的那一小块，不能无限膨胀。
2. 反馈必须能回答"它改变了下一次生成的什么"，否则就是装饰。
3. 已确认结论进检索库，与项目简报形成"常驻 + 按需"两级记忆。
4. **候选记忆要先"候选"再"生效"**：未确认的不进常驻上下文，否则一次错误反馈会污染以后所有生成。
5. **记忆会失效**：引用的内容被改动后，这条记忆标记失效，不再作为依据。否则会拿过期共识生成新内容。

### 10.2 验证机制（为什么必须有）

没有验证的复利会退化成垃圾堆积：每个具体问题都收割一条"教训"，聊一次就总结一个"skill"，注册中心很快被稀释到没有指导意义。所以**教训和 skill 都必须先当候选，验证通过才能生效**。

生命周期：`候选 → 试用观察 → 晋升 → （长期无效）退役`

晋升要看的信号（具体阈值见开放问题）：

| 信号 | 说明 |
|---|---|
| 使用次数 | 用过足够多次才有统计意义 |
| 采纳率 | 带这条 skill 生成时，卡片被确认的比例要高于不带它的基线 |
| 无回归 | 引入它之后没有带来新的问题 |
| 用户确认 | 可选，用户显式认可一条教训时可以直接晋升 |

淘汰：连续多次使用无正向效果，或长期未被使用 → 降级 → 退役。退役不删除，留痕。

**只有 M30 能改状态**，人工不能直接把 skill 置为生效。

## 11. 项目简报

项目简报是**项目级的 AGENTS.md**——给 AI 看的项目说明，每一轮都注入。

### 11.1 内容分四段

| 段落 | 写什么 |
|---|---|
| 项目是什么 | 这个项目大致是什么，解决什么问题 |
| 注意事项 | 不该做什么、有什么不能碰 |
| 原则 | 做事的方式 |
| 术语表（可选） | 项目里特定词的含义，避免 AI 理解偏 |

### 11.2 一条一条加，逐条确认

简报**不是一次性生成的**，是一条一条累积的。每加一条，系统问一句：**这条提供了信息吗？有用吗？还是废话？**

三个选择：`有用`（进，且每轮都注入）/ `一般`（进，但降级为按需检索）/ `废话`（不进）。

为什么要这样：AI 的典型毛病是过度服务。简报如果一次性生成，必然灌一堆正确的废话。逐条确认是把"要不要留"的判断权交回给人。

### 11.3 容量

**控制在 120 行左右**，作为硬上限。超了触发淘汰提示，让用户挑最没用的删。

简报无限膨胀会稀释掉真正重要的那几条。

### 11.4 内容从哪来

1. 用户直接写（M14 提供编辑入口）
2. 从用户的回应里提炼（M17）
3. 从已确认的文档内容里提炼

### 11.5 初始化内容

"原则"这一段可以内置一版默认内容，来自 Karpathy 给 AI 编程助手定的四条原则，对"帮 PM 写文档的 AI"同样成立：

1. **先思考再动手**：不确定就问，不要把困惑藏起来。有几种理解就列出来，不要默默选一个。
2. **简单优先**：只解决被要求的问题，不做投机性扩展，不为"将来可能需要"添加东西。
3. **精准修改**：只改该改的，不顺手改别的。
4. **目标驱动**：先定义什么算完成，再动手。

## 12. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 卡片太多 | 一次输出十几张卡，用户窒息 | 限制一组卡的数量，或让补信息的卡先集中问完（开放问题） |
| 上下文膨胀 | 项目简报无限增长，稀释掉重点 | §11.3 的 120 行上限与淘汰规则 |
| 记忆污染 | 一条错误反馈被当成长期记忆 | 候选与生效两态 |
| 记忆过期 | 引用的内容改了，旧结论还在当依据 | 失效机制 |
| 反馈变装饰 | 收集了但不影响生成 | §10.1 的五条约束 |
| 讨论变泛聊 | 角色群退化成场面话 | 讨论区不承担收敛责任；素材价值靠用户的勾选行为体现 |
| 编排翻车 | 死锁、死循环、格式解析失败 | 依赖必须是 DAG、必须有最大轮次、输出必须校验 + 重试 |
| Skill 堆积 | 每个具体问题都收割成一个 skill | 领域级通用的才叫 skill；具体问题归教训 |

## 13. 验收条件

**AC1 主闭环跑通**
用户输入 → 复述理解 → 生成 → 出卡 → 回应 → 确认 → 写入文档，全程无断点。

**AC2 人在环上**
不存在任何 AI 直接改写文档的路径；所有写入都能追溯到一次用户确认。

**AC3 依据可追溯**
每张卡片都能回答"这条内容依据什么"，并指向具体的文档片段、结论或材料。

**AC4 分歧可见**
角色意见冲突时产出的是摆明分歧的卡片，不是被抹平的单方结论。

**AC5 讨论区接得上主闭环**
一轮讨论结束后能整理成结构化候选；用户勾选后作为材料走进主闭环直到写入。讨论区自身不产出卡片。

**AC6 记忆两态**
新提炼的记忆先进候选态；不进常驻上下文；引用的内容改动后失效。

**AC7 事务性**
确认要么全部生效，要么全部不生效；用户手动改过的 block 不会被静默覆盖。

**AC8 版本与回退**
每次写入产生一个版本，用户手改也产生版本（**一次显式保存 = 一版**）；可回退到任意历史版本，**回退产生新版本并记下从哪一版退回来**，不删不改历史。

**AC9 契约连通**
按 CONTRACTS.md §7 的字段级走查，每一跳"谁交给谁、传哪些字段"都能对上是哪个契约。

**AC10 先复述理解**
每轮用户输入之后，第一张卡片是确认理解，且**复述里包含只有读了文档才知道的信息**（不是复读用户原话）；用户纠正后，重新组装上下文再生成，而不是拿着旧理解继续。

**AC11 卡片组语义**
确认前可任意回头修改；确认后全部只读；确认后要改只能新开一轮，旧记录可查。

**AC12 失败可见**
生成失败时，用户能看到失败在哪一步、原因是什么、能不能重试。

**AC13 写范围被强制**
有选区时，AI 产出的每条提案都落在选中的字段内；尝试写选区外的字段会被 M20 拒绝，而不是靠提示词自觉。选区在轮内不变，每轮重新选。

**AC14 填充卡是提案数组**
收尾只有一张填充卡，内容包括多条提案，按字段分区渲染；每条标明是追加还是替换；用户只能要或不要；确认时只写入要的那些。

**AC15 事件完整、来源单一**
数据流里每一个**需要被别人知道**的状态变化都有确定的事件，且同一变化只发一条；新增一个订阅者时不需要新增事件类型。8 个事件全部可用。

## 14. 范围外

- 多人协作与权限体系（**只有一个用户角色**）
- 变更影响面分析里的 **AI 语义层**部分（改了目标里某个概念，自动推断功能清单哪条措辞要调）；**模板字段之间的硬依赖提示保留**（见 C1）
- RAG：记忆多了之后才需要，触发信号是关键词检索开始频繁漏召回
- 与工程侧工具（Jira / 飞书 / 原型）的双向同步
- 多模型路由与成本优化
- 导出（M21）

## 附录 B：模板字段（初版，9 个）

文档按这 9 个字段分区，AI 只能往这些分区里填。

| # | 字段 | 作用 | 必填 |
|---|---|---|---|
| 1 | 项目是什么 | 这段产品想法到底是什么，给谁解决什么问题。**确认理解卡复述的就是它** | 是 |
| 2 | 目标 | 做成什么样算成功，含明确不做什么 | 是 |
| 3 | 用户与场景 | 谁用、在什么情况下用 | 是 |
| 4 | 功能清单 | 要做的功能点，细到行为规则。**append 用得最多的字段** | 是 |
| 5 | 依赖与边界 | 依赖什么外部条件、有哪些不能碰的约束。**这个字段设为常驻上下文**，这样约束能传导到功能清单的生成 | 是 |
| 6 | 风险 | 可能出什么问题 | 否 |
| 7 | 验收条件 | 做到什么算完成 | 是 |
| 8 | 待确认问题 | 用户跳过的卡片自动落到这里：写文档那一次，M20 把这一轮所有跳过的卡一并追加进来 | 自动维护 |
| 9 | 开放问题 | 还没想清楚、但一直没人问起的事项。**用户自己写** | 用户维护 |

两点说明：

- 8 和 9 不是给 AI 填的，是给"没决定的事有地方待着"用的。
- 字段的必填与否决定 M28 的行为：必填字段缺内容时，应该产一张**补信息卡**而不是编一个。这就是"信息不足"的判定依据。

模板会持续迭代，这是能用的初版，不是终版。
