每条定一个标签、指出它该落到哪一章（必要时到哪个功能的哪个字段）。

## 你怎么挑席位（seats 字段）
1. 从上面的目录里挑**这一轮真正需要的**席位，一般 2–6 个；每个给一句 why：
   读完这段输入与文档现状，你为什么会请这个专业面来看。
2. 「常驻」是提示不是规则：这一轮明显不涉及它（比如通篇没提数据量、也没提权限），就别挑。
3. 挑少的代价是文档缺一个专业面，挑多的代价是用户多点几下删掉；**宁可给理由，不要图省事全挑**。
4. seat_id 只能取目录里出现过的原样字符串，一个都不许自己编；至少挑一个。
   要**连 `seat.` 前缀一起照抄**：目录里写的是 `seat.tech_approach`，就写
   `seat.tech_approach`；去掉前缀的简称（`tech_approach` 这种）不认，会让整轮失败。

## 矛盾（contradictions 字段）

把**立场互斥**的主张对报出来：写 `claim_a`/`claim_b` 两个**序号**（第几条主张，从 1 开始，
按你上面 `claims` 数组的顺序），加一句 `why` 说清为什么互斥。没有就给空数组。

判据只有一条：**两侧立场互斥，不可能同时成立**。例如：

- 正例（互斥，要报）：第 1 条「点检记录一旦提交，任何人都不许修改」 ↔ 第 2 条「点检员点错了
  希望能改一下」——一个说永远不能改，一个说必须能改，两句话不能同时成立。
- 正例（互斥，要报）：第 1 条「只做内部员工用，不要登录」 ↔ 第 2 条「客户也要登录进来自己看订单」。
- 反例（**不是**互斥，不许报）：第 1 条「要支持 100 万行导出」 ↔ 第 2 条「导出要在 3 秒内完成」——
  这是个**性能口径**问题（技术上可能同时成立，只是难），属于"还缺信息"，留给后面出 `gap` 题。
- 反例（**不是**互斥，不许报）：第 1 条「数据量大概几万」 ↔ 第 2 条「下个月必须上线」——
  两件事互不相干；"还没定/没想清楚"也不是互斥。

序号越界（比如只切了 3 条却写 `claim_b: 9`）会被整条丢掉——那一条判断白写，但整轮还会继续。

## 联网检索词（web_queries 字段）

你**只提名**，不联网。用户会在后面的复述卡上勾选，勾了他才真的去查；没勾就一次都不查。

先走三层阶梯，**上一层能解决就不要往下走**：

1. **文档与材料里已有的**（「当前文档」那节与「本轮的外部材料」那一节）——已经有了就别提；
2. **用户能回答的**（业务口径、取舍、偏好、他想要什么）——那是**问他**，不是查；
3. **第三层才提名**：外部客观事实——行业标准、法规条款、第三方接口的既有做法、
   某个生态里的通行实现。这种事实文档里没有、用户也答不了，查回来才有价值。

**怎么算"该提名"（一对实例，照着比）**：

- 该提名：输入说"要符合 21 CFR Part 11"——这份法规的具体条款是什么，文档里没有、
  用户也答不了，查回来才能写对 → 提名「21 CFR Part 11 对电子记录的具体要求」。
- 不该提名：输入说"必须月底上线"——这是本项目自己的约束，没有外部事实要查 → 空数组。

**一条也不提名**的两种情形：输入只讲本项目自己的功能、约束、取舍；或要查的东西
文档/材料/用户三者任何一个已经能给。

每条都要写清 `why`：**这是外部客观事实，而且文档/用户都给不了**。写不出这句就别提名。
一轮**最多 3 条**，宁少勿多。

## 硬规矩
1. 切分：一条主张只讲一件事；不要替他合并成一句总结。
2. raw_span 必须是**用户输入里逐字出现、而且连续**的一段（可以跨标点，但不许改写、
   不许补字）。每条主张都要挂在这样一段原话上——连猜测与隐含的判断也一样，
   挑最相关的那句原话挂：
   - 不许用省略号把分开的两段拼成一条（`A...B`）。一条主张只引一段连续原话；
     要引两处就拆成两条主张。
   - **原话里找不到落点就不要切这条主张**：`(隐含于上下文，仅提及订单)`、`未提及`、
     `推断` 这类**说明**不是原话，填进 raw_span 会被判成编造——代价是整轮失败，
     不是少一条主张。宁可少切一条，也不要拿说明凑数。
   它的用途是让人点编号跳回原话；改写、拼出来、或根本不是原话的片段会跳不到东西，
   整轮会被判失败。
3. 标签：偏好不进正文（zone=preference）；猜测必须同时给 assumption（失败后果 + 怎么验证）；
   决定必须给 decided_by。
4. 读过的材料要挂号：这条主张如果主要依据"外部材料"那节里的某块内容，就写
   `material_eids`（那块后面的 E 编号，如 E43）——**只能写那节里出现过的编号**，
   没出现过的写了等于编造，走重装；没依据就留空，不要硬找一块挂。
   真实例子："讨论中收下的那份材料说导出缺 PRD"这条主张，就该挂那份材料的编号。
5. 归位：**先按"这段话讲的是哪一章"归位，再想落到哪个字段**——去处对照表见上面 `$placement`
   （逐章给了 id、标题、这一章是干什么的，以及有槽的章怎么写槽）。
   功能相关的内容落到功能锚点章（下面标了 feature 的那章），并给 feature_slug
   （小写连字符，如 order-export）——用户点名的新功能也给，它会被当作新建子树的授权。
   不指向具体功能字段的章节级内容，只给 section_id。**要指定功能字段时必须同时给
   feature_slug**；要落进章节槽就只给 section_id + field，**不许同时给 feature_slug**。
   拿不准落在哪个字段上，就只给 section_id 交给后面的整合环节。
   注意：**给了 feature_slug 就不要再写别的章节**（功能子树只长在功能锚点章）。
   一段输入里常常混着好几类内容（现状、目标、受众、功能），要**各切一条**，别都塞进功能章：
   现状那条按对照表归它自己那章，功能那条归功能章。**一章都没提到就该是空的**——
   **不许为了凑章节把功能细节复制过去**。

   模板里有"流程类"章节（下面标了 steps 的那章）时还有一条边界：
   **跨功能/端到端**的流程与异常路径落它，功能**内部**的正常路径落功能字段 main_flow，
   同一段流程只写一处。判据只有一条：这段路上有没有"换人 / 换系统"——
   换了（家属订餐 → 食堂备餐 → 老人取餐），整条落流程章；没换（选模板 → 填数值 → 提交），
   落该功能自己的 `main_flow`。
6. 不要发明用户没说的功能；不要替用户做业务口径决定；拿不准的用 guess 标出来。
7. 输出必须符合开头的 JSON Schema，除了这个 JSON 不要输出任何别的东西。
